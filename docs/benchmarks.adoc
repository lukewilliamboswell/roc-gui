= Measuring scaling

A scaling benchmark is a realistic Roc application driven by the same semantic
steps as a behaviour specification. Scale comes from application data: more
rows, more text, a deeper tree, or a change farther from a render boundary. A
benchmark never receives a special element or alternate renderer unavailable to
an ordinary application.

The specification runner builds Roc applications with the native development
backend by default. Compare captures from the same backend and executable
before interpreting timing differences; the Rust host uses its independent
release build profile.

== Benchmark policy

Add a `benchmark` clause before `steps`:

[source,scheme]
----
(test "Rows: create 10,000"
  (benchmark :warmups 2 :samples 7 :iterations 1
             :scale 10000 :initial-size 0 :change-size 10000)
  (steps
    (mark-metrics)
    (click (role button :name "Create 10,000 rows"))
    (expect-patch :kind replace :staged 40015 :removed 15)
    (expect-count (text-prefix "Row ") 10000)
    (expect-visible (text "Rows: 10000"))))
----

`:warmups`:: Complete runs discarded from timing summaries. Warmups exercise
the same setup, operation, and assertions as samples.
`:samples`:: Runs retained for measurement.
`:iterations`:: Measured runs per sample policy. Each lifecycle starts from a
fresh application state.
`:initial-size`:: Items present before the marked operation.
`:change-size`:: Items the operation is intended to affect.
`:scale`:: Resident workload proved by an `expect-count` with the same value.

Every benchmark has exactly one `mark-metrics`. Put state preparation before
the mark and the user operation plus its assertions after it. The runner
attributes cycles to setup or measured phases; locator resolution and assertion
scans are harness work, not part of the operation duration.

The declared scale is a label until the application proves it. Requiring a
matching `expect-count` prevents a fast but broken “10,000 row” case from being
reported when it created fewer rows.

== Read a scale ladder

One large case cannot distinguish fixed cost from growth. Measure the same
operation at three or more sizes, then compare columns in the scaling summary:

[source,sh]
----
python3 scripts/run_specs.py 'benchmarks/rows/specs/create-*.scm'
python3 scripts/summarize_suite.py .test-out/specs/TIMESTAMP
----

Look across sizes rather than treating one duration as a score:

* the Roc work view separates routing, application update, application render,
  and platform lowering time and allocator activity;
* validation and graph-application growth point to host graph work;
* staged and removed node counts explain how much structural work was asked for;
* allocation totals and process resources expose memory cost across samples;
* `NULL` means that component did not provide that measurement. It is not zero.

Timing is diagnostic evidence, not a pass/fail threshold. Semantic assertions,
patch expectations, scale verification, and capture health are deterministic
gates.

== Verify depth with a process-stack budget

Tree-shape specifications exercise ordinary construction, lifted structural
containers, translation ownership, current-state delegation, and replacement
by a shallow tree. Run the same production executable and specifications with
an explicit process-stack budget as well as the ordinary environment. Preserve
the selected compiler and build mode in the comparison evidence.

The structural regression reaches 10,000 lifted containers and exercises two
leaf updates before teardown. The translation regressions build and retire
1,000 owners, including alternating state types, current-state task resolution,
removal before completion, and veto at an intermediate boundary. Run each with
a 1 MB stack to verify its headless construction, adaptation, lowering, and
release path. Record the compiler backend with these results. A successful
case establishes that particular path; it does not measure arbitrary
application recursion or GPUI layout and paint depth. Record failures and
their owning call paths in the backlog rather than widening the process stack
to make the result pass.

== Bound recorder detail overhead

Use the same realistic scaling case and isolated job count for both recorder
policies:

[source,sh]
----
python3 scripts/run_specs.py 'benchmarks/rows/specs/select-10k.scm' --jobs 1 --detail summary --output .test-out/observer-summary
.test-out/observer-summary/bin/rows --host-run-spec benchmarks/rows/specs/select-10k.scm --host-stats-output=.test-out/observer-full.rgstats --host-stats-job-count=1 --host-stats-detail=full
python3 scripts/analyze_stats.py .test-out/observer-summary/benchmarks/rows/specs/select-10k.rgstats
python3 scripts/analyze_stats.py .test-out/observer-full.rgstats
----

Invoking one executable for both policies keeps executable identity fixed. The
reference run recorded seven samples per policy. Summary recorded 18 cycles and
a 3089.204 ms median; full recorded nine additional setup cycles and a 3103.423
ms median. The full-policy median increase was 0.46%, and its complete sample
range remained inside the summary range. Treat 1% as the observed detail-policy
overhead bound for this case. Timing remains report-only, and a performance
decision reruns the bound on its comparison machine.

== Workload families

The suite varies operations and shapes that applications naturally produce:

Scroll:: Populate a named scroll region with 100, 1,000, and 10,000 ordinary
text rows. This measures eager graph construction and host materialisation; it
does not substitute a benchmark-only list or renderer.
Virtual list:: Populate the production fixed-row virtual list with 100, 1,000,
and 10,000 stable-keyed text rows. Semantic scale proves the complete logical
graph; interactive captures separately report viewport-owned materialisation
and recycling without treating offscreen rows as visible native entities.
Settings search:: Populate the text-input benchmark's virtual catalogue with
100, 1,000, and 10,000 categorised settings, then edit its controlled search
field to retain one category. Exact semantic counts prove both the
initial catalogue scale and the filtered result while the measured turn uses
the ordinary text-change route.
Rows:: Create, append, sparse update, select, idempotent reselect, delete,
clear, swap, and repeated selection at 100, 1,000, and 10,000 rows, with a
100,000-row sparse-update point for confirming large replace-with-removal
scaling. Row actions are ordinary action-button nodes, so this ladder also
exercises styled button lowering, native materialisation, dispatch, and
replacement at realistic application sizes.
Row boundaries:: Update the first, middle, and last item when each row owns its
own render boundary, and exercise selection, deletion, swaps, and sparse
updates whose invariants are owned by the collection. Persistent row `Index`
storage keyed by stable IDs is separate from display order, so resolving or
replacing a row follows a bounded radix path without scanning or copying the
collection. Local edits render one row and replace four nodes: its boundary
marker, row, text, and button. Collection-owned changes enumerate the boundary
frontier and, when memoization is enabled, retain rows whose complete input is
equivalent. Dynamic SHA-256 keys are stored when entries are created. The compact-view
toggle removes per-row management controls and puts keyed components directly
beside each other under the list container; its local-edit cases exercise
direct sibling identity without per-row wrapper scopes at 100, 1,000, and
10,000 rows in both memo modes. Component, patch, and validation counts establish
local work independently of unrelated sibling count. Captured timings and
allocation spans report only the work measured by their owners; they do not
establish copying, retained memory, or unmeasured native work.
Hover trail:: Move across a 100 by 100 grid of native buttons, lighting each
cell and leaving a delayed reset trail. Every cell is an unmemoized keyed
translation with persistent indexed state. Entry, exit, and completion ladders
at 100, 1,000, and 10,000 cells assert one boundary rendered, no comparison, and
two mounted nodes replaced. Reentry tokens and fresh grid keys protect against
stale completions. A 32-cell burst exercises queued work, and a window case
checks both grid corners and native GPUI mouse-move delivery. Native GPUI mouse-movement
tests exercise the same production views and event route. Callback durations
exclude waiting for reset tasks; cycle durations include the wait. Neither
headless captures nor injected window events measure physical pointer
sampling or compositor presentation latency.
Text rows:: Vary short, long, and metadata-rich text across row counts.
Textarea editing:: Edit the production multiline text control at 1,000, 10,000,
and 100,000 initial bytes through an ordinary append action. The same application
selects memoized or unmemoized keyed translations; exact value lengths,
component counts, and patch counts establish semantic equivalence. Root refresh
also distinguishes retained input from unconditional rendering. Append derives
its value from dispatch-time state. Same-length late edits change the final byte
to exercise comparison beyond the early length check. Policy switching keeps
the same key and mounted lifetime while resetting the cache. Allocation spans
report work observed by their owners; they do not establish snapshot-retained
bytes or identify copy-on-write as a cause. Serial A/A captures characterize
timing noise without turning timing into a correctness gate.
Checkboxes:: Lower and replace 10,000 real styled controls through their
ordinary check event route.
Tree shape:: Compare deep narrow trees and balanced trees so total node count
is not the only scaling dimension.

Keep each family as a usable application with specifications beside it. Add an
operation to an existing family when it uses the same state and interaction
model; create a separate application when the data model or UI shape is
materially different.

== Compare two captures

Generate captures serially on the same machine and compare matching cases:

[source,sh]
----
python3 scripts/analyze_stats.py BEFORE.rgstats --compare AFTER.rgstats
----

The comparison checks capture identity and workload compatibility before
showing a ratio. Use `--aa` to establish the natural spread of an unchanged
executable. Supply that validated capture to the scaling view to expose the
A/A spread bound and whether the measured spread exceeds it:

[source,sh]
----
python3 scripts/analyze_stats.py CAPTURE.rgstats --view scaling --aa-bound CAPTURE-aa.rgstats
----

Without `--aa-bound`, `aa_bound_ns` and `spread_exceeds_aa_bound` are `NULL`:
the capture contains no A/A evidence from which to infer them. Treat a change
smaller than an available bound as noise.

Compare different scales only when both captures came from the same executable,
application, target, machine, recorder detail, and isolated serial policy:

[source,sh]
----
python3 scripts/analyze_stats.py SCALE-10K.rgstats --view scaling --scale-against SCALE-100K.rgstats
----

The cross-scale report gives separate ratios for the Roc callback, native-tree
validation, canonical graph application, complete sample-lifecycle allocation,
and allocation attributed to measured Roc work spans. Lifecycle allocation
includes setup outside the marked operation. Span allocation includes only the
instrumented work attributed to measured callbacks. These scopes are not
interchangeable and the report labels both. A component whose evidence status
is not complete is `NULL` independently of the other components. Mechanically
incompatible captures make every ratio unavailable. Ratios are diagnostic,
report-only timing and resource evidence; semantic and capture-health results
remain the correctness gates.
