= Resource access and trusted grants

Roc GUI applications begin with UI, bounded timers, and isolated private
application storage. Documents, projects, save destinations, network services,
devices, clipboard observation, and capture sources require a grant whose scope
matches the user-visible task. A display name, path string, URL, or application
dialog is not authority.

== Security boundary

The supported application process is confined from ambient operating-system
resources. Trusted broker services run outside that process, own protected
selection and consent UI, and return opaque typed grants through the Roc ABI.
The operating system enforces the confinement boundary; Roc types make grants
composable but are not the sandbox.

The broker attributes every request to a stable application identity. Publisher
or package-identity changes do not inherit remembered grants. Development and
automation provisioning uses the same registry and operation paths, is visibly
identified as development authority, and never represents user consent.

|Network
|A named service or selected destination; public internet, LAN, loopback, and listening are distinct scopes

|Audio output
|Ordinary mixer service; exclusive access and unusual routing require separate scope
|Playback or session

|In-context trusted authorisation with a protected activity indicator
|Recording or call session

|USB and device services
|Trusted device and function selection, preferring purpose-specific services
|Until disconnect unless explicitly remembered
|===

Three file-shaped services are deliberately distinct and are never substituted
for one another. Opening a document or project is user data reached through
trusted selection. Private application storage is durable read-write state
isolated by application identity. Shipped application assets are the
application's own read-only content: they hold no user data, so they are
provisioned without a prompt, and they carry no authority beyond the one
directory handle they are, so they never stand in for either of the others.

== Grant semantics

A grant records the resource identity, operations, parent grant, application
identity, lifetime, revocation state, and resource budget. Applications receive
only an opaque rights-specific handle. Derived handles never broaden authority:
a project child remains beneath its parent, an HTTP redirect remains within its
destination grant, and a selected file does not reveal siblings.

Cancellation is a successful selection outcome. Denial, revocation, expiry,
unavailability, invalid handles, and resource limits are distinct typed
failures. Refcount cleanup releases a handle but is not revocation. Revocation
has one broker-owned linearisation point: operations accepted before it follow
their documented commit/cancellation rule; later operations and descendants
fail. Bytes already returned to application state cannot be recalled.

The trusted *App access* surface lists concrete grants, rights, lifetime, and
active connection or capture state, and provides revoke controls. Ordinary work
inside a valid grant does not reprompt. Expanding scope requires another trusted
decision, and refusal is rate-limited so an application cannot nag repeatedly.

== Trusted workflows

Open document and Open project are broker interactions, not application-rendered
confirmation dialogs. Save As brokers an atomic destination replacement and
defines cancellation, target races, temporary-file cleanup, disk-full behaviour,
and the commit boundary. Project imports, sidecars, multiple roots,
drag-and-drop, sharing, and file clipboard operations use the same grant rules.

Network enforcement follows the actual connection. It covers DNS results,
address changes, redirects, proxies, connection reuse, IP literals, loopback,
link-local, and private networks without a check/use gap. Connectivity and
credentials are separate grants. Permission to read a document plus permission
to send to a service permits that data flow; destination restriction alone is
not an exfiltration guarantee.

== Libraries and components

Libraries accept the narrow handle they need as an argument. They do not
reacquire ambient or global authority. A parent component may attenuate a grant
for a child but cannot describe that child as restricted while also giving it a
route to acquire broader authority. Native extensions belong to the trusted
computing base unless isolated behind the same broker boundary.

== Verification

Every resource slice includes its Roc API and hosted ABI, broker/host behaviour,
semantic locators, owner-recorded deterministic counters, failure specifications, a
normal-use scaling case, and documentation. Security assertions additionally
exercise minimal authority, trusted selection and cancellation, sibling and
parent denial, traversal and symlinks, expiry, root and child revocation,
queued/running work, races, identity changes, and privacy-safe evidence.

Headless semantic specifications prove the mounted graph and normal Roc event
route. They do not certify protected consent UI, compositor delivery, OS
confinement, accessibility, or native portal behaviour. Those claims require the
production GPUI path and external platform tests.
