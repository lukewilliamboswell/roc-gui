= What you build

Roc GUI is an action/state platform for https://www.roc-lang.org[Roc], hosted
on https://www.gpui.rs[GPUI]. You describe application data and how that data
looks. The platform owns the window, turns the description into native views,
and routes button presses back to Roc.

A Roc GUI application has three parts:

State:: The data that completely describes the application at a point in time.
Render:: A pure function from state to an element tree.
Action:: The result of handling an event: an update, no change, a proposal to
the parent, or asynchronous work with a pending state and completion.

[mermaid]
....
flowchart LR
    S[State] -->|render| U[Element tree]
    U -->|native host| W[Window]
    W -->|button press| H[Handler]
    H -->|Gui.Action.update| S
    H -->|Gui.Action.none| N[No UI change]
....

This model keeps application decisions in ordinary Roc values and functions.
There is no mutable widget object to synchronise with a second copy of the
application state.

== Vocabulary

Application:: Your Roc code: its state, render functions, and event handlers.
Platform:: The Roc package selected by the application's `app` header. It
defines the GUI API, lowers elements, and routes events.
Host:: The Rust executable support linked into the application. It owns the
window, mounted graph, and GPUI views.
Element:: An immutable Roc value describing one piece of UI, such as text, a
button, a row, or a column.
Element tree:: The nested elements returned by `render`; for example, a column
whose children are text and a row of buttons.
Mounted graph:: The host-owned representation of the element tree the
application displays.
Translation:: A way to embed a component that works with a smaller part of the
application state, such as one counter on a page of counters.
Render boundary:: A part of the UI that can update without rebuilding its
siblings. A translation creates one.
Specification:: A `.scm` file that drives user actions and assertions against an
application. The steps it contains decide whether the semantic runner or the
window runner takes it.
Capability:: Authority to reach one resource outside the application, such as a
directory, an HTTP origin, or the clipboard.
Grant:: The opaque handle that carries a capability into application code. A
grant cannot be forged, widened, or turned back into a path or a URL.
Observatory:: The opt-in recorder embedded in the host. It writes semantic and
performance evidence to a SQLite `.rgstats` capture.

== What the platform provides

* text;
* semantically named buttons and checkboxes;
* single-line and multiline text editors;
* images decoded from in-memory bytes;
* horizontal rows, vertical columns, panels, and modal dialogs;
* scrolling regions, virtual lists, and a retained canvas;
* components that can update independently;
* `.scm` specifications stored beside each application;
* opt-in SQLite captures for correctness and performance evidence.

The supported targets are Linux x86_64 with Wayland and Apple Silicon macOS.

Start with state, a render function, and actions. As the application grows, the
application guide introduces local components, preserving their identity, and
reusing unchanged UI. Those tools are available when you need them; they are
not prerequisites for building your first screen.
