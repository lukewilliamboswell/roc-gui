= Building an application

Start with one state type, a render function, and event handlers that return
actions. Ordinary functions are enough to organise a small application. This
chapter introduces local components when part of the UI needs to update
independently, then keys and memoization when their additional guarantees help.

== State, render, and actions

An application exports a state type and `main : Gui.Program(State)`. The whole platform arrives through one import:

[source,roc]
----
import pf.Gui

State : { count : I64 }

render : State -> Gui.Elem(State)
render = |curr_state| Gui.col({}, [
    Gui.text("Count: ${curr_state.count.to_str()}"),
    Gui.button({
        caption: "Add one",
        label: "Increment count",
        on_press: |prev_state, _event|
            Gui.update({ count: prev_state.count + 1.I64 }),
    }),
])

main : Gui.Program(State)
main = Gui.run({ init: |_access| { count: 0 }, render })
----

`init` takes the application's authority — a `Gui.Access` — and returns the
first state. It is the only place authority enters an application, and there is
no way to produce one, so an application holds exactly what it was handed and a
library holds exactly what it was passed. An application that acquires nothing
ignores it, as this one does. One that acquires later keeps it in its state,
because the task that acquires runs after `init` has returned. The Resource
access chapter explains why the platform is built this way.

Every acquisition is a question asked of that value, from inside a task:
`access.pick_directory!()`, `access.pick_file!(types)`, `access.app_data!()`, `access.assets!(config)`,
`access.audio!()`, `access.clipboard!()`, `access.device!()`, `access.http!()`,
`access.process!()`, `access.system_monitor!()`, and `access.tcp_connect!()`.
Each answers with a handle only for what the host has granted, and the handle
carries its own operations. Code that was never handed the authority has
nothing to ask.

`render` is pure: it reads state and returns a `Gui.Elem(State)`. A button handler
receives the state associated with its render boundary and an `Gui.EventPress`.
It returns an action:

`Gui.update(next_state)`:: Propose the next state and update the required
render scope, subject to the component's memoization policy.
`Gui.none`:: Keep the existing state and element tree unchanged.

The names in the example distinguish two moments. `curr_state` describes the
UI being rendered. The handler's `prev_state` is the state immediately before
its action is applied.

Roc values are immutable. A handler that captures `curr_state` keeps that
snapshot alive in its closure. Later updates to a shared list or string may
therefore require cloning storage to preserve the captured value. Derive actions
from `prev_state` to avoid unnecessarily capturing the renderer's snapshot.
This does not eliminate cloning: other retained values, including memoization
snapshots, can still require it. Renaming a captured value does not change its
ownership or lifetime.

Using the handler argument also matters when handlers are retained across
updates: it supplies the latest state, whereas a captured render snapshot
still describes the earlier render.

Use `Gui.none` when an event is valid but has no effect, such as pressing a
decrement button at a lower bound. It is both clearer and less work than
returning an unchanged state with `Gui.update`.

An action is a value describing a transition, not a transition performed.
Constructing one changes nothing; returning it from a handler is what asks the
platform to apply it. Every transition is applied on one thread, one at a time,
so a handler's first argument is always the state that precedes it. This model
is Richard Feldman's, from his design document _Design Idea: Action-State_; the
architecture chapter records that origin and the reasoning behind it.

=== Pure application assembly

`Gui.run({ init, render, window })` describes an application with ordinary
initial state and a pure renderer. `window` is optional. Resource acquisition
and window-dependent interactions belong in actions.

Reusable modules export ordinary render functions such as
`Workspace.render : Workspace.State -> Gui.Elem(Workspace.State)`. A parent
composes them through `Gui.translate` or `Gui.translate_with`; no setup-time
registration is needed. The host assigns each mounted boundary its lifetime.
The module does not call `Gui.run` or choose the application's window.

== Asynchronous actions

Use `Gui.task({ pending, run, resolve })` when an event needs to wait for
external work. `pending` describes the UI while that work runs, such as a loading
indicator. After accepting that state, the platform runs `run` on its bounded
worker pool and passes the result to `resolve` on the UI thread.

The resolver receives `prev_state`, the state immediately before completion,
so it can preserve edits made while the worker was running. Capture only the
request data needed by the worker; derive the completion action from the
resolver's argument. Resource operations require the grants described in the
resource access chapter.

Tasks belong to the component that accepts them. Removing that component
suppresses completion delivery, but does not necessarily cancel the external
operation. The local-state section explains how a parent can own work that must
survive a child closing.

=== Timers and subscriptions

`Gui.Timer.start!({ interval_ms })` creates an opaque `Gui.TimerHandle` for intervals
from 1 through 60,000 milliseconds. `handle.next!()` waits for one tick
and belongs inside `Gui.task`; the next wait is started only after the
previous completion has been applied. This pull contract bounds backpressure
at one in-flight wait and does not accumulate missed ticks.

`handle.cancel!()` is idempotent, wakes an outstanding wait, and makes it
resolve as `Canceled`. Dropping the last typed `Box(U64)` handle also releases
the host registry entry. Applications retain the handle in state and decide
whether a `Fired` result schedules another wait.

== Elements and layout

`Gui.text(value)`:: Display a string, inheriting colour and size from its
container.
`Gui.button({ ... })`:: Display a controlled,
styled action button. `caption` is visible text, `label` is its stable semantic
name, as in every other control, and `enabled` defaults to `True`. Enabled
buttons participate in keyboard
tab order and activate with Enter or Space. Disabled buttons remain visible
with a subdued appearance and accept neither pointer nor keyboard activation.
Props include padding, sizing, growth, foreground and interaction colours,
border, radius, font size, font weight, and overflow. A call that gives only
`caption`, `label`, and `on_press` is the concise text button.
A button accepts `on_hover_enter` and `on_hover_exit` as optional
`Some(|prev_state, event| Gui.update(...))` callbacks. Their defaults are `None`:
unconfigured buttons allocate no hover routes. `Gui.EventHover` carries no fields.
Hover callbacks receive current state and return ordinary actions, including
cell-owned tasks. Native hover transitions follow GPUI pointer movement with no
mouse button held; repeated movement inside a button emits no additional enter.
Disabled buttons emit neither hover callback. Removal does not synthesize exit.
Any other element takes the same two modifiers, `on_hover_enter` and
`on_hover_exit`: the element is wrapped in a hover region that reports the
pointer entering and leaving it and presents nothing. The region takes its
element's share of the parent's space, so wrapping changes no layout.

Keep button labels and keyed projections stable. Rebuilding a hovered cell to
change its color preserves its native identity and inside state; it does not
produce another enter. `hover_bg` remains a native visual refinement independent
of these callbacks. Set it to `Default` when application actions own the hover
color, as in `benchmarks/hover-grid`.

[source,roc]
----
Gui.button({
    caption: "Preview",
    label: "Preview item",
    on_press: |_, _| Gui.none,
    on_hover_enter: Some(|prev_state, _| Gui.update({ ..prev_state, preview: True })),
    on_hover_exit: Some(|prev_state, _| Gui.update({ ..prev_state, preview: False })),
})
----

`Gui.checkbox({ ... })`:: Display a semantic checkbox and
handle `Gui.EventCheck`. `box_bg`, `box_checked_bg`, `box_border`, and
`mark_color` colour the indicator itself, which `fg` does not reach; each
defaults to the host's own value. Props include enabled state, gap, padding, sizing, growth,
foreground and interaction colours, border, radius, font size, font weight,
and overflow.
Enabled checkboxes participate in keyboard tab order and toggle with Space;
disabled checkboxes do not accept focus or activation.
`Gui.textarea({ ... })`:: Display a controlled multiline
text editor and handle `Gui.EventInput`, which carries the complete requested
value.
`label` is the stable semantic name; `placeholder`, `enabled`, and `read_only`
control editing behaviour. A read-only textarea retains multiline layout and
scrolling for response and log views. Textareas share the native style fields
and default to a 160-logical-pixel editing viewport.
`Gui.image({ label, bytes, format, ... })`:: Decode and render
capability-safe in-memory image bytes through GPUI. The explicit format is one
of `Png`, `Jpeg`, `Webp`, `Gif`, `Svg`, `Bmp`, or `Tiff`; fit defaults to
`Contain` and also supports `Cover`, `Fill`, `ScaleDown`, and `None`.
`grayscale` applies a native rendering effect. The declared box is
authoritative: `width`, `height`, and the minimum and maximum fields size the
element, and `fit` is the rule that maps the decoded pixels into that box. Image
sources are values, never ambient filesystem paths or URLs, and `label` is the
stable semantic name.
`Gui.text_input({ ... })`:: Display a controlled,
single-line native editor. `label` is its stable semantic name, `value` is the
authoritative application value, and `placeholder` is shown only while empty.
Committed edits deliver the complete value in `Gui.EventTextChange`; Enter delivers
`Gui.EventTextSubmit`. The host retains focus, caret, selection, and an active IME
composition across controlled rerenders. Disabled fields accept neither edits
nor submission. Text values are bounded to one MiB of UTF-8.
Text-input labels are non-empty and unique within their component instance
scope because they also preserve native editor identity across controlled
rerenders. Distinct keyed instances can reuse the same local input label.
`Gui.styled_text({ value, fg, font_size, font_weight, font_face })`::
Display a string in its own colour, size, weight, and face. Plain `Gui.text`
inherits all four from its container, so every typographic step otherwise costs a
one-child row or column that exists for no other reason; a wordmark, an eyebrow
label, and a status line are each a string, not a layout.
`Gui.scroll({ label, content, axis, ... })`:: Constrain content
to available space and scroll it vertically, horizontally, or in both directions.
The axis defaults to `Vertical`; `label` is the stable semantic identity. A
scroll region shares the native `Gui.Style` fields, so it carries its own size,
ground, inset, and corner rather than needing a column or panel wrapped around
it to supply them.
`Gui.virtual_list({ label, row_height, items })`:: Present
stable-keyed rows at one fixed logical height. Each item is an
`{ key, content }` record; keys must be unique within the list.
The complete item graph remains available to semantic inspection and event
routing, while GPUI materialises only the current viewport range.
A virtual list shares the native `Gui.Style` fields as well, and `row_gap` holds
that many logical pixels clear at the bottom of each row inside `row_height`, so
rows read as separate surfaces while the list's scrolling arithmetic stays
exactly one `row_height` per row. Without them a list has no ground, inset,
corner, or spacing of its own, and each row has to repaint the surface the list
is sitting on.
`Gui.virtual_rows({ label, row_height, count, render_row })`:: Present `count`
rows at one fixed logical height, building each with `render_row` only while it
is near the viewport, so the cost of a render follows the rows on screen rather
than `count`. It brings a row into view from state with `scroll_to` and reports
the rows on screen through `on_range`. It shares the style fields and `row_gap`
of `Gui.virtual_list`. See <<rows-produced-on-demand>>.
`Gui.row({ ... }, children)`:: Lay out children horizontally.
`Gui.col({ ... }, children)`:: Lay out children vertically.
`Gui.keyed_col(render_item, { ... }, { key, get, set, on_delegate })`::
Lay out a `Gui.KeyedSeq` vertically while preserving each item's component lifetime
by its complete `Gui.Key`. Inserts, moves, removals, and replacements are applied as
one mounted-graph transaction and one native keyed transaction. Construct a
sequence with `Gui.KeyedSeq.empty` and update it with `insert_before`, `remove`,
`move_before`, `set`, or one atomic `apply_all`; `Before(anchor)` and `End`
describe placement. Duplicate inserted keys, missing targets, and missing
anchors reject the operation without publishing a partial revision.
`on_delegate : parent, Gui.Key -> Gui.Action(parent)`
receives the complete key of the delegating item. Item actions project through
their key, so a move
does not retarget an action and a removed item cannot be recreated by a late
completion. If the platform has missed the sequence's one-generation journal,
it reconciles the full ordered snapshot while retaining every surviving key.
An exact journal renders only inserted and set items; a move preserves the
existing item component and a removal retires it, its routes, and its pending
task delivery. The full snapshot is materialised only for stale recovery.
`Gui.panel({ ... }, children)`:: Group children vertically in
a labelled surface that is padded, bordered, and rounded by default. `heading`
is the panel's own visible heading, painted above its children in
`heading_size`, `heading_weight`, and `heading_color`; each zero or `Default`
keeps the panel's own type. It is distinct from `label`, which remains the
semantic locator and is never painted, so a panel named for what a
specification calls it can still say something else to a reader. An empty
heading, the default, paints none.
`Gui.popover({ label, ... }, anchor, content)`:: Annotate `anchor`, any
element, with a non-modal surface presenting `content` beside it. The surface
opens `delay_ms` (default 500, at most 60000) after the pointer comes to rest
on the anchor, and at once when keyboard focus enters the anchor. It closes
when both the pointer and focus have left, and Escape that no dialog takes
closes every presenting popover until the pointer or focus enters it again.
`placement` is `Below` (the default), `Above`, `Start`, or `End`; a surface the
window has no room for moves to the opposite side and stays inside the
window. The surface floats above the rest of the window, outside any scroll
region's clipping, and blocks nothing: its content is read, not operated.
`label` names the surface as a `tooltip` for specifications and assistive
technology; a closed surface is not presented, so nothing in it can be found.
The style fields dress the surface, and a modifier applied to a popover applies
to its anchor. `on_hover_enter` and `on_hover_exit` are optional handlers for
the anchor's pointer edges. The host owns when a surface presents, so opening
and closing one runs no application code.
`Gui.tooltip(anchor, text)`:: Annotate an element with a popover presenting
one line of text, named by that text.

[source,roc]
----
Gui.popover(
    { label: "title in result row 0", delay_ms: 400 },
    cell,
    [Gui.text("title · TEXT"), Gui.text(value)],
)
----

`Gui.dialog({ label, on_dismiss, ... }, children)`:: Present
one modal surface above an input-blocking scrim. The first enabled control gains
focus, Tab and Shift+Tab stay within the dialog, Escape calls `on_dismiss`, and
closing the dialog restores its opener by stable semantic identity. Render at
most one dialog at a time.

Row, column, panel, dialog, popover, scroll, virtual-list, and button props share
the native
`Gui.Style` fields: gap, padding, width, height, growth, colours, borders,
radius, shadow, font size, font weight, per-axis overflow, and the two axis
placements.
`font_weight` is zero for the native default, or 100 through 900; 700 is bold.

A colour is written as a `0xRRGGBB` literal wherever a `Gui.Color` is expected,
as in `bg: 0x24404b`, and a value above `0xffffff` is rejected when the
application is compiled. A colour held in a name is annotated, `ink : Gui.Color`
then `ink = 0x1f1c17`, and one computed at run time is `Rgb(value)`. `Default`
keeps the control's native colour.

`padding` is the shorthand for all four sides. `padding_top`, `padding_right`,
`padding_bottom`, and `padding_left` each override one side with `Px(n)` and
default to `Same`, which takes the shorthand. A pill-shaped control wants
generous horizontal and tight vertical padding, which is the shorthand plus two
sides rather than a fixed height chosen to cancel the padding out.

`font_face` is `Default` for the host's proportional face or `Monospace` for the
platform's fixed-pitch one, which is what columnar output and changing digits
need. The host names the face each operating system ships rather than a generic
word only one font stack resolves.

`min_width`, `min_height`, `max_width`, and `max_height` are floors and
ceilings for the two sides, given as `Px(n)`. A fixed length is a basis a
sibling's overflow can shrink, so a row of uniform thumbnails beside captions of
different lengths needs a floor to keep one shape.

`text_overflow` decides what a string does when it is wider than the space it
was given. `Wrap` reflows onto further lines and grows the container, which is
the default. `NoWrap` keeps one line and leaves the rest to `overflow_x`.
`Ellipsis` keeps one line and ends it with a marker, so a shortened value never
looks like a complete one.

`disabled_bg`, `disabled_fg`, and `focus_color` replace the host's own
control-state colours. The host defaults suit its dark ground: a blue-grey
disabled fill at 55% opacity, and an amber focus ring. An application that names
its own disabled colours gets those at full opacity, because a chosen colour is
already the colour it wants to be.

`border_width` is likewise the shorthand, with `border_top`, `border_right`,
`border_bottom`, and `border_left` overriding one side each. A dense panel
divides its regions with a rule on the one edge that faces the next region,
rather than giving every region a complete box whose outer edges are also
drawn.

`shadow` is the blur radius of a soft drop shadow under the element, offset down
by `shadow_y` and painted in `shadow_color` at `shadow_alpha` percent of that
colour. `shadow: 0`, the default, paints none. A raised card on a near-white
ground separates from its paper by shadow where a hairline border has too little
contrast to read, and the colour is the application's own rather than a host
grey, so the shadow can be cast in the page's ink.

`justify` distributes children along the container's own layout axis and `align`
places them across it. `justify` is `Start`, `Center`, `End`, `Between`, or
`Around`; `align` is `Start`, `Center`, `End`, `Baseline`, or `Stretch`. Both
default to `Default`, which keeps the element's native placement. A grown child
with `justify: End` puts a trailing status field at the far edge without a
spacer element, and a grown empty-state column with `align: Center` and
`justify: Center` sits in the middle of the area it was given.
`Auto`, `Fill`, and `Px(n)` express dimensions. An optional non-empty `label`
provides a stable semantic locator, such as
`(role panel :name "Directory view")`; it does not add visible text.

Rows and columns accept a `List(Gui.Elem(State))`, which makes ordinary list
transformations useful for repeated UI:

[source,roc]
----
render_names : List(Str) -> Gui.Elem(State)
render_names = |names| Gui.col(
    { width: Fill, gap: 6 },
    names.map(|name| Gui.text(name)),
)
----

The empty `{}` retains neutral defaults. Semantic element names are not visible
labels. Give each simultaneously visible button a unique, stable name such as
`"Delete row ${row.id.to_str()}"`; specifications use that identity instead of
screen position.

Keyboard focus has a visible outline. Tab and Shift+Tab traverse enabled
buttons, checkboxes, and text inputs in rendered child order, so application
layout order is also the default keyboard order. Keep labels concise and
semantic names stable across state updates.

`Gui.run` also accepts a `window` record with an initial logical `width`,
`height`, and titlebar `title`. Defaults allow an `init`/`render`-only configuration;
windows remain resizable and layout elements using `Fill` follow the available
viewport.

`background` and `foreground` set the colour behind the root element and the
ink text inherits when it names none. The background reaches the whole window,
including its rounded corners and the edge above the root element, which a
grown root element cannot cover. Both default to the host's own ground, so an
application that says nothing keeps it.

=== Rows produced on demand

`Gui.virtual_list` receives every row as an item. GPUI draws only the rows in
view, but every row is still built, lowered, and mounted, so its cost follows the
list's length. `Gui.virtual_rows` receives a row count and a row function
instead:

[source,roc]
----
Gui.virtual_rows({
    label: "Query rows",
    row_height: 24,
    count: result.rows.len(),
    render_row: |index| result_row(result, index),
    scroll_to: state.rows_scroll,
    on_range: Some(|prev_state, visible| Gui.update({ ..prev_state, on_screen: Some(visible) })),
})
----

The host owns the viewport, so the host names the rows to build: those the
viewport shows and one viewport's worth either side of them. Only those rows are
rendered, lowered, and mounted. When scrolling brings the viewport within half a
viewport of the edge of the mounted rows, the platform renders the list again
for the new range. The list is its own render boundary: that render calls the
`render_row` of the owner's most recent render and lowers the list alone,
without rendering its owner. A row the viewport reaches before the list has
been rendered for it holds its place, blank, for the frames in between.

The boundary is transparent. An action raised by a row, or by `on_range`,
belongs to the list's owner exactly as if the rows had been built there, and a
task it starts is owned by that owner too. A row may contain translations,
buttons, editors, and nested lists like any other element.

`row_key : U64 -> U64`:: The stable identity of the row at an index; it
defaults to the index. Keys are unique among the rows mounted together. A key
drawn from the data keeps a row's native state — a pending press, focus, an
editor — with its data when rows are inserted above it.
`scroll_to : [None, Some(Gui.ScrollRequest)]`:: Bring a row into view from
state. A `Gui.ScrollRequest` is `{ row, align, serial }`, and `align` is a
`Gui.RowAlign`: `Start`, `Center`, `End`, or `Nearest`, which moves the list the
least distance and not at all when the row is already in view. The list moves
once for each distinct `serial`. Holding a request in state across later
renders leaves a person's own scrolling alone; jumping again, even to the same
row, or restoring a remembered position takes a new serial. The rows around the
requested one are built in the render that asks for them, so a jump lands on
built rows without building any row in between.
`on_range : [None, Some((a, Gui.EventVisibleRows => Gui.Action(a)))]`:: Receive
`{ start, end }`, the half-open range of rows the viewport intersects, whenever
it changes. This is the hook for paging: an application that holds only part of
its data reads the rest as the viewport approaches it. An action that changes
nothing still lets a pending rebuild of the list happen.

Visible rows are a fact about a presented frame, so `on_range` is delivered by
GPUI frames alone. Without a window, the semantic runner takes the viewport to
be as tall as the window the application asked for: a list mounts the rows such
a viewport shows and one viewport below them, and a scroll request moves that
viewport by the same arithmetic the window uses.

=== Modifiers

A property record is how an element is written. The code that builds an
element knows what it is, so it states the element's presentation in one place.
A caller that receives an element something else built, such as a themed
component or a translated child, adjusts it with modifier methods instead.

Every presentation field is also a method on an element: `width`, `grow`,
`padding`, `gap`, `bg`, `fg`, `radius`, `font_size`, `align`, `justify`, the
per-side `padding_top` and `border_bottom`, and so on for each shared style
field, together with `label`. Control-specific fields such as `enabled`,
`placeholder`, `read_only`, `axis`, `row_gap`, `fit`, `grayscale`, and `heading`
follow the same rule, as do the handlers `on_press`, `on_hover_enter`,
`on_hover_exit`, `on_check`, `on_change`, `on_submit`, `on_input`,
`on_dismiss`, and `on_pointer`. A modifier that does not apply to an element
leaves it unchanged. A typographic modifier on `Gui.text` styles that string,
and a modifier on a translated component applies to the root that component
renders.

In `examples/counter`, `Counter.render` owns how a card looks and the page
decides how much of the row each translated card takes:

[source,roc]
----
share : Gui.Elem(State) -> Gui.Elem(State)
share = |card| card.width(Fill).grow(True)

cards = Gui.row({ width: Fill, gap: 24 }, [
    share(Gui.translate(|counter| Counter.render("Left", counter), |parent| parent.left, |parent, counter| { ..parent, left: counter })),
    share(Gui.translate(|counter| Counter.render("Right", counter), |parent| parent.right, |parent, counter| { ..parent, right: counter })),
])
----

The component stays reusable at any width because it never chose one, and the
page states its division of space without reaching into the component.

== Translations and local state

Begin by splitting a large render function into ordinary helper functions.
Introduce a translation when a part of the UI should work with its own smaller
state and update independently. For example, each counter can own its counting
logic while the page holds two counter states.

`Gui.translate(render, get, set)` introduces a local rendering, delegation,
and task-ownership boundary. `get` reads the child's state from the parent;
`set` puts an updated child back while preserving the rest of the parent:

[source,roc]
----
render = |curr_state| Gui.col({}, [
    Gui.text(curr_state.title),
    Gui.translate(
        |counter| Counter.render("Left", counter),
        |parent| parent.left,
        |parent, counter| { ..parent, left: counter },
    ),
])

main = Gui.run({ init, render })
----

An unkeyed translation has a fresh lifetime whenever its parent reconstructs
it. Its own local updates preserve its lifetime and parent-owned application
data survives reconstruction unless an action changes it.

=== Preserve a component across parent renders

Use `Gui.translate_with(render, config)` when a component should keep its
lifetime across parent rebuilds or reordering. A stable key lets an in-flight
task still reach that same component after the parent renders:

[source,roc]
----
Gui.translate_with(
    |counter| Counter.render("Left", counter),
    {
        key: "left",
        get: |parent| parent.left,
        set: |parent, counter| { ..parent, left: counter },
    },
)
----

The required configuration fields are `key`, `get`, and `set`.
`on_delegate : parent -> Gui.Action(parent)` defaults to `Gui.update`.
`memo` defaults to `None`; `Some(|prev_state, curr_state| prev_state == curr_state)` opts into
comparison of child inputs.

`Gui.try_translate(render, config)` has the same configuration but its getter
returns `Try(child, [Removed])` and its setter returns `Try(parent, [Removed])`.
Use it for removable collection entries. Resolve a stable application identity
against the latest state; do not capture a render-time row index. Adapters do
not decode keys. A successful setter preserves the logical identity and
presence of its projection and unrelated parent data. A missing projection
cannot recreate deleted state. If a setter returns `Err(Removed)`, the whole
candidate is discarded before invoking delegation handlers or launching tasks.
Emitting a boundary whose getter returns
`Err(Removed)` is an application error; omit it from the element tree instead.

=== Keys identify instances within a scope

Use a string literal for a fixed component, `Gui.Key.from_str` for a computed name,
or `Gui.Key.id(U64)` for a numeric application identifier. The string `"7"` and
`Gui.Key.id(7)` are distinct keys. Compute dynamic keys when creating model entries
and reuse them during rendering.

Keys must be unique within their owner and native-container scope. A container's
kind and semantic label help define that scope. Reordering within that scope
preserves the lifetime; changing key or scope, removing and remounting, or
remounting the owner creates a new lifetime. Instance IDs are never recycled
within a session. The architecture chapter describes the identity protocol.

A key promises the same logical component and stable state projection for its
lifetime. Rebinding either requires a different key. The platform does not
compare functions to infer identity. Keep container kinds and semantic names
stable when native interaction state should survive. A translation adds no
padding or layout surface.

=== Persistent application collections

Keep a small collection in a list unless measurements give you a reason to
change it. For a large collection with frequent single-entry updates, retaining
an old state can force the list to be copied. An index limits how much shared
storage each update needs to copy; it does not eliminate copying.

`Index(value)` is a persistent map keyed by application `U64` identifiers.
`Gui.Index.empty`, `Gui.Index.get(index, id)`, `Gui.Index.set(index, id, value)`, and
`Gui.Index.remove(index, id)` provide lookup, insertion/replacement, and removal.
Lookup returns `Try(value, [Missing])`. Updating an index preserves older
snapshots and copies at most sixteen radix branches, rather than an entire
collection. Numeric storage identifiers are separate from mounted-instance IDs
and from the full-digest `Gui.Key` used by translations.

Store dynamic keys alongside their model entries. A removable collection can
keep its display order separately, project entries through `Gui.Index.get`, and
translate `Missing` into `Removed`. This lets a local action replace one entry
without copying an unrelated flat list. The row-boundaries application uses
the same persistent index as the platform's production route registry.

=== Local updates and delegation

Sometimes a child change also affects its parent: a counter may contribute to
a page total, or a review decision may need approval from the queue. Choose
delegation when the parent must participate in the change.

`Gui.update(next_child)` commits through the adapters and renders only its
originating boundary. Parent and sibling renderers and comparators are not
visited. A parent summary responds through explicit delegation or composition
inside the same render boundary; reading child state does not establish a
tracked dependency.

`element.lift(get, set)` adapts a prebuilt element without adding a render
boundary, lifetime, or memoization. It does not consume delegation. Its
non-fallible adapters must remain valid for the existing owner's lifetime.

`Gui.delegate(next_child)` constructs a candidate parent through the nearest
translation, then calls `on_delegate(candidate)`. That handler may:

* return `Gui.update(candidate)` to accept;
* return an update with revised parent data;
* return `Gui.none` to veto the entire candidate;
* return `Gui.task` to start parent-owned work; or
* return `Gui.delegate` to continue to the next parent policy.

Delegation reaching the root becomes a root update. Handlers receive current
state. Veto commits none of the candidate, including its child changes.

=== Memoization is opt-in

Add memoization when a parent frequently rebuilds an expensive child whose input
has not changed. A key alone preserves lifetime; memoization additionally lets
the platform reuse the child's rendered UI. Start without it so there is no
comparison policy to maintain or extra state snapshot to retain.

Ordinary translations require no equality and retain no comparison snapshot.
A keyed translation enables memoization with `memo: Some(compare)`. Comparison
runs only for boundaries reached by rendering and with a valid saved snapshot.
A hit retains the subtree and captured handlers; it does not suppress accepted
state transitions or task launches. Local updates never scan siblings.

The compared input must cover all variable rendering and captured-handler
dependencies, including labels, increment amounts, and layout properties.
Renderer captures and comparators must remain semantically stable for a keyed
lifetime. Returning `True` promises that keeping the old subtree and handlers
is equivalent to rebuilding them. Equality is suitable only when it satisfies
that promise: custom equality can omit fields, and floating-point equality can
equate signed zero even if rendering distinguishes it.

Descendant updates invalidate strict-ancestor snapshots without rendering those
ancestors. This prevents stale `A -> B -> A` reuse. Enabling or disabling memo
preserves instance identity and task ownership but rebuilds the boundary and
resets its cache. Saved inputs can inhibit Roc's in-place updates; measure the
production scaling cases before choosing a comparison policy.

=== Tasks follow the accepting boundary

Tasks launch only after their pending-state graph transaction is accepted.
Resolvers receive the latest state. Matching keyed rebuilds and reordering
preserve task ownership. Parent-owned tasks survive removal of their source
child. If the owner or its projected state has disappeared, completion delivery
is discarded. Reusing a removed key cannot revive old tasks.

Discarding a completion releases its result and captures through ordinary
reference counting; it does not promise cancellation of the underlying
operation. Use capability-specific cancellation for blocked work and application
request IDs to reject superseded results within a surviving instance.
Route revisions likewise prevent stale events from reaching replacement
handlers.

See `examples/counter` for plain translations, `examples/review-queue` for
explicit parent policy and removable state, and `examples/terminal-workspace`
for keyed resource-bearing panes.

== Directory capabilities and tasks

`access.pick_directory!()` requests a trusted host-owned Open Project
selection.
The selected project grants read authority, while cancellation is a normal
`Canceled` result and denial is `PickDirectoryErr(AccessDenied)`. The returned
`Gui.FilesDirRead` is an opaque, reference-counted handle: it may be stored in
state or captured by tasks, but applications cannot forge it or recover an
ambient path. Internally it uses the platform-wide typed `Resource.Handle`
representation, leaving the same ABI shape available to future resource APIs.

Open Project is presented by the operating system, never by application code.
On Linux Wayland the host asks the XDG Desktop Portal with directory,
single-selection, read-only and modal options and accepts one portal-returned
`file://` directory. On macOS the host asks the running window for the native
directory panel, and the window owning that panel is the only thread that shows
it. Either way the host opens the selected directory once at the trusted broker
boundary and places only the resulting capability in the registry.

An absent chooser is `PickDirectoryErr(Unavailable)`: a missing portal or D-Bus
on Linux, and on macOS a request made before the window exists or from the
window's own thread, which is the thread that would have to show the panel. One
chooser may be active at a time, and cancellation or refusal starts a short
host-owned cooldown that prevents application-driven prompt loops. An already
provisioned development grant never prompts and is not affected by that
cooldown.

Every root grant records whether its source was trusted chooser selection or
development provisioning and has session lifetime. Derived child handles carry
their immediate parent and inherited source. This metadata is host-private; no
path or grant identity enters captures. `--host-cap-dir` remains development
and automation provisioning and never represents consent.

`directory.list!()` lists at most 10,000 direct children and 4 MiB of
UTF-8 names. Entries distinguish files, directories, symlinks, and other file
types. `directory.open_dir!(name)` acquires a direct child
directory without following the final symlink; names containing traversal or
multiple path components are rejected. `directory.read!(name)` reads
one direct ordinary file as a bounded `List(U8)` without following links. The
64 MiB bound returns `ResourceLimit` instead of constructing an unbounded
application value. Run filesystem operations inside `Gui.task`, as
`examples/folder-browser/main.roc` shows.

== Single-file capabilities

`access.pick_file!(types)` asks the person for one file in the same trusted
surface Open Project uses, and grants read authority for exactly that file.
Each `Gui.FilesFileType` is a `label`, a list of `extensions` written without
a leading dot, and a list of `mime_types`; an empty list offers every file. On
Linux Wayland the XDG Desktop Portal is asked for one file with one filter per
type. On macOS the window's native panel is asked for one file. Whatever
presented the choice, the host then checks the chosen name against every
offered extension and answers `PickFileErr(Unsupported)` for any other file, so
the filter is a guarantee rather than advice. A type offered only by MIME type
is left to the chooser, because the host does not sniff content. An extension
that is a pattern rather than a name, or a type that offers nothing, is
`PickFileErr(InvalidName)`.

Cancellation is `Ok(Canceled)`, and the chooser follows the same one-at-a-time
rule and refusal cooldown as Open Project. A chosen file is
`Chosen({ name, file })`, where `file` is an opaque, reference-counted
`Gui.FilesFileRead`. It names the file and not its folder, so it reveals no
sibling and takes no name from the application. `file.read!()` reads the whole
file under the same 64 MiB bound and without following a link, and
`Gui.Sqlite.open_file_read!(file)` opens it in place as a read-only database.

The grant is recorded as a `document` root with `read` and `derive`, with its
origin and session lifetime, and a database opened from it is derived from it.
Withdrawing the file withdraws the database, even after the application has
released the file handle and kept only the connection. `--host-cap-file PATH`
provisions the file the chooser answers with, and `--host-cap-file-canceled`
answers it with a cancellation; both are development and automation
provisioning and never represent consent.

Filesystem failures use the `Gui.FilesFileErr` tag union. Its
`ListDirectoryErr`, `OpenReadDirectoryErr`, `PickDirectoryErr`, `PickFileErr`, and
`ReadFileErr` tags identify the failed operation directly; each carries a
portable `Gui.FilesReason` value.

`Revoked` is distinct from an invalid handle. Each directory operation resolves
the opaque handle and its immutable root lineage while holding the broker
registry mutex. That check is the revocation linearization point. Revocation
that wins the mutex causes that root and every derived child to reject future
list, child-open, and read operations as `Revoked`. An operation that already
won the check owns an `Arc<Dir>` and completes under its ordinary bounds;
revocation does not close that accepted resource. Task submission alone is not
acceptance, so queued work that has not reached the check is rejected.

The trusted host access snapshot exposes only counts grouped by source,
session lifetime, read rights, and active or revoked state. Root identifiers,
names, paths, and URIs remain internal and never enter capture evidence.

Retain a root-to-current list of directory handles to implement Back and
clickable breadcrumbs without exposing paths. Relist a retained handle before
committing navigation, and attach a monotonically increasing request identity
to asynchronous work so a superseded completion cannot replace a newer view.

== Encoded image data

`Gui.ImageData.inspect!(bytes, format)` validates bounded encoded bytes already
obtained through application data or an explicit capability and reports pixel
dimensions. It accepts neither paths nor URLs. Raster inspection uses the
maintained `image` decoder and SVG inspection uses `usvg`; inputs above 64 MiB,
dimensions above 32,768, and images above 200 million pixels are rejected.

Failures carry the operation tag `InspectImageErr` and one of `Corrupt`,
`InvalidDimensions`, `ResourceLimit`, or `Unsupported`. Image presentation
continues to use the byte-based `Gui.image` properties. `Gui.ImageData` owns metadata and
integrity inspection only; it does not duplicate layout or rendering props.

The native image-data owner counts staged image nodes, staged encoded bytes,
inspections, and inspection failures. Semantic specifications compare those
numeric counters with `expect-image-owner-counters`; captures never store
encoded content, image names, paths, dimensions, or application text.

== Shipped application assets

An application's own artwork is not user data and not durable state. It is the
application's own read-only content, so it is provisioned automatically and
prompts nobody, and it belongs to a surface of its own.

Small artwork needs no surface at all. A compile-time file import places the
bytes in the executable and `Gui.image` renders them:

[source,roc]
----
import "icons/folder.png" as folder : List(U8)

icon = Gui.image({ label: "Folder", bytes: folder, format: Png })
----

`Assets` is for the larger asset -- a background banner, a photograph -- that
should not be paid for in executable size. An application opens a store once
and reads a file when it wants it; the bytes flow into that same `Gui.image`.

A store is anchored to a named root, not to an ambient path. Three roots exist
because moving an executable, changing the working directory, and installing
content apart from the program are three separate events, and none may silently
change what another means:

`Gui.Assets.beside_executable(path)`:: A directory beneath the executable's own
directory. The artwork travels with the program, so the store resolves the same
way however the program was launched.
`Gui.Assets.working_directory(path)`:: A directory beneath the process working
directory. The root follows the shell, which is what running from a project
checkout wants.
`Gui.Assets.content_directory`:: The content directory the host provisioned for
this application. The application names no path here, so an asset store is
never a route to a directory the host did not hand it.

`access.assets!(config)` returns an opaque `Gui.AssetsStore`; `store.read!(path)`
returns the bytes of one asset beneath it. Both touch the disk, so both belong
inside `Gui.task`, which runs them on the bounded worker pool and resolves on
the UI thread:

[source,roc]
----
Gui.task({
    pending: { ..state, banner: Loading },
    run: || {
        store = state.access.assets!(Gui.Assets.beside_executable("assets"))?
        store.read!("banners/hero.png")
    },
    resolve: |latest, result| match result {
        Ok(bytes) => Gui.update({ ..latest, banner: Loaded(bytes) })
        Err(_) => Gui.update({ ..latest, banner: Failed })
    },
})
----

`Gui.Assets.stub` is the resource-free store value. An application that keeps a
store in its state needs one to write that state down in a pure `expect`; reads
through it fail, and it proves nothing about asset resolution.

=== Validating an asset set at startup

An asset set may declare a `roc-assets.manifest` file at its root: an
`asset_set` name, a `schema` version, a `content_version`, and an optional
`sha256` digest, one `key = value` per line with `#` comments.

....
# The gallery's shipped artwork
asset_set = gallery
schema = 1
content_version = 7
sha256 = 3b1f...c90a
....

`Gui.Assets.with_manifest(config, expectation)` makes the open check that file, so
a half-updated or mismatched asset set is reported at startup rather than
surfacing much later as one image that will not draw. The four comparisons are
reported separately: `AssetSetMismatch`, `SchemaMismatch`,
`ContentVersionMismatch`, and `ContentHashMismatch`. A manifest that is absent,
unreadable, or not a manifest is `ManifestMissing`, `ManifestUnreadable`, or
`ManifestMalformed`; an expectation the host cannot use, such as a digest that
is not 64 hexadecimal characters, is `InvalidExpectation` and is answered before
any file is touched.

The comparison is against the manifest's own declarations. Nothing walks or
hashes the files beneath the root, so an open costs the same for one asset as
for ten thousand.

=== What a store refuses

A store root is a directory handle, never an ambient filesystem capability. The
host resolves every root and every asset path through the one resolver that
serves granted directories. An absolute path, an empty path, a path holding a
NUL, and any `.` or `..` component are refused rather than rewritten, and each
step of a walk refuses to follow a symbolic link, so nothing inside a store can
name anything outside it. A final entry that is a symbolic link or is not a
regular file is `Unsupported`. One asset reads into one value up to 64 MiB;
beyond that the read is `ResourceLimit`. The host never calls `chdir`.

The native asset owner counts opens, refused opens, manifest checks, reads,
refused reads, and bytes read. Semantic specifications compare those six numbers
with `expect-asset-counters`. No path, file name, or asset content ever becomes
evidence.

== Process and pseudo-terminal capabilities

`access.process!()` returns an opaque process grant only when the application is
launched with `--host-cap-process=local-shell` or
`--host-cap-process=test-program`. The grant fixes the only profile that may be
started. `grant.spawn!` accepts only terminal dimensions;
applications never provide a profile, executable path, arguments, environment
variables, or command lines to the host.

`Grant.spawn!` creates a real pseudo-terminal with an explicitly bounded row
and column size. `read!`, `write!`, `resize!`, and
`cancel!` are methods on its typed `Gui.ProcessPty` handle. Reads and writes are
capped at 65,536 bytes per call, one read may wait on a PTY, and cancellation
wakes that wait. Blocking operations belong in `Gui.task`, whose completion
is reconciled with the latest state on the ordinary event route.

Failures carry their operation in the tag, such as
`SpawnProcessErr(AccessDenied)` or `ReadProcessErr(Busy)`. Process grants and
PTYs are opaque `Box(U64)` resources and cannot be confused with other handle
kinds.

== HID device capabilities

`access.device!()` returns an opaque grant only when the host has authorised one
exact virtual device or physical USB vendor/product identity. Applications
cannot request arbitrary hardware, inspect operating-system device paths, or
read serial numbers. `grant.discover!()` lists only comparison-safe identity
within that grant, and `grant.connect!()` connects exactly the granted device.

Connections are typed `Box(U64)` resources. `connection.transact!` exchanges one
bounded byte request and response; device-specific framing and values belong in
an application or protocol package rather than the platform. Physical HID and
deterministic virtual transports enter this same operation. Blocking discovery,
connection, and transactions run through `Gui.task`.

Failures retain their operation in tags such as
`DiscoverDeviceErr(NotFound)` and `TransactDeviceErr(Protocol)`. Connection and
transaction lifecycle counts are recorded by the host that owns those events.

== System observation capabilities

`access.system_monitor!()` returns an opaque typed sampler only when the host has
granted read-only system observation. `sampler.sample!()` refreshes CPU,
memory, aggregate process disk I/O, network I/O, and a bounded process list on a
task worker. `sampler.close!()` is idempotent. Applications cannot request
another machine or broaden the grant.

Every snapshot field is a tagged `Value` or `Unavailable(Unsupported)` value.
Permission denial is an `AcquireSystemErr(AccessDenied)` operation failure, not
a fabricated unavailable sensor. Overall CPU is normalised across the machine
and uses tenths of one percent in `0..1000`. Per-process CPU uses the same unit
and can exceed `1000` for multi-core use. Memory and I/O counters are bytes as
reported by `sysinfo`; the platform does not infer unavailable measurements.

Processes are bounded and sorted by CPU, memory, then PID. Only PID, display
name, CPU, and memory cross the ABI; user, executable path, arguments,
environment, hostname, and machine identity do not.

== Durable application data

`access.app_data!()` acquires the application's private read-write directory
granted by `--host-cap-app-data PATH`. The result is an opaque typed
`Gui.FilesDirReadWrite` handle; applications cannot recover the host path.

`directory.read_utf8!(name)` distinguishes `Missing` from
`Value(Str)`. `directory.write_utf8_atomic!(name, value)`
synchronises a private temporary file before replacing the direct child in the
same directory. Names are flat ASCII identifiers of at most 128 bytes, values
are UTF-8 of at most one MiB, and the ordinary operation-tagged `Gui.FilesFileErr`
surface reports acquisition, read, and write failures.

Run these blocking operations inside `Gui.task`, with a monotonic request
identity when an edit can supersede pending work. The Settings Center uses this
route and retains a newer draft when an older load completes.

== Audio output capabilities

`access.audio!()` acquires an opaque output handle for ordinary mixer
output.
Playing sound through the shared system mixer is an automatically provisioned
service with no prompt, and the handle lasts for the session; exclusive access
or unusual routing would be separate scope. Acquisition fails when the machine
has no usable output device. `Gui.Audio.load!(output, directory, name)` loads
one direct file through an existing `Gui.FilesDirRead` grant; names with traversal
or multiple components are rejected and encoded input is bounded to 64 MiB.
The host delegates media decoding and playback to Rodio and Symphonia.

`Gui.AudioTrack` is an opaque host resource. `Gui.Audio.play!`, `Gui.Audio.pause!`,
`Gui.Audio.seek!`, `Gui.Audio.status!`, and `Gui.Audio.stop!` are bounded operations intended
for `Gui.task`. Status reports the decoder-owned duration, playback position,
and `Playing`, `Paused`, or `Stopped` state. `Gui.AudioAudioErr` identifies
the failed operation and carries a portable reason such as `DecodeFailed`,
`OutputUnavailable`, or `InvalidCapability`.

Specification runs may receive a harness-owned null-output grant. It drains
the same paced Rodio mixer, decoder, and player state used by a system output;
it changes only the final device sink.

== Clipboard capabilities

`access.clipboard!()` acquires text clipboard authority only when the host
was launched with `--host-cap-clipboard`. Its opaque `Gui.ClipboardHandle` uses
the common typed `Box(U64)` representation and cannot be manufactured or
confused with another resource family.

`handle.read_text!()` returns a bounded UTF-8 snapshot with a
monotonic sequence. Applications compare sequences to suppress stale reads and
deduplicate repeated content. `handle.write_text!(text)` schedules
replacement on GPUI's owning UI context. Both directions reject values larger
than 64 KiB. `Gui.ClipboardClipboardErr` identifies acquisition, reading, and
writing with distinct operation tags carrying a portable reason.

Observe changes with one pull-based `Gui.Timer` subscription inside `Gui.task`.
Pause by cancelling that timer; sensitive values are discarded before they
enter state. Clipboard content is application data and never enters host
diagnostics or observatory captures.

== HTTP requests

Applications declare `roc-lang/http` v1.0.0 and build its canonical `Request`
values. `access.http!()` returns an opaque `Gui.HttpClient` only when the host
was launched with `--host-cap-http-origin ORIGIN`. The grant names one exact
scheme, host, and effective port; requests and redirects cannot leave it.
Acquire failures are `AcquireHttpErr(reason)` and exchange failures are
`SendHttpErr(reason)`, retaining the operation together with the portable
reason. Provisioning grants authority for development and automation; they are
not a substitute for an application's user-visible trusted-destination setup.

The host disables ambient proxy discovery, rejects credentials embedded in
URLs, and pins an accepted non-literal destination resolution for the exchange.
Literal loopback or private addresses remain usable only when named explicitly
by the provisioned origin.

`client.send!(config, request)` performs one bounded exchange and returns
the package's canonical `Response`. Call it from `Gui.task` so connection,
TLS, and response work runs on the native worker pool and its reducer returns
through the ordinary UI-thread completion dispatcher.

Requests and config make policy explicit: method, URI, headers, body, timeout,
`max_response_bytes`, and `max_redirects`. `Gui.HttpConfig` carries a default for
each limit -- a 30 second timeout, a 1 MiB response, and three redirects -- so
`{ timeout_ms: 2_000 }` states only the limit it moves. URLs must
use `http` or `https`.
The platform accepts standard methods, at most 64 headers and 32 KiB of header
data, a request body up to 1 MiB, a timeout from 1 through 60,000 milliseconds,
a response limit from 1 byte through 4 MiB, and from zero through ten redirects.
Response bodies remain `List(U8)` so downstream packages share the same nominal
types. Portable failures distinguish invalid inputs, denied or invalid
capabilities, unsupported schemes, connection and timeout failures, and
redirect and body limits.

Give each submitted request a monotonically increasing identity. In the task
resolver, compare that identity with the latest state and return `Gui.none`
for an obsolete result. This prevents a slow earlier response from replacing a
newer response without creating a second completion route.

== Read-only SQLite capabilities

`Gui.Sqlite.open_read!(directory, name)` opens one direct ordinary child of a
granted directory as a read-only database capability. The operation rejects
path traversal and symlinks and never exposes an ambient path. The database is
read in place, so its size is not bounded by memory, and the file SQLite opens
is checked to be the one the directory grant names. The returned
`Gui.SqliteDb` is an opaque, reference-counted `Box(U64)` handle whose final
release closes the native connection. The connection is derived from the
directory grant, so withdrawing the folder withdraws the database with it.
`Gui.Sqlite.open_file_read!(file)` opens a granted file the same way, derived
from the file grant.

The connection is read-only and cannot attach another database. It is not
opened as immutable: a database in write-ahead-log mode is read through its log,
so every query sees the writes another process has committed, including a
writer that is still running. SQLite keeps a write-ahead-logged database's
shared index files beside it; the database file itself is never written.

`database.query!(sql)` prepares and executes one read-only statement.
`database.query_with!(sql, params)` binds a `List(Gui.SqliteValue)` to the
statement's `?` placeholders in order. Values are bound, never spliced into the
statement text, and the number of values must match the placeholders.
Results preserve SQLite's `Null`, `Integer`, `Real`, `String`, and `Bytes`
value kinds. Queries are bounded to 64 KiB of SQL, 256 columns, 256
parameters, 10,000 rows, and 16 MiB of returned text and blob bytes; the same
16 MiB bounds the bytes of the parameters. Limit violations and invalid,
corrupt, busy, inaccessible, or non-database resources are typed errors.
Failures use `OpenDatabaseErr(reason)` and `QueryDatabaseErr(reason)`, so callers
can distinguish the failed operation before matching the portable reason.
Every reason retains SQLite's bounded diagnostic string; `Gui.Sqlite.detail`
extracts it for user-facing status without flattening the public error type.

A result longer than the row limit is read in pages.
`database.page!({ sql, params, rows })` returns a `Gui.SqlitePage` holding at
most `rows` rows, from one to the row limit, and `more`, which is `True`
when the result continues past the page. The next page is a further call whose
parameters carry the position: a keyset such as `WHERE id > ? ORDER BY id`
bound to the last key seen, or `LIMIT -1 OFFSET ?` bound to the rows already
read. A keyset page costs the same at any depth; an offset page costs more the
deeper it lies. Each page is one statement, so no read transaction is held
between pages and a writer is never blocked by a reader turning pages.

[source,roc]
----
next = database.page!({
    sql: "SELECT id, title FROM books WHERE id > ? ORDER BY id",
    params: [Integer(last_id)],
    rows: 1000,
})
----

Open and query calls are blocking capability operations. Run them inside
`Gui.task`, retain the last successful view while work is pending, and use a
monotonic request identity in the resolver so an older completion cannot
replace a newer result. `examples/database-browser` demonstrates this pattern.

== TCP endpoint capabilities

`access.tcp_connect!()` opens an ordered byte stream to the single numeric
`IP:PORT` endpoint granted with `--host-cap-tcp`. Without that host grant it
returns `ConnectTcpErr(AccessDenied)`. The application cannot select or derive a
different destination from the opaque handle, and releasing its final
reference closes the socket and removes the host registry entry.

`stream.read_up_to!(max_bytes)` reads between one byte and a
one-MiB requested maximum; an empty list means orderly end of stream.
`stream.write_all!(bytes)` writes the complete value or fails and
accepts at most 16 MiB. `stream.close!()` is idempotent. Connections,
reads, and writes have finite native timeouts, and failures use the
operation-tagged `Gui.TcpTcpErr` union: `ConnectTcpErr`, `ReadTcpErr`,
`WriteTcpErr`, or `CloseTcpErr` wraps a portable reason.

The numeric endpoint has no DNS resolution or ambient destination selection.
The command-line grant provisions development and automation authority; a
user-facing client obtains trusted connection authority through a named,
revocable destination broker rather than treating that flag as user consent.

TCP operations block and belong inside `Gui.task`. Protocol packages build
on the byte transport rather than being reimplemented by the platform. The
Redis Explorer adapts a stream with `roc-redis`'s `Transport.from_bytes_io`, so
command encoding, bounded RESP2 decoding, typed commands, and exchange policy
remain the responsibility of the established platform-independent package.

== Retained canvas

`Gui.canvas` paints an ordered list of keyed primitives in native GPUI, built
with `Gui.rectangle({ ... })`, `Gui.ellipse({ ... })`, `Gui.line({ ... })`, and
`Gui.canvas_text({ ... })`. A canvas and every primitive have stable
semantic labels. Primitive keys are non-zero and unique within the canvas;
they preserve direct-manipulation identity independently of list position.

The controlled `on_pointer` handler receives `Begin`, `Move`, and `End` in
integer canvas coordinates. The topmost hit-tested primitive is captured on
`Begin`, and that same optional target key accompanies the complete gesture,
including when a state update replaces the canvas subtree.

A text primitive sets one line of `value` in the canvas's inherited font, at
`size` logical pixels and in `color`, within the box from `x` to `x + width`
with its top at `y`. `align` places it at the box's `Start`, `Center`, or
`End`. Its semantic rectangle is that box, one line tall: `size` and a quarter
again. Text labels the shapes beneath it and is never a pointer target, so a
caption drawn over a bar leaves the bar as the target.

`on_hover` receives pointer movement with no button pressed. `Move` carries the
point and the topmost keyed primitive under it, and is delivered once for each
new point; `Leave` is delivered once when the pointer leaves the canvas, with
the last point delivered. A pressed pointer is always an `on_pointer` gesture,
so hovering never interrupts a drag. `on_wheel` receives wheel and trackpad
scrolling as `dx` and `dy` logical pixels, positive towards the content's end,
with the pointer's point and target; a wheel that reports lines is converted at
the window's line height. A canvas that handles the wheel consumes it, so an
enclosing scroll region does not also move. Both handlers are optional. A
canvas without one is not listened to for it, and moving the pointer across it
records nothing.

Each delivered hover records one `hover` cycle and each wheel scroll one
`wheel` cycle, through the same recorded dispatch as a `drag` phase, whether a
person or a specification moves the pointer.
