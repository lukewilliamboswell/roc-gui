= Building an application

Resource-bearing APIs consume opaque grants under the policy set out in the
resource access chapter. A path, URL, or application-rendered dialog is never a
substitute for trusted authorisation.

== State, render, and actions

An application exports a state type and `main : Program(State)`:

[source,roc]
----
import pf.Action
import pf.Elem
import pf.Program

State : { count : I64 }

render : State -> Elem(State)
render = |state| Elem.col({}, [
    Elem.text("Count: ${state.count.to_str()}"),
    Elem.button({
        caption: "Add one",
        label: "Increment count",
        on_press: |previous, _event|
            Action.update({ count: previous.count + 1.I64 }),
    }),
])

setup! : () => { state : State, render : State -> Elem(State) }
setup! = || { state: { count: 0 }, render }

main : Program(State)
main = Program.run({ setup: setup! })
----

`render` is pure: it reads state and returns an `Elem(State)`. A button handler
receives the state associated with its render boundary and an `Event.Press`.
It returns an action:

`Action.update(next_state)`:: Propose the next state and update the required
render scope, subject to the component's memoization policy.
`Action.none`:: Keep the existing state and element tree unchanged.
`Action.delegate(next_state)`:: Propose a child change to the nearest component's
parent policy. That policy returns the action to accept, revise, veto, or
delegate further.
`Action.task({ pending, run, resolve })`:: Commit `pending`, run `run` on the
bounded native worker pool, then invoke `resolve` against the latest state on
the UI thread if the task's owning component instance still exists.

Use `Action.none` when an event is valid but has no effect, such as pressing a
decrement button at a lower bound. It is both clearer and less work than
returning an unchanged state with `Action.update`.

An action is a value describing a transition, not a transition performed.
Constructing one changes nothing; returning it from a handler is what asks the
platform to apply it. Every transition is applied on one thread, one at a time,
so a handler's first argument is always the state that precedes it. This model
is Richard Feldman's, from his design document _Design Idea: Action-State_; the
architecture chapter records that origin and the reasoning behind it.

=== Setup runs before the first render

`Program.run({ setup, window })` describes the application. `setup` is an
effectful, zero-argument function returning `{ state, render }`; `window` is
optional. Setup runs once. Use a named, explicitly typed helper as above, and
create component definitions there before capturing their handles in the
returned renderer. Resource acquisition in setup must use the same granted
capabilities as task work. Window-dependent interactions belong in actions once
the window exists.

Define nested components from the leaves upward, passing existing definition
handles into their parents' immutable renderer closures. The definition graph
is acyclic; ordinary recursive functions may still build recursive element
trees. Definitions cannot be created inside render functions or event handlers.

== Timers and subscriptions

`Timer.start!({ interval_ms })` creates an opaque `Timer.Handle` for intervals
from 1 through 60,000 milliseconds. `handle.next!()` waits for one tick
and belongs inside `Action.task`; the next wait is started only after the
previous completion has been applied. This pull contract bounds backpressure
at one in-flight wait and does not accumulate missed ticks.

`handle.cancel!()` is idempotent, wakes an outstanding wait, and makes it
resolve as `Canceled`. Dropping the last typed `Box(U64)` handle also releases
the host registry entry. Applications retain the handle in state and decide
whether a `Fired` result schedules another wait.

== Elements and layout

`Elem.text(value)`:: Display a string, inheriting colour and size from its
container.
`Elem.action_button(Elem.ActionButtonProps.{ ... })`:: Display a controlled,
styled action button. `caption` is visible text, `label` is its stable semantic
name, and `enabled` defaults to `True`. Enabled buttons participate in keyboard
tab order and activate with Enter or Space. Disabled buttons remain visible
with a subdued appearance and accept neither pointer nor keyboard activation.
Props include padding, sizing, growth, foreground and interaction colours,
border, radius, font size, font weight, and overflow.
`Elem.button({ caption, label, on_press })`:: Concise text-button constructor
over the same native action-button node. `caption` is the visible text and
`label` is the stable semantic name, as in every other control; use
`Elem.action_button` for styling.
`Elem.checkbox(Elem.CheckboxProps.{ ... })`:: Display a semantic checkbox and
handle `Event.Check`. `box_bg`, `box_checked_bg`, `box_border`, and
`mark_color` colour the indicator itself, which `fg` does not reach; each
defaults to the host's own value. Props include enabled state, gap, padding, sizing, growth,
foreground and interaction colours, border, radius, font size, font weight,
and overflow.
Enabled checkboxes participate in keyboard tab order and toggle with Space;
disabled checkboxes do not accept focus or activation.
`Elem.textarea(Elem.TextareaProps.{ ... })`:: Display a controlled multiline
text editor and handle `Event.Input`, which carries the complete requested
value.
`label` is the stable semantic name; `placeholder`, `enabled`, and `read_only`
control editing behaviour. A read-only textarea retains multiline layout and
scrolling for response and log views. Textareas share the native style fields
and default to a 160-logical-pixel editing viewport.
`Elem.image(Elem.ImageProps.{ label, bytes, format, ... })`:: Decode and render
capability-safe in-memory image bytes through GPUI. The explicit format is one
of `Png`, `Jpeg`, `Webp`, `Gif`, `Svg`, `Bmp`, or `Tiff`; fit defaults to
`Contain` and also supports `Cover`, `Fill`, `ScaleDown`, and `None`.
`grayscale` applies a native rendering effect. The declared box is
authoritative: `width`, `height`, and the minimum and maximum fields size the
element, and `fit` is the rule that maps the decoded pixels into that box. Image
sources are values, never ambient filesystem paths or URLs, and `label` is the
stable semantic name.
`Elem.text_input(Elem.TextInputProps.{ ... })`:: Display a controlled,
single-line native editor. `label` is its stable semantic name, `value` is the
authoritative application value, and `placeholder` is shown only while empty.
Committed edits deliver the complete value in `Event.TextChange`; Enter delivers
`Event.TextSubmit`. The host retains focus, caret, selection, and an active IME
composition across controlled rerenders. Disabled fields accept neither edits
nor submission. Text values are bounded to one MiB of UTF-8.
Text-input labels are non-empty and unique within their component instance
scope because they also preserve native editor identity across controlled
rerenders. Distinct keyed instances can reuse the same local input label.
`Elem.styled_text(Elem.TextProps.{ value, fg, font_size, font_weight, font_face })`::
Display a string in its own colour, size, weight, and face. Plain `Elem.text`
inherits all four from its container, so every typographic step otherwise costs a
one-child row or column that exists for no other reason; a wordmark, an eyebrow
label, and a status line are each a string, not a layout.
`Elem.scroll(Elem.ScrollProps.{ label, content, axis, ... })`:: Constrain content
to available space and scroll it vertically, horizontally, or in both directions.
The axis defaults to `Vertical`; `label` is the stable semantic identity. A
scroll region shares the native `Gui.Style` fields, so it carries its own size,
ground, inset, and corner rather than needing a column or panel wrapped around
it to supply them.
`Elem.virtual_list(Elem.VirtualListProps.{ label, row_height, items })`:: Present
stable-keyed rows at one fixed logical height. Each item is an
`Elem.VirtualListItem.{ key, content }`; keys must be unique within the list.
The complete item graph remains available to semantic inspection and event
routing, while GPUI materialises only the current viewport range.
A virtual list shares the native `Gui.Style` fields as well, and `row_gap` holds
that many logical pixels clear at the bottom of each row inside `row_height`, so
rows read as separate surfaces while the list's scrolling arithmetic stays
exactly one `row_height` per row. Without them a list has no ground, inset,
corner, or spacing of its own, and each row has to repaint the surface the list
is sitting on.
`Elem.row(Elem.RowProps.{ ... }, children)`:: Lay out children horizontally.
`Elem.col(Elem.ColProps.{ ... }, children)`:: Lay out children vertically.
`Elem.panel(Elem.PanelProps.{ ... }, children)`:: Group children vertically in
a labelled surface that is padded, bordered, and rounded by default. `heading`
is the panel's own visible heading, painted above its children in
`heading_size`, `heading_weight`, and `heading_color`; each zero or `Default`
keeps the panel's own type. It is distinct from `label`, which remains the
semantic locator and is never painted, so a panel named for what a
specification calls it can still say something else to a reader. An empty
heading, the default, paints none.
`Elem.dialog(Elem.DialogProps.{ label, on_dismiss, ... }, children)`:: Present
one modal surface above an input-blocking scrim. The first enabled control gains
focus, Tab and Shift+Tab stay within the dialog, Escape calls `on_dismiss`, and
closing the dialog restores its opener by stable semantic identity. Render at
most one dialog at a time.

Row, column, panel, dialog, scroll, virtual-list, and action-button props share
the native
`Gui.Style` fields: gap, padding, width, height, growth, colours, borders,
radius, shadow, font size, font weight, per-axis overflow, and the two axis
placements.
`font_weight` is zero for the native default, or 100 through 900; 700 is bold.

`padding` is the shorthand for all four sides. `padding_top`, `padding_right`,
`padding_bottom`, and `padding_left` each override one side with `Px(n)` and
default to `Same`, which takes the shorthand. A pill-shaped control wants
generous horizontal and tight vertical padding, which is the shorthand plus two
sides rather than a fixed height chosen to cancel the padding out.

`font_face` is `Default` for the host's proportional face or `Monospace` for the
platform's fixed-pitch one, which is what columnar output and changing digits
need. The host names the face each operating system ships rather than a generic
word only one font stack resolves.

`min_width`, `min_height`, `max_width`, and `max_height` are floors and
ceilings for the two sides, given as `Px(n)`. A fixed length is a basis a
sibling's overflow can shrink, so a row of uniform thumbnails beside captions of
different lengths needs a floor to keep one shape.

`text_overflow` decides what a string does when it is wider than the space it
was given. `Wrap` reflows onto further lines and grows the container, which is
the default. `NoWrap` keeps one line and leaves the rest to `overflow_x`.
`Ellipsis` keeps one line and ends it with a marker, so a shortened value never
looks like a complete one.

`disabled_bg`, `disabled_fg`, and `focus_color` replace the host's own
control-state colours. The host defaults suit its dark ground: a blue-grey
disabled fill at 55% opacity, and an amber focus ring. An application that names
its own disabled colours gets those at full opacity, because a chosen colour is
already the colour it wants to be.

`border_width` is likewise the shorthand, with `border_top`, `border_right`,
`border_bottom`, and `border_left` overriding one side each. A dense panel
divides its regions with a rule on the one edge that faces the next region,
rather than giving every region a complete box whose outer edges are also
drawn.

`shadow` is the blur radius of a soft drop shadow under the element, offset down
by `shadow_y` and painted in `shadow_color` at `shadow_alpha` percent of that
colour. `shadow: 0`, the default, paints none. A raised card on a near-white
ground separates from its paper by shadow where a hairline border has too little
contrast to read, and the colour is the application's own rather than a host
grey, so the shadow can be cast in the page's ink.

`justify` distributes children along the container's own layout axis and `align`
places them across it. `justify` is `Start`, `Center`, `End`, `Between`, or
`Around`; `align` is `Start`, `Center`, `End`, `Baseline`, or `Stretch`. Both
default to `Default`, which keeps the element's native placement. A grown child
with `justify: End` puts a trailing status field at the far edge without a
spacer element, and a grown empty-state column with `align: Center` and
`justify: Center` sits in the middle of the area it was given.
`Auto`, `Fill`, and `Px(n)` express dimensions. An optional non-empty `label`
provides a stable semantic locator, such as
`(role panel :name "Directory view")`; it does not add visible text.

Rows and columns accept a `List(Elem(State))`, which makes ordinary list
transformations useful for repeated UI:

[source,roc]
----
render_names : List(Str) -> Elem(State)
render_names = |names| Elem.col(
    Elem.ColProps.{ width: Fill, gap: 6 },
    names.map(|name| Elem.text(name)),
)
----

The empty `{}` retains neutral defaults. Semantic element names are not visible
labels. Give each simultaneously visible button a unique, stable name such as
`"Delete row ${row.id.to_str()}"`; specifications use that identity instead of
screen position.

Keyboard focus has a visible outline. Tab and Shift+Tab traverse enabled
buttons, checkboxes, and text inputs in rendered child order, so application
layout order is also the default keyboard order. Keep labels concise and
semantic names stable across state updates.

`Program.run` also accepts a `window` record with an initial logical `width`,
`height`, and titlebar `title`. Defaults allow a setup-only configuration;
windows remain resizable and layout elements using `Fill` follow the available
viewport.

`background` and `foreground` set the colour behind the root element and the
ink text inherits when it names none. The background reaches the whole window,
including its rounded corners and the edge above the root element, which a
grown root element cannot cover. Both default to the host's own ground, so an
application that says nothing keeps it.

== Keyed components and local state

A component definition fixes how to read and replace child state, render it,
and handle delegation. `Component.define!` creates an equality-memoized definition
during setup. `Elem.component(definition, key)` mounts an instance while rendering:

[source,roc]
----
import pf.Component

State : { title : Str, counter : Counter.State }

counter_get : State, Elem.Key -> Try(Counter.State, [Removed])
counter_get = |parent, key| match Elem.Key.inspect(key) {
    Name("Main") => Ok(parent.counter)
    _ => Err(Removed)
}

counter_set : State, Elem.Key, Counter.State -> Try(State, [Removed])
counter_set = |parent, key, child| match Elem.Key.inspect(key) {
    Name("Main") => Ok({ ..parent, counter: child })
    _ => Err(Removed)
}

counter_render : Counter.State -> Elem(Counter.State)
counter_render = |child| Counter.render("Main", child)

render : Component(State), State -> Elem(State)
render = |counter, state| Elem.col({}, [
    Elem.text(state.title),
    Elem.component(counter, Name("Main")),
])

setup! : () => { state : State, render : State -> Elem(State) }
setup! = || {
    counter : Component(State)
    counter = Component.define!({
        get: counter_get,
        set: counter_set,
        render: counter_render,
    })
    {
        state: { title: "Counter", counter: Counter.init(0) },
        render: |state| render(counter, state),
    }
}

main : Program(State)
main = Program.run({ setup: setup! })
----

`Component.Config(parent, child)` contains:

`get : parent, Elem.Key -> Try(child, [Removed])`:: Select current child input
by stable key. Return `Err(Removed)` when that instance's state is absent.
`set : parent, Elem.Key, child -> Try(parent, [Removed])`:: Replace that child in
the latest parent. Return `Err(Removed)` instead of inserting a missing child.
`render : child -> Elem(child)`:: Render the complete child input, with handlers
typed to that input.
`update_scope : [Local, Parent]`:: Declare the minimum render scope. Defaults to
`Local`.
`on_delegate : parent, Elem.Key -> Action(parent)`:: Decide what to do with a
candidate parent after `Action.delegate`. Defaults to accepting it with
`Action.update`.

The definition's renderer, adapters, and policies are immutable. All changing
inputs must come through `get`, including properties borrowed from parent state
that rendering or captured handlers use. For a collection, resolve the stable
key against the latest collection; do not capture a render-time row index.
The getter and setter succeed for a live projection. A successful setter
preserves that instance's key and presence, changes only its writable child
state, and preserves unrelated parent fields; it cannot resurrect an absent
row. Removing or moving ownership belongs to the parent action, not to a child
setter that silently changes its own identity. Rendering a component for which
`get` returns `Removed` is a contract
error: omit that instance from the element tree instead.

=== Keys identify instances within a scope

`Elem.Key` is `Name(Str)` or `Id(U64)`: `Name("7")` and `Id(7)` are distinct.
Keys are unique among components in the same structural parent scope, even
when the definitions differ. Reordering keyed siblings within that scope keeps
their instance lifetimes. A different definition at the same key, changing the
structural ancestor path, or removing and later recreating a key mounts a new
instance.

A key is not a global native-widget identity. Keep surrounding container kinds
and semantic names stable when interaction state should survive. Components
add no padding or layout surface, and directly nested components have separate
lifetime markers even when their visible content has one native root.

=== Render ownership is explicit

In the example, the title does not depend on the count, so a local counter
update can leave the parent and its siblings untouched. If the parent also
renders a total derived from that child, set `update_scope: Parent` on the
definition. Rendering then reaches the parent boundary, and enclosing `Parent`
policies propagate through further ancestors. The selected scope must contain
every UI consumer of the changed state. A getter and setter do not establish
exclusive ownership, and the platform does not infer dependencies from reads.

`Elem.lift(element, get, set)` adapts a prebuilt element to parent state without
creating a component. It does not add a render scope, lifetime, or memoization,
and does not intercept delegation. Its non-fallible getter and setter must
remain valid throughout the existing owner's lifetime. Use a fallible
component boundary for a projection that can be removed.

=== Delegation lets the parent decide

`Action.delegate(next_child)` crosses the nearest actual component boundary.
The platform writes the proposed child into a candidate parent, then calls the
definition's `on_delegate(candidate, key)`. The callback may:

* return `Action.update(candidate)` to accept;
* return an update with revised parent data;
* return `Action.none` to veto the whole proposal without committing child data;
* return `Action.task` to start work owned by the parent; or
* return `Action.delegate` to continue to the next parent policy.

Render promotion through `update_scope: Parent` neither calls this callback
nor transfers task ownership. A reusable child can delegate an intent while
its parent decides whether that intent should mutate a collection, close a
view, or begin work that must survive the child's removal.

=== Memoization by default

`Component.define!` compares the complete child input using its `is_eq` method.
Its signature requires `where [child.is_eq : child, child -> Bool]`; ordinary
record inputs need no handwritten comparator. Equal input retains the mounted
subtree and its captured handlers.

Use `Component.memo!` to override that comparison. It accepts the same
fields as `Component.define!` plus `same : child, child -> Bool`:

[source,roc]
----
counter = Component.memo!({
    get: counter_get,
    set: counter_set,
    render: counter_render,
    same: |previous, next| previous.count == next.count,
})
----

The comparison runs only when a mounted snapshot is valid. Returning `True`
promises that retaining the old subtree, including its captured handlers, is
equivalent to rebuilding it with `next`. Include every changing render and
handler dependency in the child input and comparison. Comparing a visible count
alone is wrong if a button also captures a changing increment amount, label,
or layout property. Immutable definition identity avoids comparing functions.

Equality is not automatically this contract. A custom equality may omit fields;
floating-point equality may equate positive and negative zero even if rendering
distinguishes them. An unnecessary miss costs work, but an incorrect hit keeps
stale behavior. Determinism does not make every equality representation-sensitive.
Use an exact input wrapper or a custom comparator if signed zero matters.
The type constraint proves that comparison exists, not that it obeys this law.

`Component.unmemoized!` accepts the same configuration as `Component.define!`
without an equality constraint. It does not retain a comparison snapshot and
always renders when the boundary is reached. Use it for opaque resources,
inputs without a suitable equivalence, or when measurement shows comparison
and snapshot retention cost more than the work they save. It preserves keyed
identity, update scope, delegation, and task ownership; nested memoized
components can still be retained.

A hit during ancestor rendering retains the complete child graph, event routes,
nested instances, and native views. A miss rerenders the component and can
still retain matching memoized descendants. Local descendant updates invalidate
ancestor snapshots so a later ancestor render cannot mistake an old snapshot
for the mounted output. Saved inputs consume memory and may inhibit Roc's
in-place updates. Default memoization is a cost tradeoff, not a guarantee that
comparison is free or that every application benefits; measure with the
production scaling cases and opt out where appropriate.

=== Tasks follow the action owner

Tasks are submitted only after their pending-state graph transaction is
accepted. A completion resolves against the latest state of its original
component instance, not against a render-time snapshot. Matching rerenders and
keyed reorders preserve that lifetime. Removal revokes completion delivery
before any captured getter or resolver runs; reusing the key later does not
revive old work. A delegated task returned by the parent's policy belongs to
that parent instead.

Revocation releases the completed result and captures through ordinary
reference counting. It does not cancel an arbitrary running operation. Use
capability-specific cancellation for blocked work, and application request IDs
to reject superseded results within an instance that remains alive.

For a complete reusable component, see `examples/counter/Counter.roc` and its
composition in `examples/counter/main.roc`. `examples/review-queue` composes
nested components and specifies parent summaries, captured-handler inputs,
delegation, removal, and local versus parent-owned task completion. The terminal
workspace mounts resource-bearing terminal state with `Component.unmemoized!`.

== Directory capabilities and tasks

`Files.pick_directory!()` requests a trusted host-owned Open Project selection.
The selected project grants read authority, while cancellation is a normal
`Canceled` result and denial is `PickDirectoryErr(AccessDenied)`. The returned
`Files.Dir.Read` is an opaque, reference-counted handle: it may be stored in
state or captured by tasks, but applications cannot forge it or recover an
ambient path. Internally it uses the platform-wide typed `Resource.Handle`
representation, leaving the same ABI shape available to future resource APIs.

Open Project is presented by the operating system, never by application code.
On Linux Wayland the host asks the XDG Desktop Portal with directory,
single-selection, read-only and modal options and accepts one portal-returned
`file://` directory. On macOS the host asks the running window for the native
directory panel, and the window owning that panel is the only thread that shows
it. Either way the host opens the selected directory once at the trusted broker
boundary and places only the resulting capability in the registry.

An absent chooser is `PickDirectoryErr(Unavailable)`: a missing portal or D-Bus
on Linux, and on macOS a request made before the window exists or from the
window's own thread, which is the thread that would have to show the panel. One
chooser may be active at a time, and cancellation or refusal starts a short
host-owned cooldown that prevents application-driven prompt loops. An already
provisioned development grant never prompts and is not affected by that
cooldown.

Every root grant records whether its source was trusted chooser selection or
development provisioning and has session lifetime. Derived child handles carry
their immediate parent and inherited source. This metadata is host-private; no
path or grant identity enters captures. `--host-cap-dir` remains development
and automation provisioning and never represents consent.

`directory.list!()` lists at most 10,000 direct children and 4 MiB of
UTF-8 names. Entries distinguish files, directories, symlinks, and other file
types. `directory.open_dir!(name)` acquires a direct child
directory without following the final symlink; names containing traversal or
multiple path components are rejected. `directory.read!(name)` reads
one direct ordinary file as a bounded `List(U8)` without following links. The
64 MiB bound returns `ResourceLimit` instead of constructing an unbounded
application value. Run filesystem operations inside `Action.task`, as
`examples/folder-browser/main.roc` shows.

Filesystem failures use the `Files.FileErr` tag union. Its
`ListDirectoryErr`, `OpenReadDirectoryErr`, `PickDirectoryErr`, and
`ReadFileErr` tags identify the failed operation directly; each carries a
portable `Files.Reason` value.

`Revoked` is distinct from an invalid handle. Each directory operation resolves
the opaque handle and its immutable root lineage while holding the broker
registry mutex. That check is the revocation linearization point. Revocation
that wins the mutex causes that root and every derived child to reject future
list, child-open, and read operations as `Revoked`. An operation that already
won the check owns an `Arc<Dir>` and completes under its ordinary bounds;
revocation does not close that accepted resource. Task submission alone is not
acceptance, so queued work that has not reached the check is rejected.

The trusted host access snapshot exposes only counts grouped by source,
session lifetime, read rights, and active or revoked state. Root identifiers,
names, paths, and URIs remain internal and never enter capture evidence.

Retain a root-to-current list of directory handles to implement Back and
clickable breadcrumbs without exposing paths. Relist a retained handle before
committing navigation, and attach a monotonically increasing request identity
to asynchronous work so a superseded completion cannot replace a newer view.

== Encoded image data

`ImageData.inspect!(bytes, format)` validates bounded encoded bytes already
obtained through application data or an explicit capability and reports pixel
dimensions. It accepts neither paths nor URLs. Raster inspection uses the
maintained `image` decoder and SVG inspection uses `usvg`; inputs above 64 MiB,
dimensions above 32,768, and images above 200 million pixels are rejected.

Failures carry the operation tag `InspectImageErr` and one of `Corrupt`,
`InvalidDimensions`, `ResourceLimit`, or `Unsupported`. Image presentation
continues to use byte-based `Elem.ImageProps`. `ImageData` owns metadata and
integrity inspection only; it does not duplicate layout or rendering props.

The native image-data owner counts staged image nodes, staged encoded bytes,
inspections, and inspection failures. Semantic specifications compare those
numeric counters with `expect-image-owner-counters`; captures never store
encoded content, image names, paths, dimensions, or application text.

== Shipped application assets

An application's own artwork is not user data and not durable state. It is the
application's own read-only content, so it is provisioned automatically and
prompts nobody, and it belongs to a surface of its own.

Small artwork needs no surface at all. A compile-time file import places the
bytes in the executable and `Elem.image` renders them:

[source,roc]
----
import "icons/folder.png" as folder : List(U8)

icon = Elem.image(Elem.ImageProps.{ label: "Folder", bytes: folder, format: Png })
----

`Assets` is for the larger asset -- a background banner, a photograph -- that
should not be paid for in executable size. An application opens a store once
and reads a file when it wants it; the bytes flow into that same `Elem.image`.

A store is anchored to a named root, not to an ambient path. Three roots exist
because moving an executable, changing the working directory, and installing
content apart from the program are three separate events, and none may silently
change what another means:

`Assets.beside_executable(path)`:: A directory beneath the executable's own
directory. The artwork travels with the program, so the store resolves the same
way however the program was launched.
`Assets.working_directory(path)`:: A directory beneath the process working
directory. The root follows the shell, which is what running from a project
checkout wants.
`Assets.content_directory`:: The content directory the host provisioned for
this application. The application names no path here, so an asset store is
never a route to a directory the host did not hand it.

`Assets.open!` returns an opaque `Assets.Store`; `store.read!(path)`
returns the bytes of one asset beneath it. Both touch the disk, so both belong
inside `Action.task`, which runs them on the bounded worker pool and resolves on
the UI thread:

[source,roc]
----
Action.task({
    pending: { ..state, banner: Loading },
    run: || {
        store = Assets.open!(Assets.beside_executable("assets"))?
        store.read!("banners/hero.png")
    },
    resolve: |latest, result| match result {
        Ok(bytes) => Action.update({ ..latest, banner: Loaded(bytes) })
        Err(_) => Action.update({ ..latest, banner: Failed })
    },
})
----

`Assets.Store.stub` is the resource-free store value. An application that keeps a
store in its state needs one to write that state down in a pure `expect`; reads
through it fail, and it proves nothing about asset resolution.

=== Validating an asset set at startup

An asset set may declare a `roc-assets.manifest` file at its root: an
`asset_set` name, a `schema` version, a `content_version`, and an optional
`sha256` digest, one `key = value` per line with `#` comments.

....
# The gallery's shipped artwork
asset_set = gallery
schema = 1
content_version = 7
sha256 = 3b1f...c90a
....

`Assets.with_manifest(config, expectation)` makes the open check that file, so
a half-updated or mismatched asset set is reported at startup rather than
surfacing much later as one image that will not draw. The four comparisons are
reported separately: `AssetSetMismatch`, `SchemaMismatch`,
`ContentVersionMismatch`, and `ContentHashMismatch`. A manifest that is absent,
unreadable, or not a manifest is `ManifestMissing`, `ManifestUnreadable`, or
`ManifestMalformed`; an expectation the host cannot use, such as a digest that
is not 64 hexadecimal characters, is `InvalidExpectation` and is answered before
any file is touched.

The comparison is against the manifest's own declarations. Nothing walks or
hashes the files beneath the root, so an open costs the same for one asset as
for ten thousand.

=== What a store refuses

A store root is a directory handle, never an ambient filesystem capability. The
host resolves every root and every asset path through the one resolver that
serves granted directories. An absolute path, an empty path, a path holding a
NUL, and any `.` or `..` component are refused rather than rewritten, and each
step of a walk refuses to follow a symbolic link, so nothing inside a store can
name anything outside it. A final entry that is a symbolic link or is not a
regular file is `Unsupported`. One asset reads into one value up to 64 MiB;
beyond that the read is `ResourceLimit`. The host never calls `chdir`.

The native asset owner counts opens, refused opens, manifest checks, reads,
refused reads, and bytes read. Semantic specifications compare those six numbers
with `expect-asset-counters`. No path, file name, or asset content ever becomes
evidence.

== Process and pseudo-terminal capabilities

`Process.acquire!` returns an opaque process grant only when the application is
launched with `--host-cap-process=local-shell` or
`--host-cap-process=test-program`. The grant fixes the only profile that may be
started. `grant.spawn!` accepts only terminal dimensions;
applications never provide a profile, executable path, arguments, environment
variables, or command lines to the host.

`Grant.spawn!` creates a real pseudo-terminal with an explicitly bounded row
and column size. `read!`, `write!`, `resize!`, and
`cancel!` are methods on its typed `Process.Pty` handle. Reads and writes are
capped at 65,536 bytes per call, one read may wait on a PTY, and cancellation
wakes that wait. Blocking operations belong in `Action.task`, whose completion
is reconciled with the latest state on the ordinary event route.

Failures carry their operation in the tag, such as
`SpawnProcessErr(AccessDenied)` or `ReadProcessErr(Busy)`. Process grants and
PTYs are opaque `Box(U64)` resources and cannot be confused with other handle
kinds.

== HID device capabilities

`Device.acquire!` returns an opaque grant only when the host has authorised one
exact virtual device or physical USB vendor/product identity. Applications
cannot request arbitrary hardware, inspect operating-system device paths, or
read serial numbers. `grant.discover!()` lists only comparison-safe identity
within that grant, and `grant.connect!()` connects exactly the granted device.

Connections are typed `Box(U64)` resources. `connection.transact!` exchanges one
bounded byte request and response; device-specific framing and values belong in
an application or protocol package rather than the platform. Physical HID and
deterministic virtual transports enter this same operation. Blocking discovery,
connection, and transactions run through `Action.task`.

Failures retain their operation in tags such as
`DiscoverDeviceErr(NotFound)` and `TransactDeviceErr(Protocol)`. Connection and
transaction lifecycle counts are recorded by the host that owns those events.

== System observation capabilities

`SystemMonitor.acquire!` returns an opaque typed sampler only when the host has
granted read-only system observation. `sampler.sample!()` refreshes CPU,
memory, aggregate process disk I/O, network I/O, and a bounded process list on a
task worker. `sampler.close!()` is idempotent. Applications cannot request
another machine or broaden the grant.

Every snapshot field is a tagged `Value` or `Unavailable(Unsupported)` value.
Permission denial is an `AcquireSystemErr(AccessDenied)` operation failure, not
a fabricated unavailable sensor. Overall CPU is normalised across the machine
and uses tenths of one percent in `0..1000`. Per-process CPU uses the same unit
and can exceed `1000` for multi-core use. Memory and I/O counters are bytes as
reported by `sysinfo`; the platform does not infer unavailable measurements.

Processes are bounded and sorted by CPU, memory, then PID. Only PID, display
name, CPU, and memory cross the ABI; user, executable path, arguments,
environment, hostname, and machine identity do not.

== Durable application data

`Files.app_data!()` acquires the application's private read-write directory
granted by `--host-cap-app-data PATH`. The result is an opaque typed
`Files.Dir.ReadWrite` handle; applications cannot recover the host path.

`directory.read_utf8!(name)` distinguishes `Missing` from
`Value(Str)`. `directory.write_utf8_atomic!(name, value)`
synchronises a private temporary file before replacing the direct child in the
same directory. Names are flat ASCII identifiers of at most 128 bytes, values
are UTF-8 of at most one MiB, and the ordinary operation-tagged `Files.FileErr`
surface reports acquisition, read, and write failures.

Run these blocking operations inside `Action.task`, with a monotonic request
identity when an edit can supersede pending work. The Settings Center uses this
route and retains a newer draft when an older load completes.

== Audio output capabilities

`Audio.acquire!()` acquires an opaque output handle for ordinary mixer output.
Playing sound through the shared system mixer is an automatically provisioned
service with no prompt, and the handle lasts for the session; exclusive access
or unusual routing would be separate scope. Acquisition fails when the machine
has no usable output device. `Audio.load!(output, directory, name)` loads
one direct file through an existing `Files.Dir.Read` grant; names with traversal
or multiple components are rejected and encoded input is bounded to 64 MiB.
The host delegates media decoding and playback to Rodio and Symphonia.

`Audio.Track` is an opaque host resource. `Audio.play!`, `Audio.pause!`,
`Audio.seek!`, `Audio.status!`, and `Audio.stop!` are bounded operations intended
for `Action.task`. Status reports the decoder-owned duration, playback position,
and `Playing`, `Paused`, or `Stopped` state. `Audio.AudioErr` identifies
the failed operation and carries a portable reason such as `DecodeFailed`,
`OutputUnavailable`, or `InvalidCapability`.

Specification runs may receive a harness-owned null-output grant. It drains
the same paced Rodio mixer, decoder, and player state used by a system output;
it changes only the final device sink.

== Clipboard capabilities

`Clipboard.acquire!()` acquires text clipboard authority only when the host
was launched with `--host-cap-clipboard`. Its opaque `Clipboard.Handle` uses
the common typed `Box(U64)` representation and cannot be manufactured or
confused with another resource family.

`handle.read_text!()` returns a bounded UTF-8 snapshot with a
monotonic sequence. Applications compare sequences to suppress stale reads and
deduplicate repeated content. `handle.write_text!(text)` schedules
replacement on GPUI's owning UI context. Both directions reject values larger
than 64 KiB. `Clipboard.ClipboardErr` identifies acquisition, reading, and
writing with distinct operation tags carrying a portable reason.

Observe changes with one pull-based `Timer` subscription inside `Action.task`.
Pause by cancelling that timer; sensitive values are discarded before they
enter state. Clipboard content is application data and never enters host
diagnostics or observatory captures.

== HTTP requests

Applications declare `roc-lang/http` v1.0.0 and build its canonical `Request`
values. `Http.acquire!()` returns an opaque `Http.Client` only when the host
was launched with `--host-cap-http-origin ORIGIN`. The grant names one exact
scheme, host, and effective port; requests and redirects cannot leave it.
Acquire failures are `AcquireHttpErr(reason)` and exchange failures are
`SendHttpErr(reason)`, retaining the operation together with the portable
reason. Provisioning grants authority for development and automation; they are
not a substitute for an application's user-visible trusted-destination setup.

The host disables ambient proxy discovery, rejects credentials embedded in
URLs, and pins an accepted non-literal destination resolution for the exchange.
Literal loopback or private addresses remain usable only when named explicitly
by the provisioned origin.

`client.send!(config, request)` performs one bounded exchange and returns
the package's canonical `Response`. Call it from `Action.task` so connection,
TLS, and response work runs on the native worker pool and its reducer returns
through the ordinary UI-thread completion dispatcher.

Requests and config make policy explicit: method, URI, headers, body, timeout,
`max_response_bytes`, and `max_redirects`. `Http.Config` carries a default for
each limit -- a 30 second timeout, a 1 MiB response, and three redirects -- so
`Http.Config.{ timeout_ms: 2_000 }` states only the limit it moves. URLs must
use `http` or `https`.
The platform accepts standard methods, at most 64 headers and 32 KiB of header
data, a request body up to 1 MiB, a timeout from 1 through 60,000 milliseconds,
a response limit from 1 byte through 4 MiB, and from zero through ten redirects.
Response bodies remain `List(U8)` so downstream packages share the same nominal
types. Portable failures distinguish invalid inputs, denied or invalid
capabilities, unsupported schemes, connection and timeout failures, and
redirect and body limits.

Give each submitted request a monotonically increasing identity. In the task
resolver, compare that identity with the latest state and return `Action.none`
for an obsolete result. This prevents a slow earlier response from replacing a
newer response without creating a second completion route.

== Read-only SQLite capabilities

`Sqlite.open_read!(directory, name)` opens one direct ordinary child of a
granted directory as a read-only database capability. The operation rejects
path traversal and symlinks and never exposes an ambient path. Database bytes
are bounded to 64 MiB and the returned `Sqlite.Db` is an opaque, reference-
counted `Box(U64)` handle whose final release closes the native connection.

`database.query!(sql)` prepares and executes one read-only statement.
Results preserve SQLite's `Null`, `Integer`, `Real`, `String`, and `Bytes`
value kinds. Queries are bounded to 64 KiB of SQL, 256 columns, 10,000 rows,
and 16 MiB of returned text and blob bytes. Limit violations and invalid,
corrupt, busy, inaccessible, or non-database resources are typed errors.
Failures use `OpenDatabaseErr(reason)` and `QueryDatabaseErr(reason)`, so callers
can distinguish the failed operation before matching the portable reason.
Every reason retains SQLite's bounded diagnostic string; `Sqlite.detail`
extracts it for user-facing status without flattening the public error type.

Open and query calls are blocking capability operations. Run them inside
`Action.task`, retain the last successful view while work is pending, and use a
monotonic request identity in the resolver so an older completion cannot
replace a newer result. `examples/database-browser` demonstrates this pattern.

== TCP endpoint capabilities

`Tcp.connect!()` opens an ordered byte stream to the single numeric
`IP:PORT` endpoint granted with `--host-cap-tcp`. Without that host grant it
returns `ConnectTcpErr(AccessDenied)`. The application cannot select or derive a
different destination from the opaque handle, and releasing its final
reference closes the socket and removes the host registry entry.

`stream.read_up_to!(max_bytes)` reads between one byte and a
one-MiB requested maximum; an empty list means orderly end of stream.
`stream.write_all!(bytes)` writes the complete value or fails and
accepts at most 16 MiB. `stream.close!()` is idempotent. Connections,
reads, and writes have finite native timeouts, and failures use the
operation-tagged `Tcp.TcpErr` union: `ConnectTcpErr`, `ReadTcpErr`,
`WriteTcpErr`, or `CloseTcpErr` wraps a portable reason.

The numeric endpoint has no DNS resolution or ambient destination selection.
The command-line grant provisions development and automation authority; a
user-facing client obtains trusted connection authority through a named,
revocable destination broker rather than treating that flag as user consent.

TCP operations block and belong inside `Action.task`. Protocol packages build
on the byte transport rather than being reimplemented by the platform. The
Redis Explorer adapts a stream with `roc-redis`'s `Transport.from_bytes_io`, so
command encoding, bounded RESP2 decoding, typed commands, and exchange policy
remain the responsibility of the established platform-independent package.

== Retained canvas

`Elem.canvas` paints an ordered list of keyed `Rectangle`, `Ellipse`, and
`Line` primitives in native GPUI. A canvas and every primitive have stable
semantic labels. Primitive keys are non-zero and unique within the canvas;
they preserve direct-manipulation identity independently of list position.

The controlled `on_pointer` handler receives `Begin`, `Move`, and `End` in
integer canvas coordinates. The topmost hit-tested primitive is captured on
`Begin`, and that same optional target key accompanies the complete gesture,
including when a state update replaces the canvas subtree.
