= Specification language reference

The complete `.scm` vocabulary: locators, operations, assertions, window steps,
and case selection. Read Testing your application first if you are verifying an
application for the first time; this chapter is the one to reach for once you
know what you want to say and need to know how to say it. Steps that depend on
this repository's own fixtures are described in Contributing instead, so a
vocabulary entry here means the same thing in any application.

Specifications describe the application as a user sees it: find text, identify
a button by its semantic name, press it, and check the result. Put `.scm` files
in a `specs/` directory beside the `main.roc` they exercise. Both runners read
the same directory, because the steps a file contains decide which runner takes
it:

....
my-app/
├── main.roc
└── specs/
    └── editing.scm
....

The files contain S-expression data. They are not Scheme programs and do not
execute arbitrary code.

== A behaviour specification

[source,scheme]
----
(test "Counter increments independently"
  (steps
    (expect-visible (text "Counter"))
    (expect-visible (text "-1"))
    (click (role button :name "Left increment"))
    (expect-not-visible (text "-1"))
    (expect-visible (text "0"))))
----

Run one application's specifications with a repository-relative glob:

[source,sh]
----
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
----

Run every example and benchmark specification with no pattern:

[source,sh]
----
python3 scripts/run_specs.py
----

Each specification gets a fresh process. This isolates application state and
produces one `.rgstats` SQLite capture beneath a timestamped
`.test-out/specs/` directory. A failing assertion makes the command fail and
prints the specification line and reason.

== Grants

A specification states the capabilities it needs beside its steps, so a case can
be read on its own and nothing is inferred from a file name:

[source,scheme]
----
(test "a corrupt track is isolated"
  (grants
    (directory "fixture")
    (audio null))
  (steps
    (click (role button :name "Open library"))
    (expect-visible (text "1 track skipped"))))
----

A specification with no `(grants ...)` clause, and one with an empty `(grants)`,
both receive no capability at all. Write the empty clause when the absence is
the point: a denial case takes the same refusal from the same production
acquisition call that a real broker would give it.

Each grant may appear once. A path is relative to the application directory, the
one holding `main.roc`, and a path that leaves it is a parse error naming its
line, as an unknown grant or a malformed one is.

`(app-data "PATH")`:: Private application-data storage, seeded from `PATH`. The
run receives a fresh private copy, so it writes through the production
capability without changing the checked-in directory.
`(assets "PATH")`:: The content directory an `Assets.content_directory` store
resolves to. The application names no path of its own, so the case names the one
the host provisions. Omit the grant and the open is `AccessDenied`, which is how
a case exercises an application's missing-artwork path.
`(audio null)`:: A paced null output in place of the system audio device. It
changes only the final sink; decoding, mixing, playback, seeking, and status
remain the production path.
`(clipboard system)` and `(clipboard fixture)`:: Text clipboard authority. The
system form reaches the real clipboard; the fixture form gives the case a
clipboard the `clipboard-text` step drives, which is rejected without it.
`(device virtual)` and `(device virtual N)`:: One deterministic virtual HID
device, optionally with `N` controls, reached through the same host capability
as physical hardware.
`(device "VID:PID")`:: One physical HID device by hexadecimal vendor and product
identifier.
`(directory "PATH")`:: Read access to one directory, reached through the same
opaque capability operations as an interactive grant.
`(directory canceled)`:: A directory chooser the person dismisses without
choosing. The chooser opens and the acquisition call runs, but no authority is
produced and `Files.pick_directory!` answers `Ok(Canceled)`. Cancelling is not a
failure, so this is its own provisioning rather than an absent grant, and it is
how a case shows that an application returns to rest instead of accusing the
person of a denial. It cannot be combined with `(directory "PATH")`.
`(http-origin "ORIGIN")`:: HTTP access to exactly one origin. A request to any
other origin is denied by the host.
`(process local-shell)` and `(process test-program)`:: One PTY child profile.
`test-program` is the fixed deterministic child; `local-shell` is the user's
shell.
`(server "PATH" PORT)`:: A loopback service the runner starts before the case
and stops after it. `PATH` names a script beside the application, and `PORT` is
the port it reports readiness on. This grants the harness, not the application:
a case still needs `(http-origin ...)` or `(tcp ...)` to reach it.
`(system-monitor standard)`, `(system-monitor unavailable)`, and
`(system-monitor processes N)`:: A deterministic system sampler delivering its
snapshots through the same ABI as the physical source.
`(tcp "IP:PORT")`:: TCP access to exactly one endpoint.

== Locators

`within` scopes any locator to a named part of the mounted graph. Text and
prefix locators follow, then role locators in alphabetical order by role.

`(within ANCESTOR TARGET)`:: Matches `TARGET` nodes that are strict descendants
of a node matched by `ANCESTOR`. Either locator may itself use `within`. The
ancestor never matches itself, and several matching ancestors do not duplicate
a target. Multiple target matches remain ambiguous for interactions.
`(text "value")`:: Text whose entire value equals `value`.
`(text-prefix "prefix")`:: Text beginning with `prefix`.
`(button-prefix "prefix")`:: Button names beginning with `prefix`.
`(canvas-item-prefix "prefix")`:: Keyed canvas primitives whose labels begin
with `prefix`. This locator supports deterministic primitive counts in scaling
specifications.
`(checkbox-prefix "prefix")`:: Checkbox labels beginning with `prefix`.
`(role button :name "name")`:: A button with the semantic `name` passed to
`Elem.button` or `Elem.action_button`.
`(role canvas :name "name")`:: A retained drawing surface identified by its
stable semantic name.
`(role canvas-item :name "name")`:: A keyed canvas primitive identified by its
stable semantic label.
`(role checkbox :name "label")`:: A checkbox identified by its visible label.
`(role column :name "name")`:: A column identified by its semantic name.
`(role dialog :name "label")`:: The active modal dialog identified by its
semantic label.
`(role image :name "name")`:: An encoded image identified by its
application-supplied semantic name. Neither encoded bytes nor source filenames
are captured.
`(role panel :name "label")`:: A panel identified by its semantic label.
`(role row :name "name")`:: A row identified by its semantic name.
`(role scroll :name "name")`:: A scroll region identified by its semantic name.
`(role textarea :name "name")`:: A multiline editor identified by its semantic
name. Locator matching never records its value.
`(role textbox :name "label")`:: A controlled text input identified by its
semantic label.
`(role virtual-list :name "name")`:: A fixed-row virtual list identified by its
semantic name.

An interaction locator must resolve to exactly one live node. Ambiguous and
missing targets fail instead of choosing one by traversal order. Use unique
semantic names or scope repeated component-local names through a named
container:

[source,scheme]
----
(replace-text
  (within (role panel :name "Left editor") (role textbox :name "Value"))
  "Changed")
----

Both runners resolve scoped locators through the same mounted-graph matcher.
Scopes do not depend on native view materialisation, so they also work for
logically mounted virtual-list rows. A canvas primitive is a strict semantic
child of its owning canvas, so `(within (role canvas :name "Stage")
(canvas-item-prefix "Dot"))` counts matching primitives on that canvas. A
primitive is a leaf and cannot itself contain further matches.

Row and column locators describe the mounted application graph. They do not
assert pixel geometry or operating-system accessibility.

== Operations

Steps that act on the application, in alphabetical order.

`(await-count LOCATOR N)`:: Apply task completions until the locator matches
`N` nodes, then continue. Output that arrives over several tasks, such as a
terminal's, is chunked by the platform rather than by the application, so a
specification that counted `await-task` steps would be asserting how an
operating system flushed a pipe. This waits for what the application shows
instead, and fails if the graph has not said it before the task budget expires.
Follow it with `expect-count` to assert the same number exactly. On the window
runner the step ends on a presented frame carrying those nodes, so a following
`expect-on-screen` asks about something the window has actually drawn.
It waits for a state, not for a change. A count that already holds when the step
begins satisfies it immediately, having awaited nothing, so a locator matching
something left over from an earlier step proves nothing about this one. Wait for
what the step under test produces, such as the output of the command it sent.
`(await-task)`:: Wait for exactly one accepted worker task and apply its
completion through the normal latest-state route. A task that resolves to
another task requires another `await-task` step.
+
On the window runner this claim is weaker, and knowingly so: frames are what
apply completions, so the task has usually landed before the step runs, and an
application holding a subscription open — a terminal reading, a timer playing —
never reaches a moment with nothing in flight. The step therefore waits for the
window to go quiet rather than for a completion it can attribute. Where the
distinction matters, say what the application should show with `await-count`
instead of counting tasks.
`(await-ticks N)`:: Apply `N` successive timer wait completions through that
same worker and latest-state route. `N` must be positive.
`(click LOCATOR)`:: Press exactly one matching enabled control through the
application's normal Roc event route. A disabled control consumes no event and
does not call Roc, matching the interactive host.
`(hover-enter LOCATOR)` and `(hover-exit LOCATOR)`:: Deliver a button hover
transition through the canonical mounted graph and normal Roc route. Duplicate
transitions and disabled controls dispatch nothing. Both runners use the same
transition owner. The window runner requires an entering target to be painted
and visible, then dispatches a GPUI mouse-move event at its centre. Exit moves
the simulated pointer outside the window; GPUI performs hit testing and delivers
the resulting transitions.
`(expect-background LOCATOR 0xRRGGBB)`:: Compare the explicit application
background in the mounted graph. Native hover refinements are separate. Missing
backgrounds fail as unavailable; colors are not recorded as count evidence.
`(mark-native-work)`:: Start observing completed native frames in a window run.
The underlying production counters remain active independently of recording.
`(expect-native-work :button-renders-max N :boundary-renders-max N :boundary-elements-max N :cached-prepaint-subtrees-min N :cached-paint-subtrees-min N :replayed-scene-operations-min N :fresh-hitboxes-max N :fresh-mouse-listeners-max N :element-states-moved-min N)`:: Bound
actual button and boundary view renders and boundary view elements created in
every completed frame since the mark. Each limit is optional, but at least one
is required. GPUI-owned limits distinguish cached subtree replay from fresh
hitbox and listener insertion and finish-time element-state movement. Minimums
prove that reuse work actually occurred; maxima bound fresh reconstruction.
Element creation measures the host handing a view to GPUI even
when that view subsequently reuses its rendered subtree. A missing
mark or no completed frame fails as unavailable. Choose limits from the
changed patch frontier and the application's ordinary native controls; these
assertions belong to controlled interactions without unrelated input or resize.
`(drag LOCATOR FROM-X FROM-Y TO-X TO-Y)`:: Send one complete captured pointer
gesture through a canvas's production event route. Coordinates are integer
logical pixels in canvas space.
`(focus LOCATOR)`:: Give semantic keyboard focus to exactly one enabled button
or checkbox. Focus remains valid only while that mounted node is live.
`(mark-metrics)`:: Separate benchmark setup from the operation being measured.
`(press-key Enter)`:: Activate the focused button through the normal Roc event
route.
`(press-key Escape)`:: Dismiss the active dialog through its `on_dismiss` route.
`(press-key Space)`:: Activate the focused button, or toggle the focused enabled
checkbox, through the normal Roc event route.
`(replace-text LOCATOR "value")`:: Replace the complete controlled value of one
editable text input or textarea through its production Roc input route. A text
input delivers `Event.TextChange`; a textarea delivers `Event.Input`. A
disabled text input consumes no edit and dispatches nothing. A disabled or
read-only textarea fails as non-editable.
`(submit LOCATOR)`:: Deliver an enabled text input's current controlled value as
`Event.TextSubmit` through the normal Roc event route.

== Assertions

Steps that check the application, in alphabetical order.

`(expect-before FIRST SECOND)`:: Require a match for `FIRST` to occur before a
match for `SECOND` in mounted-tree order.
`(expect-asset-counters OPENS REFUSED CHECKS READS READS-REFUSED BYTES)`::
Require the asset owner's six totals, in that order: opens, refused opens,
manifest checks, reads, refused reads, and bytes read. No asset path, file name,
or content becomes evidence.
`(expect-grant-counters RECORDED RELEASED REVOKED DENIED)`:: Require the grant
registry's four totals, in that order. Released and revoked are counted apart
because they are different facts: an application that stopped holding a handle
did not have its authority taken away.
`(expect-grants DESCRIPTION...)`:: Require exactly these grants, in registry
order, each written as `KIND ORIGIN/ENFORCEMENT LINEAGE RIGHTS` with ` revoked`
appended once its authority has been taken away — for example
`"directory provisioned/consent-only root read,list,derive"`. `ORIGIN` is
`trusted-selection`, `provisioned`, or `automatic`; `ENFORCEMENT` is `brokered`
when the broker returned authority the process could not obtain for itself and
`consent-only` when a person chose in a trusted surface but nothing outside the
process enforces the scope. `LINEAGE` is `root` or `derived`. No step means the
application holds no authority at all. Identifiers are deliberately not part of
a description: they are allocation order, which is a fact about the run rather
than about the authority.
`(expect-canvas-primitives LOCATOR N)`:: Require one canvas owner to report
exactly `N` retained primitives. The expected and observed values are stored as
deterministic scale evidence.
`(expect-clipboard-counters LIVE ACQUIRE READ WRITE)`:: Require the
owner-recorded live handle count and attempted clipboard operations. A field
may be `_` when concurrent production work makes that particular expectation
nondeterministic. Its observed value is still recorded; the expected evidence
column is absent rather than zero.
`(expect-component-work :rendered N :compared N :skipped N :mounted N :retired N :registry-visits N :ancestor-invalidations N :projection-gets N :projection-sets N :keyed-order-visits N :keyed-snapshot-items N)`::
Require exact component-runtime work in the most recently committed action
turn, including its nested rendering and lowering. Supply one or more named
counts in any order; omitted counts are unconstrained. Both runners read the
same production observation, including when capture is disabled. A missing
observation fails as unavailable. Assertions do not start a new action turn.
Projection counts record configured getter and setter calls, including calls
that return `Removed`; they exclude arbitrary application reads and background
worker execution. They measure adapter work separately from boundary renders.
`(expect-count LOCATOR N)`:: Require exactly `N` matches and record expected and
observed counts.
`(expect-device-connections N)`:: Require exactly `N` host-owned device
connection handles.
`(expect-device-transactions N)`:: Require exactly `N` completed host-owned
device transactions.
`(expect-file-picks N)`, `(expect-file-lists N)`, `(expect-file-opens N)`, and
`(expect-file-reads N)`:: Require exact cumulative counts recorded by the Files
owner.
`(expect-focused LOCATOR)`:: Require semantic focus to be on exactly one
matching enabled control. This proves the host's dialog focus policy, not a
compositor-delivered focus event.
`(expect-http-counters LIVE ACQUIRE SEND DENIED)`:: Require the owner-recorded
live client count, operation attempts, and authority denials.
`(expect-image-bytes LOCATOR N)`:: Require an image node to own exactly `N`
encoded bytes, and record expected and observed deterministic counts without
persisting image content.
`(expect-not-visible LOCATOR)`:: Require no matches.
`(expect-patch :kind KIND :staged N :removed N)`:: Check the host patch produced
by the preceding click. `KIND` is `mount`, `replace`, or `no_change`.
`(expect-processes N)`:: Require exactly `N` live host-owned PTY child
processes.
`(expect-sqlite-counters LIVE OPEN QUERY)`:: Require the owner-recorded live
connection count and attempted SQLite operations.
`(expect-subscriptions N)`:: Require exactly `N` active host timer handles. This
assertion reads the timer registry that owns cancellation state.
`(expect-system-samplers N)`:: Require exactly `N` active host-owned system
samplers.
`(expect-system-samples N)`:: Require exactly `N` completed host-owned system
samples.
`(expect-tcp-counters LIVE CONNECT READ WRITE CLOSE)`:: Require the complete
owner-recorded TCP resource and attempted-operation vector.
`(expect-tcp-streams N)`:: Require exactly `N` live host TCP stream handles.
`(expect-value LOCATOR "value")`:: Require an exact controlled text-input or textarea value.
The value is compared in memory and is not copied into captures or diagnostics.
`(expect-value-bytes LOCATOR N)`:: Require the text-input or textarea value to contain exactly
`N` UTF-8 bytes, and record the expected and observed deterministic counts.
`(expect-visible LOCATOR)`:: Require at least one match.

Each counter assertion reads the production owner of the resource or component
work, and records its expected and observed values as ordinary
deterministic step evidence.

Prefer semantic results—visible text, counts, and order—for application
behaviour. Use `expect-patch` when the amount or absence of host work is itself
part of the contract, such as proving that an idempotent press returns
`no_change` and stages no nodes.

== What the semantic runner proves

The semantic runner queries the same mounted graph the native host uses. It
does not construct a separate test tree. Because it opens no GPUI window, it
suits deterministic semantic checks; pixels, layout, and presentation are
outside its evidence. Those claims belong to the window runner.

For a virtual list, text and control locators inspect all logically mounted
items, including rows outside an interactive viewport. A headless
`expect-visible` therefore proves logical presence, not viewport intersection.
Only GPUI records native visible-range and materialisation evidence.

`focus` and `press-key` model the production controls' accepted activation-key
matrix and invoke their normal Roc event route. In the semantic runner they
inject no native GPUI key event and verify neither compositor delivery, tab
traversal, focus painting, nor operating-system accessibility.

== Window specifications

A window specification is an ordinary `(test ...)` file that uses window-only
steps. It lives beside every other specification for its application, because
the steps a file contains are what decide which runner takes it. Nothing about
its location or its name carries that meaning.

Your application runs one itself:

[source,sh]
----
./my-app --host-run-window-spec specs/on-screen.scm \
    --host-window-report=.test-out/report.json \
    --host-window-shot-dir=.test-out
----

The process opens the production GPUI window, drives it through the same render
path and event route an interactive session uses, and writes a JSON report. In
this repository `scripts/run_specs.py` builds the host, builds each example, and
routes each case to the runner its steps require:

[source,sh]
----
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
python3 scripts/run_specs.py --only window
----

`--host-describe-specs PATH...` prints one JSON line per file giving the runner
it needs and the capability flags its grants become, which is how the driver
routes and wires a case without keeping a second copy of the vocabulary.

=== One vocabulary, split by capability

There is one specification language. Every step declares where it can be
honest, and each runner refuses the other's steps by name rather than skipping
them silently:

`semantic-only`:: `mark-metrics`, `expect-patch`, and `benchmark` clauses,
which depend on the semantic runner's per-iteration mount. Also every step the
window runner does not implement: `drag`, `replace-text`, `submit`, and the
repository fixture steps the Contributing chapter describes.

`window-only`:: `settle`, `screenshot`, `type`, `key`, `resize`, `scroll`,
`expect-on-screen`, `expect-rendered-count`, and `expect-bounds`. None of these
mean anything without a presented frame: without layout there is no fold for
content to be below, and no size a window could be resized from.

`both`:: `click`, `focus`, `press-key`, `await-task`, `await-count`, `clipboard-text`,
`await-ticks`, `expect-visible`, `expect-focused`, `expect-not-visible`,
`expect-count`, `expect-component-work`, and the value and ordering assertions — `expect-value`,
`expect-value-bytes`, `expect-image-bytes`, `expect-before`, and
`expect-canvas-primitives`. The fixture clipboard is one process-wide store, so
changing the granted source and waiting for the application's own timer to
observe it mean the same thing under either runner; without them a windowed
case could not put a single item into a clipboard-driven application, and so
could not photograph one. The value and ordering assertions read the mounted
graph, which both runners hold, and both call the same code to answer them, so
one window case can assert a semantic truth and photograph it in the same run.

Also `revoke-file-grants` and the live-resource and capability counter
assertions. The host owns one files registry, one clipboard, one audio device
table; both runners read them through the same shared implementation, and
revocation acts on that one registry. A windowed case can therefore photograph a
granted-authority readout and assert the counters that produced it in the same
run. File operation counts are differences from the start of the run's
lifecycle, of which the window runner has exactly one.

A step is classified by what a runner actually does, so a specification is
refused before the window opens rather than part-way through a run.
`expect-visible` asserts the same claim on either runner: presence in the
mounted graph. The stronger pixel claim is `expect-on-screen`, so one word never
means two different things.

=== Window-only steps

Input steps first, then waiting, then assertions in alphabetical order.

`(key "CHORD")`:: Send one real chord, such as `"cmd-a"` or `"escape"`, through
the window's production keymap. The semantic `press-key` covers three
activation keys and no modifiers.
`(type "TEXT")`:: Send each character as a real keystroke into the focused
element, through GPUI's own keystroke dispatch. The semantic `replace-text`
sets a value directly and exercises none of the editing path.
`(resize W H)`:: Resize the production window to `W` by `H` logical pixels, each
64 to 8192. A layout is only proved at the size it was tested at, and
`main.roc` asks for one size, so this is how a specification claims a narrow or
a wide window rather than assuming one. Follow it with `(settle)` before
asserting, as with any other input step.
`(scroll REGION :by N)`:: Move a scroll region or a virtual list by `N` logical
pixels. Positive moves towards the end of the content, which is the direction a
wheel-down gesture moves it; negative moves back. The request is clamped against
the real content size, so an overlarge `N` settles at the end rather than past
it, which is how a specification returns a list to its start without knowing how
tall it is.
`(scroll REGION :to LOCATOR)`:: Move `REGION` only as far as it must to bring
`LOCATOR` inside it. A target already in view does not move the region at all.
The target must be inside the region, and a target taller than the region is
aligned to its leading edge, since no offset shows all of it.
+
For a scroll region the distance is real geometry: every child is laid out,
below the fold included, so the travel is measured rather than estimated. A
virtual list has no such rectangle — a row below the fold has no element at all
— so the list is positioned by that row's index among the entries the
application mounted, and the row materialises as a result. This is what brings
an off-screen target on screen, and it is the only handle an unrendered row
offers.
`(settle)` / `(settle :frames N :timeout-ms N)`:: Wait for `N` consecutive
presented frames during which no host task started or finished. Defaults are
`:frames 2 :timeout-ms 2000`. A timeout fails the step; it never proceeds
quietly, because an assertion against a half-settled frame is not evidence.
`(expect-bounds LOCATOR :min-width N :max-width N :min-height N :max-height N)`::
The laid-out size falls within the given bounds. At least one bound is
required. Deliberately minimum and maximum only, never exact: exact pixel
geometry is font- and DPI-dependent and would rot the suite.
`(expect-on-screen LOCATOR)`:: The node was painted in the last completed frame
and its rectangle survives clipping by the viewport and by every scrolling
ancestor. This is the claim the semantic runner cannot make.
`(expect-rendered-count LOCATOR N)`:: Exactly `N` matching nodes took part in
the last frame. For a virtual list this is materialisation evidence;
`expect-count` counts logically mounted nodes instead.

=== Screenshots

`(screenshot NAME)`:: Photograph the window's content area.
`(screenshot NAME :region LOCATOR)`:: Crop to a located element's visible
bounds. These are the bounds `expect-on-screen` uses, so a shot frames what was
asserted, and an element half below the fold of a scroll region is photographed
where it has pixels rather than where it was laid out.
+
A canvas-item locator works here too. A primitive has no element and no recorded
bounds of its own, so its rectangle is the canvas's painted surface offset by
the coordinates the owner drew at — the mapping `canvas_target` inverts to
decide what a press landed on — clipped to that surface. A line is expanded by
half its stroke, since its coordinates describe its centre. Give it `:pad`: a
marker a few points across is unreadable cropped to itself.
`(screenshot NAME :region (rect X Y WIDTH HEIGHT))`:: Crop to an explicit
content-relative rectangle.
`:pad N`:: Expand the region by `N` points on every side, then clamp to the
content area. A control cropped to its exact bounds is usually unreadable out
of context.

`NAME` is required and becomes the file stem, so it is limited to lowercase
letters, digits, and hyphens. Files are written as `NN-NAME.png`, numbered by
step, and indexed in the report's `screenshots` array. A `:region` locator that
does not match exactly one node fails the step, as `click` does.

The host asks the platform's capture tool for a screen rectangle, which it can
compute because it knows its own window origin and where each node was laid
out. Cropping is therefore part of the request rather than a post-processing
step. On macOS this is `screencapture`; under a wlroots compositor it is
`grim`.

Capture is honest about not happening. A missing tool, a denied Screen
Recording permission, or a region with no area on screen is reported as
`unavailable` with a reason and a hint, never as a pass and never as an empty
file. By default an unavailable screenshot fails the run;
`--host-window-allow-missing-shots` downgrades it to a report entry, which is
how continuous integration runs these specifications on machines that cannot
grant screen recording. Every behavioural assertion still gates there.

Screenshots taken before a failing step are kept. The image of the state an
assertion stopped at is usually the most useful evidence in the run.

=== What input is real

Keyboard steps send real keystrokes through the window's production keymap.
`scroll` writes the offset cell of the scroll handle the production element
tracks — the same cell GPUI's own wheel handler writes, and the same one that
keeps a list where the person left it across a rerender. What it does not
synthesise is a wheel event, so hit testing, momentum, and rubber-banding are
not exercised; those belong to the pointer seam this host does not have.
Pointer steps are simulated at the production handler, but are refused unless
the control was laid out, is unclipped, is enabled, and is not behind a modal
dialog, so a `click` a real user could not have performed fails rather than
passing quietly. `hover-enter` and `hover-exit` dispatch mouse-move events into
the live GPUI window, exercising hit testing, production views, and the normal
event route. They do not move the operating-system pointer. GPUI tests also
verify replacement continuity and disabled or stale routes. The Testing your
application chapter explains why, and what each guarantee is worth.

=== What the probe cannot see

Bounds come from the production render path, through the same `canvas` prepaint
closure the host already uses for canvas hit testing. Recording is off unless a
window specification asked for it, gated by a runtime check rather than a
compile-time one, so the shipped binary stays the tested binary.

* A node that never renders has no bounds. That is the intended signal rather
  than a gap: an unmaterialised virtual-list row is genuinely absent from the
  frame.
* Only a canvas node's own rectangle is recorded, never its primitives. A
  canvas-item locator has no bounds of its own to assert against, so
  `expect-bounds` and `expect-on-screen` do not take one; a screenshot region
  does, because a primitive's rectangle is derivable from its canvas's painted
  surface and the coordinates the owner drew at.
* Bounds are recorded for nodes scrolled out of view, because they are laid
  out and merely clipped. `expect-on-screen` intersects against scrolling
  ancestors for this reason; asking only whether bounds exist would call a
  clipped element visible.

Bounds persist until a node leaves the mounted graph. GPUI caches views, so a
control whose state did not change is not re-rendered and records nothing that
frame; treating that as "not laid out" would report a plainly visible control
as missing. `expect-rendered-count` therefore counts nodes that have been laid
out while mounted, which is the materialisation evidence a virtual list needs.

Because bounds describe the tree as it stood when a frame drew it, they answer
nothing about a change no frame has drawn yet. The runtime counts a generation
for every applied patch and each frame stamps the generation it drew, so a
painted step waits for the window to catch up before it reads anything, and a
graph the window has not drawn is reported as exactly that rather than as an
element that is missing. Waiting is not left to the specification: an input
step returns once the window has drawn what it did, and `await-count` ends on a
frame carrying the nodes it waited for. Assertions that read the mounted graph,
such as `expect-visible` and `expect-count`, need no frame and take none.

== Selecting and repeating cases

Patterns match repository-relative specification paths. Multiple patterns may
be supplied. Compatible released hosts are verified and staged automatically.
Use `--skip-host-build` only to reuse an already staged local host while
iterating:

[source,sh]
----
python3 scripts/run_specs.py \
  'benchmarks/rows/specs/create-*.scm' \
  'benchmarks/rows/specs/append-*.scm' \
  --skip-host-build
----

The default is one case at a time. `--jobs N` runs cases concurrently, which is
useful for semantic validation but marks timing-environment evidence partial.
Use serial runs for performance comparisons. `--aa` repeats each passing case
with the same executable to show run-to-run noise.

The runner prints a UTC start, UTC finish, and elapsed wall time for every case,
including timeouts and process failures. Timing is diagnostic evidence only;
specification assertions and deterministic counters decide correctness. CI runs
ordinary semantics, serial scaling cases, native smoke checks, and real-window
specifications as independent jobs. On failure it retains bounded JSON status,
partial `.rgstats` evidence, and a sanitized textual Windows debugger report
when one is available. Raw process memory is never retained because it can
contain application data and machine identity.
