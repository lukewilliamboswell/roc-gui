= Specifying behaviour

Specifications describe the application as a user sees it: find text, identify
a button by its semantic name, press it, and check the result. Put `.scm` files
in a `specs/` directory beside the `main.roc` they exercise:

....
my-app/
├── main.roc
└── specs/
    └── editing.scm
....

The files contain S-expression data. They are not Scheme programs and do not
execute arbitrary code.

== A behaviour specification

[source,scheme]
----
(test "Counter increments independently"
  (steps
    (expect-visible (text "Counter"))
    (expect-visible (text "-1"))
    (click (role button :name "Left increment"))
    (expect-not-visible (text "-1"))
    (expect-visible (text "0"))))
----

Run one application's specifications with a repository-relative glob:

[source,sh]
----
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
----

Run every example and benchmark specification with no pattern:

[source,sh]
----
python3 scripts/run_specs.py
----

Each specification gets a fresh process. This isolates application state and
produces one `.rgstats` SQLite capture beneath a timestamped
`.test-out/specs/` directory. A failing assertion makes the command fail and
prints the specification line and reason.

If an application has an adjacent `fixture/` directory, the runner grants that
directory through the production `--host-cap-dir` boundary. Fixture contents
are therefore exercised through the same opaque capability operations as an
interactive grant, without giving the application ambient test-only I/O.

Image specifications can assert the production image-data owner's staged-node,
staged-byte, inspection, and failure totals with
`expect-image-owner-counters`. These are numeric work counters only. Image
names, paths, encoded values, dimensions, and rendered application text are not
capture evidence.

An adjacent `app-data-fixture/` grants a fresh private copy through
`--host-cap-app-data` for each case, so writes use the production capability
without mutating checked-in data. A subdirectory named after the spec selects
case-specific initial state; otherwise `default/` is used. Neither the granted
path nor preference contents become capture identity.

`expect-file-selection-counters` compares seven host-owned numeric totals in
order: portal requests, chosen results, cancellations, denials, unavailable
results, suppressed prompts, and development provisions. The evidence contains
no selected name, path, URI, or application text.

`revoke-file-grants` invokes the trusted-host revocation seam; it is not an
application event or Roc capability API. `expect-file-access` compares portal,
provisioned, and revoked root counts. `expect-file-lifecycle-counters` compares
root allocations, child allocations, live handles, revocation requests,
successful revocations, and post-revocation operation rejections. All are
numeric owner evidence without internal root identifiers.

The Settings Center's 100-, 1,000-, and 10,000-byte profile-note cases exercise
ordinary controlled editing followed by the same worker-backed atomic save used
by the application. `expect-value-bytes` supplies deterministic, content-free
scale evidence; task and patch counters remain owned by their production paths.

Generic per-case fixture metadata may name a loopback server script, readiness
port, and exact HTTP origin or TCP endpoint. The runner starts only services
selected by that metadata, while applications use their production protocol
packages, capabilities, worker pools, and completion routes. This avoids
public-network availability and remote service state without introducing a
test-only network path or application-name policy.

A `process-fixture/SPEC_NAME` file containing `test-program` grants the fixed
deterministic PTY child to that case through `--host-cap-process`. Cases without
the file receive no process authority, which exercises denial without adding a
test-only product control. The application uses the same `New terminal` action
for both outcomes.

A `device-fixture/SPEC_NAME` file grants a deterministic virtual HID device to
that case through the same host capability used for physical hardware. An
optional bounded control count selects the device model's ordinary capability
size. The product performs the same discover, connect, and byte transaction
operations for both transports; cases without a fixture exercise denial through
the normal `Discover devices` action.

A `system-monitor-fixture/SPEC_NAME` file grants a deterministic system sampler
through the same snapshot ABI used by the physical `sysinfo` source. Its value
is `standard`, `unavailable`, or `processes:N`; this is runner metadata, not an
application switch. Cases without the file exercise permission denial through
the ordinary `Resume sampling` action.

An adjacent `audio-fixture` file containing `null` grants a paced null output
to that application's cases. The harness-only grant is not advertised as a
product option; it changes only the final sink while Rodio retains ownership of
the production decoder, mixer, player, seeking, and status state. The
`expect-audio-counters` assertion records live outputs, live tracks, and the
seven operation-attempt counters as deterministic step evidence.

Native file and clipboard fixtures are selected by `fixture-metadata/SPEC_NAME`.
Each `directory=RELATIVE_PATH` or `clipboard=RELATIVE_PATH` entry grants that
adjacent directory to the corresponding production capability. The metadata is
generic to the harness and does not depend on an application directory name.
Either value may be `none` to exercise denial through the same production
acquisition call.

== Locators

`(text "value")`:: Text whose entire value equals `value`.
`(text-prefix "prefix")`:: Text beginning with `prefix`.
`(checkbox-prefix "prefix")`:: Checkbox labels beginning with `prefix`.
`(button-prefix "prefix")`:: Button names beginning with `prefix`.
`(role button :name "name")`:: A button with the semantic `name` passed to
`Elem.button` or `Elem.action_button`.
`(role checkbox :name "label")`:: A checkbox identified by its visible label.
`(role panel :name "label")`:: A panel identified by its semantic label.
`(role dialog :name "label")`:: The active modal dialog identified by its
semantic label.
`(role scroll :name "name")`:: A scroll region identified by its semantic name.
`(role virtual-list :name "name")`:: A fixed-row virtual list identified by its
semantic name.
`(role textarea :name "name")`:: A multiline editor identified by its semantic
name. Locator matching never records its value.
`(role image :name "name")`:: An encoded image identified by its application
supplied semantic name. Neither encoded bytes nor source filenames are captured.
`(role canvas :name "name")`:: A retained drawing surface identified by its
stable semantic name.
`(role canvas-item :name "name")`:: A keyed canvas primitive identified by its
stable semantic label.

`(role textbox :name "label")`:: A controlled text input identified by its
semantic label.

An interaction locator must resolve to exactly one live node. Ambiguous and
missing targets fail instead of choosing one by traversal order. Make button
names unique wherever the buttons are visible together.

== Assertions and operations

`(click LOCATOR)`:: Press exactly one matching enabled control through the
application's normal Roc event route. A disabled control consumes no event and
does not call Roc, matching the interactive host.
`(drag LOCATOR FROM-X FROM-Y TO-X TO-Y)`:: Send one complete captured pointer
gesture through a canvas's production event route. Coordinates are integer
logical pixels in canvas space. `(canvas-item-prefix "prefix")` supports
deterministic primitive counts in scaling specifications.
`(expect-canvas-primitives LOCATOR COUNT)`:: Require one canvas owner to report
the exact retained primitive count. The expected and observed values are stored
as deterministic scale evidence.
`(replace-text LOCATOR "value")`:: Replace an editable textarea's controlled
value through its production Roc input route. Disabled and read-only textareas
fail as non-editable.
`(focus LOCATOR)`:: Give semantic keyboard focus to exactly one enabled button
or checkbox. Focus remains valid only while that mounted node is live.
`(press-key Enter)`:: Activate the focused button through the normal Roc event
route.
`(press-key Space)`:: Activate the focused button or toggle the focused enabled
checkbox through the normal Roc event route.
`(press-key Escape)`:: Dismiss the active dialog through its `on_dismiss` route.
`(replace-text LOCATOR "value")`:: Replace an enabled text input's complete
value and deliver `Event.TextChange` through the normal Roc event route. A
disabled input consumes no edit and dispatches nothing.
`(submit LOCATOR)`:: Deliver an enabled text input's current controlled value as
`Event.TextSubmit` through the normal Roc event route.
`(clipboard-text "value")`:: Change the clipboard source granted to a semantic
fixture. This command is rejected without an explicit fixture grant. The next
application timer pull observes it through the production capability and host
read route; the value is neither copied into capture evidence nor emitted as a
diagnostic.
`(expect-clipboard-counters LIVE ACQUIRE READ WRITE)`:: Assert the owner-recorded
live handle count and attempted Clipboard operations.
`(expect-sqlite-counters LIVE OPEN QUERY)`:: Assert the owner-recorded live
connection count and attempted SQLite operations.
`(expect-http-counters LIVE ACQUIRE SEND DENIED)`:: Assert the owner-recorded
live client count, operation attempts, and authority denials.
`(await-task)`:: Wait for exactly one accepted worker task and apply its
completion through the normal latest-state route. A task that resolves to
another task requires another `await-task` step.
`(await-ticks N)`:: Apply `N` successive timer wait completions through that
same worker and latest-state route. `N` must be positive.
`(expect-subscriptions N)`:: Require exactly `N` active host timer handles.
This assertion reads the timer registry that owns cancellation state.
`(expect-tcp-streams N)`:: Require exactly `N` live host TCP stream handles.
`(expect-tcp-counters LIVE CONNECT READ WRITE CLOSE)`:: Assert the complete
owner-recorded TCP resource and attempted-operation vector.
`(expect-device-connections N)`:: Require exactly `N` host-owned device connection handles.
`(expect-device-transactions N)`:: Require exactly `N` completed host-owned device transactions.
`(expect-system-samplers N)`:: Require exactly `N` active host-owned system samplers.
`(expect-system-samples N)`:: Require exactly `N` completed host-owned system samples.
This assertion reads the capability registry that owns stream lifecycle and
records expected and observed deterministic counts.
`(expect-file-picks N)`, `(expect-file-lists N)`, `(expect-file-opens N)`, and
`(expect-file-reads N)`:: Require exact cumulative counts recorded by the Files
owner. Each scalar assertion preserves its expected and observed value in the
ordinary deterministic step evidence.
`(expect-visible LOCATOR)`:: Require at least one match.
`(expect-focused LOCATOR)`:: Require semantic focus to be on exactly one
matching enabled control. This proves the host's dialog focus policy, not a
compositor-delivered focus event.
`(expect-not-visible LOCATOR)`:: Require no matches.
`(expect-count LOCATOR N)`:: Require exactly `N` matches and record expected and
observed counts.
`(expect-value LOCATOR "value")`:: Require an exact controlled textarea value.
The value is compared in memory and is not copied into captures or diagnostics.
`(expect-value-bytes LOCATOR N)`:: Require the textarea value to contain exactly
`N` UTF-8 bytes and record the expected and observed deterministic counts.
`(expect-image-bytes LOCATOR N)`:: Require an image node to own exactly `N`
encoded bytes and record expected and observed deterministic counts without
persisting image content.
`(expect-before FIRST SECOND)`:: Require a match for `FIRST` to occur before a
match for `SECOND` in mounted-tree order.
`(expect-patch :kind KIND :staged N :removed N)`:: Check the host patch produced
by the preceding click. `KIND` is `mount`, `replace`, or `no_change`.
`(mark-metrics)`:: Separate benchmark setup from the operation being measured.

Prefer semantic results—visible text, counts, and order—for application
behaviour. Use `expect-patch` when the amount or absence of host work is itself
part of the contract, such as proving that an idempotent press returns
`no_change` and stages no nodes.

The runner queries the same mounted graph the native host uses. It does not
construct a separate test tree. Because it does not open a GPUI window, it is
suited to deterministic semantic checks; pixels, layout, and presentation are
outside this runner's evidence. Those claims belong to the window runner
described in <<window-specifications>>.

For a virtual list, text and control locators inspect all logically mounted
items, including rows outside an interactive viewport. A headless
`expect-visible` therefore proves logical presence, not viewport intersection;
native visible-range and materialization evidence is recorded only by GPUI.

`focus` and `press-key` model the production controls' accepted activation-key
matrix and invoke their normal Roc event route. In the semantic runner they do
not inject a native GPUI key event or verify compositor delivery, tab traversal,
focus painting, or operating-system accessibility.

Named rows and columns use `(role row :name "...")` and
`(role column :name "...")`. These locators describe the mounted application
graph; they do not assert pixel geometry or operating-system accessibility.

`(expect-processes N)` asserts the host-owned count of live PTY child
processes. The process subsystem records this lifecycle evidence.

== Window specifications

A window specification is an ordinary `(test ...)` file that uses window-only
steps. It lives in `examples/<app>/window-specs/` rather than
`examples/<app>/specs/`, and `scripts/run_window_specs.py` runs it:

[source,sh]
----
python3 scripts/run_window_specs.py 'examples/counter/window-specs/*.scm'
----

Each case runs one host process with `--host-run-window-spec`. That process
opens the production GPUI window, drives it through the same render path and
event route an interactive session uses, and writes a JSON report the running
agent can read.

=== One vocabulary, split by capability

There is one specification language. Every step declares where it can be
honest, and each runner refuses the other's steps by name rather than skipping
them silently:

`semantic-only`:: `mark-metrics`, `expect-patch`, and `benchmark` clauses.
These depend on the semantic runner's per-iteration mount; the window runner
runs exactly one lifecycle and does not measure it.

`window-only`:: `settle`, `screenshot`, `type`, `key`, `expect-on-screen`,
`expect-rendered-count`, and `expect-bounds`. None of these mean anything
without a presented frame.

`both`:: everything else, including `expect-visible`, which asserts the same
claim on either runner: presence in the mounted graph. The stronger pixel claim
is `expect-on-screen`, so one word never means two different things.

=== Window-only steps

`(type "TEXT")`:: Send each character as a real keystroke into the focused
element, through GPUI's own keystroke dispatch. The semantic `replace-text`
sets a value directly and exercises none of the editing path.

`(key "CHORD")`:: Send one real chord, such as `"cmd-a"` or `"escape"`, through
the window's production keymap. The semantic `press-key` covers three
activation keys and no modifiers.

`(settle)` / `(settle :frames N :timeout-ms N)`:: Wait for `N` consecutive
presented frames during which no host task started or finished. Defaults are
`:frames 2 :timeout-ms 2000`. A timeout fails the step; it never proceeds
quietly, because an assertion against a half-settled frame is not evidence.

`(expect-on-screen LOCATOR)`:: The node was painted in the last completed frame
and its rectangle survives clipping by the viewport and by every scrolling
ancestor. This is the claim the semantic runner cannot make.

`(expect-rendered-count LOCATOR N)`:: Exactly `N` matching nodes took part in
the last frame. For a virtual list this is materialization evidence;
`expect-count` counts logically mounted nodes instead.

`(expect-bounds LOCATOR :min-width N :max-width N :min-height N :max-height N)`::
The laid-out size falls within the given bounds. At least one bound is
required. Deliberately minimum and maximum only, never exact: exact pixel
geometry is font- and DPI-dependent and would rot the suite.

=== Screenshots

`(screenshot NAME)`:: Photograph the window's content area.

`(screenshot NAME :region LOCATOR)`:: Crop to a located element's laid-out
bounds. The same bounds `expect-on-screen` uses, so a shot frames what was
asserted.

`(screenshot NAME :region (rect X Y WIDTH HEIGHT))`:: Crop to an explicit
content-relative rectangle.

`:pad N`:: Expand the region by `N` points on every side, then clamp to the
content area. A control cropped to its exact bounds is usually unreadable out
of context.

`NAME` is required and becomes the file stem, so it is limited to lowercase
letters, digits, and hyphens. Files are written as `NN-NAME.png`, numbered by
step, and indexed in the report's `screenshots` array. A `:region` locator that
does not match exactly one node fails the step, as `click` does.

The host asks the platform's capture tool for a screen rectangle, which it can
compute because it knows its own window origin and where each node was laid
out. Cropping is therefore part of the request rather than a post-processing
step. On macOS this is `screencapture`; under a wlroots compositor it is
`grim`.

Capture is honest about not happening. A missing tool, a denied Screen
Recording permission, or a region with no area on screen is reported as
`unavailable` with a reason and a hint, never as a pass and never as an empty
file. By default an unavailable screenshot fails the run;
`--host-window-allow-missing-shots` downgrades it to a report entry, which is
how continuous integration runs these specifications on machines that cannot
grant screen recording. Every behavioural assertion still gates there.

Screenshots taken before a failing step are kept. The image of the state an
assertion stopped at is usually the most useful evidence in the run.

=== What input is real

Keyboard input is real. `focus` moves focus through the same `FocusHandle` the
host uses, `press-key`, `key`, and `type` reach GPUI's `dispatch_keystroke` and
the window's production keymap, and `expect-focused` asks the focus handle
rather than a model of it.

Pointer input is simulated, because GPUI 0.2.2 exposes no usable entry point
for it: `Window::dispatch_event` returns a crate-private type and cannot be
called from outside GPUI, and every simulated-mouse helper lives on
`TestAppContext` behind `test-support`. A `click` therefore invokes the same
handler the production click closure invokes.

What is *not* simulated is whether the click could have landed. Before
dispatching, the window runner requires from real laid-out geometry that the
control:

* has been laid out, not merely mounted;
* survives clipping by the viewport and by every scrolling ancestor;
* accepts pointer activation, which the production render path grants only to
  enabled controls;
* is not behind an active modal dialog.

This is strictly stronger than a semantic `click`, which cannot tell that a
control is scrolled out of view or was never laid out. It does not exercise
GPUI's dispatch tree, occlusion by unrelated elements, or the click closure's
own wiring. There is no `hover` step for the same reason: hover styling is
driven by GPUI's internal pointer position, and a step that could not honestly
move it would not mean what its name says.

=== What the probe cannot see

Bounds come from the production render path, through the same `canvas` prepaint
closure the host already uses for canvas hit testing. Recording is off unless a
window specification asked for it, gated by a runtime check rather than a
compile-time one, so the shipped binary stays the tested binary.

* A node that never renders has no bounds. That is the intended signal rather
  than a gap: an unmaterialized virtual-list row is genuinely absent from the
  frame.
* Only a canvas node's own rectangle is recorded, never its primitives. A
  canvas-item locator therefore has no geometry of its own.
* Bounds are recorded for nodes scrolled out of view, because they are laid
  out and merely clipped. `expect-on-screen` intersects against scrolling
  ancestors for this reason; asking only whether bounds exist would call a
  clipped element visible.

Bounds persist until a node leaves the mounted graph. GPUI caches views, so a
control whose state did not change is not re-rendered and records nothing that
frame; treating that as "not laid out" would report a plainly visible control
as missing. `expect-rendered-count` therefore counts nodes that have been laid
out while mounted, which is the materialization evidence a virtual list needs.

=== Reports are not captures

A window run writes `report.json` into `.test-out/`. It is deliberately not a
`.rgstats` capture and never becomes one. The two carry different kinds of
fact:

* A capture is durable, archived, and privacy-clean. It records that a step ran
  and its status, and never application text, paths, or pixels.
* A report is ephemeral working evidence for whoever is iterating, and it
  carries exactly what a capture must not: the failing locator as written, the
  message, and the screenshots.

For the same reason screenshots are written beside the report in `.test-out/`
and never into a capture.

== Selecting and repeating cases

Patterns match repository-relative specification paths. Multiple patterns may
be supplied. Compatible released hosts are verified and staged automatically.
Use `--skip-host-build` only to reuse an already staged local host while
iterating:

[source,sh]
----
python3 scripts/run_specs.py \
  'benchmarks/rows/specs/create-*.scm' \
  'benchmarks/rows/specs/append-*.scm' \
  --skip-host-build
----

The default is one case at a time. `--jobs N` runs cases concurrently, which is
useful for semantic validation but marks timing-environment evidence partial.
Use serial runs for performance comparisons. `--aa` repeats each passing case
with the same executable to show run-to-run noise.
