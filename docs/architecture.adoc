= How Roc GUI works

This chapter is the map of roc-gui for advanced users and contributors. It
explains the path from application state to pixels, the path from input back to
state, and the replacement model that joins them. You do not need to know GPUI
internals to follow it.

The crucial detail is that roc-gui does not diff two virtual trees. An update
renders and replaces one explicit state-boundary subtree with fresh node IDs
and GPUI entities. Nodes and entities outside that boundary remain mounted.

== The model in one page

roc-gui has three representations of a UI:

`Elem` value:: A short-lived Roc description produced by a renderer. It carries
text, layout, buttons, checkboxes, controlled text inputs, handlers, and
explicit local-state boundaries.
Mounted graph:: The host's canonical, validated tree of native nodes. It is the
source of truth shared by the interactive window and semantic specs.
GPUI entities:: Retained native views materialised from mounted nodes. GPUI uses
them to perform its rendering-system work and deliver input.

[mermaid]
....
flowchart TB
    A["Roc state"] --> B["render"]
    B --> C["Elem tree"]
    C --> D["platform lowering"]
    D --> E["staged native nodes"]
    E --> F["validated patch"]
    F --> G["mounted graph"]
    G --> H["GPUI entities"]
    H --> I["layout, paint, presentation"]
    I --> J["input: node ID"]
    J --> K["Roc event handler"]
    K --> L["NoChange or Update"]
    L --> D
....

The application never mutates the mounted graph or GPUI entities directly. It
returns an `Action`; the platform turns that action into exactly one patch; and
the host applies it through the same graph implementation in every GUI host and
the built-in test runner.

== From state to pixels

=== The application renders a value

`Program.run` supplies an initial state, a renderer, and initial resizable-window
metadata. Calling the renderer
produces an immutable `Elem(State)` description. Composition stays in Roc:
styled and semantically named `Elem.row`, `Elem.col`, `Elem.panel`,
`Elem.text`, `Elem.action_button`, and named
`Elem.scroll` regions build the tree, while
`Elem.translate` introduces a local-state boundary.

An `Elem` is not a long-lived widget object, and rendering one does not draw
pixels. It is an intermediate value consumed immediately by platform lowering.
The application renderer runs initially and after an updating event; it does
not run for every display frame.

=== The platform lowers the description

The platform lowers the `Elem` description into native nodes with host-issued
identities. The result is staged separately from the visible graph so it can be
validated as a complete change before commit.

During the same walk, the platform builds an event route for every action button and
records each state boundary's renderer, native root, and parent boundary. A
route connects a semantic button name and native node ID to a Roc handler and
the boundary that owns its update.

Lowering ends with exactly one `Mount`, `Replace`, or `NoChange` commit. Staging
alone cannot modify the visible graph.

=== The host validates and commits

The host validates a staged tree before accepting it. References and ownership
must be internally consistent, the result must describe one valid tree, and a
replacement target must still belong to the mounted graph.

The canonical `MountedGraph` then applies the patch:

* `Mount` installs the first root.
* `NoChange` leaves the graph untouched.
* `Replace` atomically substitutes a new subtree for a mounted one.

Node IDs increase for the lifetime of the process. An ID removed by replacement
is stale and cannot later identify another control.

=== The host materialises GPUI views

Ordinary newly mounted graph nodes become GPUI `Entity<NodeView>` values. Rows
and columns become flex containers, panels become styled surfaces, dialogs
become centered modal layers with input-blocking scrims, text becomes
a text child, and enabled action buttons add focus, keyboard, and pointer
listeners. Disabled action buttons add no event listener or tab stop. Text input
entities retain native focus, caret, selection, and IME preedit state while
committed values cross the same controlled Roc replacement boundary. IME
preedit remains transient in the editor and dispatches one change when the
composition commits. A virtual
list is the deliberate exception: its
complete keyed item subtrees remain in the canonical graph, but GPUI's
viewport callback creates entities only for intersecting fixed-height rows and
recycles entities that leave the range. The host connects the new native
subtree to retained entities around its boundary and releases replaced views.

While a dialog is mounted, controls outside its graph subtree do not install
pointer listeners or tab stops. The runtime focuses the first enabled dialog
control, routes Escape to the dialog node, and restores the opener by its stable
role and semantic name after the dialog leaves the graph.

The host notifies GPUI of the changed entity. GPUI owns subsequent rendering,
layout, prepaint, paint, and presentation. roc-gui does not calculate geometry
or issue GPU commands in Roc, and one application event does not necessarily
correspond to one presented frame.

== One event turn

[mermaid]
....
sequenceDiagram
    participant U as User or spec
    participant G as GPUI or semantic locator
    participant H as Host
    participant P as Roc dispatcher
    participant A as App handler

    U->>G: activate or edit a named control
    G->>H: live node ID and private event payload
    H->>P: dispatch(node ID)
    P->>A: handler(current state, event)
    A-->>P: Action
    alt NoChange
        P->>H: commit NoChange
    else Update(next state)
        P->>P: render and lower owning boundary
        P->>H: commit Replace(old root, new root)
        H->>H: validate and splice graph
        H->>G: materialise and notify entities
    end
    P->>H: install next dispatcher
....

The dispatcher is one-shot state: each turn captures the state, routes, and
boundaries valid for that mounted graph, then installs its successor. Thus a
later event cannot accidentally run a handler against an old state snapshot.
The interactive host also checks that an ID still names a live button before
dispatch. A delayed callback for a removed button cannot reach Roc.

== Boundaries determine update scope

`Elem.translate(render_child, get_child, set_child)` adapts a child component's
handlers to parent state and creates a replacement boundary around its renderer.
The application renderer itself is the root boundary.

When a button returns `Update`, the platform selects the boundary recorded for
that button. It renders that boundary with the next application state and
replaces only its native subtree. Routes and nested boundaries inside the old
subtree are discarded and rebuilt; those elsewhere are retained.

[mermaid]
....
flowchart LR
    subgraph before["Before update"]
        P1["retained parent"] --> S1["retained sibling"]
        P1 --> O["old boundary subtree"]
    end
    subgraph after["After update"]
        P2["same parent"] --> S2["same sibling"]
        P2 --> N["fresh boundary subtree"]
    end
    before -->|"one Replace patch"| after
....

For example, two translated counters may share a parent state record. Clicking
the left counter replaces the left counter subtree. A heading and the right
counter retain their mounted nodes, routes, and GPUI entities. Without an inner
boundary, the button belongs to the root boundary and the complete application
subtree is replaced.

Boundaries affect both composition and cost. Put them around state that can
update independently, but do not treat one as a cache: its complete subtree is
rendered and lowered afresh for every `Update` it owns. `Action.none` is the
only handler result that stages no tree and mutates no graph or GPUI entity.

== Asynchronous action turns

An `Action.task` first replaces its owning boundary with the declared pending
state. The host then accepts the boxed task into one unbounded queue serviced by
between four and sixteen native workers. A worker returns a boxed reducer, not
a state snapshot. The UI thread applies that reducer through the latest
installed task dispatcher, renders the root boundary, commits one ordinary
patch, and installs successor dispatchers. Roc values cross threads only as
owned erased callables; generic state and actions remain boxed across the ABI.

Periodic subscriptions use the same route. A timer has at most one waiting
`Timer.next!` task. Its wait parks on a worker and returns a normal boxed
reducer; the UI thread applies that reducer with the installed task dispatcher.
Cancellation wakes the waiter, and cadence advances from the completion of the
preceding pull, so a slow consumer cannot create an unbounded event backlog.

HTTP requests also use `Action.task` and the canonical worker/completion route.
An opaque `Box(U64)` client names a host registry entry for one explicitly
granted origin. The initial URL and every redirect retain its scheme, host, and
effective port.
The host applies explicit scheme, timeout, redirect, header, request-body, and
response-body limits before returning an owned reducer to the UI thread. It
buffers one bounded byte response rather than exposing a streaming callback.
Applications suppress obsolete completions by comparing their request identity
with latest state. URLs, headers, bodies, and response text never enter host
captures or deterministic diagnostics.

Directory, HTTP, and timer handles are typed nominal wrappers over `Box(U64)`. Each token names
a host registry entry containing a `cap_std::fs::Dir`; final box deallocation
removes that entry. The phantom resource kind leaves room for other handle
families without allowing their types to be confused. Ambient filesystem
authority is used only to create the explicit
`--host-cap-dir` grant. Listing and child acquisition operate relative to the
stored handle, and child acquisition uses the no-follow operation from
`cap-fs-ext`.

== There is no node-level diff

roc-gui does not compare old and new descriptions, reconcile keyed siblings,
or mutate equivalent nodes in place. Every node inside an updating boundary is
new even if its text and position are unchanged. Retained identity stops at the
boundary's surroundings.

This makes the costs and semantics direct:

* the boundary structure exposes replacement and invalidation scope;
* there is no hidden key contract or reconciliation heuristic;
* removed routes and node IDs become unambiguously stale; and
* large boundaries incur rendering, lowering, validation, materialisation, and
  removal work proportional to the update shape.

The scaling suite exercises full-root collections, local boundaries, text
density, tree depth, and tree breadth so the consequences of replacement scope
remain visible as the implementation evolves.

== How this compares

[cols="1,2,2,2",options="header"]
|===
|Model |What persists |How application changes arrive |Identity on update

|roc-gui
|Mounted graph and GPUI entities outside the updated boundary
|A state-derived `Elem` subtree becomes one replacement patch
|Fresh IDs inside the boundary; retained IDs outside it

|Virtual-tree reconciliation
|A native/render tree, often plus a previous description
|Old and new descriptions are diffed, commonly using keys
|The reconciler may preserve matching nodes

|Immediate mode
|Rendering-system state rather than an application widget tree
|Application code describes the interface repeatedly, commonly each frame
|Usually not expressed as persistent application widget identity

|Traditional retained widgets
|Application-visible widget objects
|Application code mutates long-lived widget properties and children
|Widget objects ordinarily retain identity until explicitly removed
|===

roc-gui combines a declarative Roc front end with retained native state. It is
not immediate mode because the application does not redraw the interface every
frame. It is not virtual-DOM reconciliation because replacement boundaries,
not a diff algorithm, choose what survives. GPUI may perform its own internal
rendering invalidation; that is separate from roc-gui's application graph
replacement model.

== Semantic tests use the production graph

The built-in `.scm` runner stops after the mounted-graph layer because it needs
no display server to locate semantic controls or assert text. It invokes the
real Roc renderer and dispatcher, consumes the real patches, and uses the same
`MountedGraph` implementation for validation, replacement, event routing, and
node accounting. It does not reproduce those behaviours in a test-only graph.

The interactive host continues by materialising GPUI entities. Consequently,
semantic specs prove application behaviour and mounted topology, but do not
exercise `NodeView`, display frames, layout, paint, GPU work, or presentation.
Those require the interactive production path.

== Threading and observability

Application callbacks, graph commits, GPUI entity updates, and window work stay
on the interactive application path. With recording disabled, observatory work
is kept out of that path apart from the inexpensive enablement check.

With recording enabled, work owners emit bounded records. A separate writer
thread drains them in batches and commits transactions to the `.rgstats` SQLite
capture. UI behaviour never waits for a report query. If the recorder cannot
accept evidence, the capture records that loss rather than presenting partial
data as complete.

A timer means only the phase that owns it. Host application timing is not a
substitute for later layout, paint, GPU execution, or presentation. See
<<_understanding_captures>> for availability and report views and
<<_measuring_scaling>> for representative workloads.

== Correctness boundaries

The platform and host maintain these invariants across every event turn:

* one initial mount and one canonical mounted root;
* one completed action and graph decision per dispatch;
* unambiguous native identity for every live node;
* structurally valid changes applied only to mounted targets;
* routes and boundaries rebuilt whenever their owning subtree is replaced; and
* mounted-graph commit before GPUI materialisation.

A malformed ABI value or structurally invalid patch is a platform defect, not
application input to recover from. The host rejects it at the ownership
boundary rather than displaying a partially mutated graph.

Rows and columns stream their lowered child identities into nesting-safe,
host-owned builders. The closing node effect consumes its builder and stages
the same ordered graph node used everywhere else. This ownership boundary
avoids allocating a temporary Roc child-identity list and then copying it into
host storage. A patch cannot commit while a child builder remains unfinished,
and builders must close in nesting order.

== Responsibilities when extending the platform

[cols="2,4",options="header"]
|===

|Roc platform

|Lowering, routes, boundaries, and dispatcher succession
|Roc platform

|Hosted effects and ABI ownership
|Platform and Rust host boundary

|Canonical graph, patch validation, and accounting
|Host graph

|Native appearance, click input, and entity materialisation
|GPUI host

|Tab order, visible focus, and Enter/Space control activation
|GPUI host over the canonical button and checkbox nodes

|Headless semantic driving and locators
|Host runner using production structures

|Capture lifecycle, batching, SQLite schema, and reports

A new feature crosses every owner it needs: public API, lowering and ABI, graph
representation and validation, GPUI behaviour, semantic locators and specs,
scaling coverage, and documentation. The governing rule is one mounted graph,
one event route, and one production path: tests and measurements drive those
structures; they do not imitate them.
