= Contributing

Read `AGENTS.md` before changing the platform. The central constraint is “test
what we fly”: tests and measurements drive the production implementation and
never reproduce it.

== Validate a change

[source,sh]
----
python3 scripts/run_cargo.py test --locked --package roc-gui-host
roc check examples/counter/main.roc
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
----

The specification runner verifies and stages the independently released native
host when its recorded source fingerprint matches the checkout. A host-source
change automatically builds and exercises the changed production host instead.

Run the affected benchmark family when a change touches rendering, routing,
graph work, allocation, recording, or a scaling-sensitive data structure. Run
the complete specification suite before integrating a cross-cutting change.

When changing an effect, update `wip/resource-access-inventory.md` after reading
the public API, hosted ABI, native owner, configuration source, and verifying
specifications. Mark missing enforcement or evidence `Unverified`; never infer security
from an absent public function or an opaque Roc type.

== Complete a platform feature

A new element, property, event, or state mechanism is complete when it has:

. a Roc API and hosted ABI representation;
. behaviour in the single host graph and GPUI path;
. semantic locators, operations, and assertions where users need to observe it;
. deterministic counters and timing spans recorded by the work owner;
. behaviour, ambiguity, and failure specifications;
. a realistic scaling case for every dimension that can grow;
. focused SQLite reporting for evidence that production code populates;
. application-facing documentation.

A resource feature additionally requires trusted authorisation, OS-enforced
scope, derivation and lifetime rules, revocation semantics, privacy review, and
platform-boundary tests. The Resource access and trusted grants chapter
describes them.

Exercise recorder-disabled, enabled, saturated, output-limited, interrupted,
and writer-failure paths when changing capture infrastructure. Timing is not a
correctness assertion.

== Fixtures for this repository's examples

`scripts/run_specs.py` wires the specifications in this repository to
deterministic fixtures, so a case exercises a real capability without depending
on the machine it runs on. Fixture directories sit beside the application and
are keyed by specification name, which is why specification names are unique
within an application. Every grant crosses the production capability boundary;
none of them gives an application ambient test-only I/O.

=== Fixture sources

An adjacent `fixture/` directory:: The runner grants the directory through the
production `--host-cap-dir` boundary, so its contents are reached through the
same opaque capability operations as an interactive grant.
An adjacent `app-data-fixture/` directory:: Each case receives a fresh private
copy through `--host-cap-app-data`, so writes use the production capability
without mutating checked-in data. A subdirectory named after the specification
selects case-specific initial state; otherwise `default/` is used. Neither the
granted path nor preference contents become capture identity.
An adjacent `audio-fixture` file containing `null`:: The application's cases
receive a paced null output. This harness-only grant is not advertised as a
product option; it changes only the final sink, while Rodio retains ownership
of the production decoder, mixer, player, seeking, and status state.
`device-fixture/SPEC_NAME`:: The case receives a deterministic virtual HID
device through the same host capability used for physical hardware. An optional
bounded control count selects the device model's ordinary capability size. The
product performs the same discover, connect, and byte transaction operations
for both transports. A case without the file exercises denial through the
ordinary `Discover devices` action.
`fixture-metadata/SPEC_NAME`:: Each `directory=RELATIVE_PATH` or
`clipboard=RELATIVE_PATH` entry grants that adjacent directory to the
corresponding production capability. The metadata is generic to the harness and
does not depend on an application directory name. Either value may be `none` to
exercise denial through the same production acquisition call. Per-case metadata
may also name a loopback server script, readiness port, and exact HTTP origin
or TCP endpoint; the runner starts only the services that metadata selects,
while applications use their production protocol packages, capabilities, worker
pools, and completion routes. This avoids depending on public-network
availability and remote service state without introducing a test-only network
path or an application-name policy.
`process-fixture/SPEC_NAME` containing `test-program`:: The case receives the
fixed deterministic PTY child through `--host-cap-process`. A case without the
file receives no process authority, which exercises denial without adding a
test-only product control. The application uses the same `New terminal` action
for both outcomes.
`system-monitor-fixture/SPEC_NAME`:: The case receives a deterministic system
sampler through the same snapshot ABI used by the physical `sysinfo` source.
Its value is `standard`, `unavailable`, or `processes:N`; this is runner
metadata, not an application switch. A case without the file exercises
permission denial through the ordinary `Resume sampling` action.

=== Fixture-backed assertions

These steps are available to any specification, and this repository's fixtures
are what make their counts deterministic. All of them are numeric owner
evidence: no name, path, URI, identifier, or application text is recorded.

`expect-audio-counters`:: Live outputs, live tracks, and the seven
operation-attempt counters.
`expect-file-access`:: Portal, provisioned, and revoked root counts.
`expect-file-lifecycle-counters`:: Root allocations, child allocations, live
handles, revocation requests, successful revocations, and post-revocation
operation rejections.
`expect-file-selection-counters`:: Seven host-owned totals, in order: portal
requests, chosen results, cancellations, denials, unavailable results,
suppressed prompts, and development provisions.
`expect-image-owner-counters`:: The production image-data owner's staged-node,
staged-byte, inspection, and failure totals. Image names, paths, encoded
values, and dimensions are not capture evidence.
`revoke-file-grants`:: Invokes the trusted-host revocation seam. It is not an
application event or a Roc capability API.

The Settings Center's 100-, 1,000-, and 10,000-byte profile-note cases exercise
ordinary controlled editing followed by the same worker-backed atomic save the
application uses. `expect-value-bytes` supplies deterministic, content-free
scale evidence; task and patch counters remain owned by their production paths.

== Generated bindings

Regenerate checked-in Roc ABI bindings whenever hosted functions or
`platform/Host.roc` change:

[source,sh]
----
python3 scripts/regenerate_glue.py /path/to/roc
----

`platform/main-glue.roc` is an ABI-generation root. Applications build against
`platform/main.roc`.

== Documentation

AsciiDoc sources live in `docs/`; `docs/index.adoc` is the complete book. Build
the HTML site with:

[source,sh]
----
python3 scripts/build_docs.py
----

Build the standalone PDF as well with `python3 scripts/build_docs.py --pdf`.
Docker supplies the pinned Asciidoctor, diagram, PDF, Mermaid, and syntax
highlighting toolchain; only Python and Docker are required on the host. Output
is written beneath `.docs-out/`.

Documentation describes the product and its enduring contracts. Put defects,
missing capabilities, and implementation tasks in `wip/issues-backlog.md`, then
remove entries when they are resolved.

== Native linker inputs and releases

Generated objects, libraries, TBD files, host archives, and platform bundles do
not belong in Git. Reviewed recipes, catalogs, provenance, locks, and license
texts do.

Native artifacts have three independent release layers:

. External linker-input producers build one independently versioned dependency
  from pinned sources or a reviewed system-library interface catalogue.
. Host producers build `libhost.a` for each target and bind it to the exact host
  source, Cargo lock, configuration, profile, and toolchain inputs.
. Platform release assembly admits released external and host inputs, runs the
  supported consumer matrix, and publishes those same tested bytes under Roc's
  content-addressed bundle name.

Producer releases and consumer adoption are separate reviews. A producer
workflow publishes a deterministic archive, complete inventory, licenses and
reproduction material, and signed build-provenance attestation. It creates the
release as a draft, verifies the tag and complete asset inventory, and then
publishes it immutably. The consumer lock records the release, target, digest,
size, source revision, signer workflow, and source fingerprint.

Consumers verify locked bytes before extraction and on cache hits. A digest,
size, manifest, target, provenance, or attestation mismatch is a hard failure and
must never fall back to a local build. Developers may explicitly select a native
source build when an artifact is absent or its source fingerprint is stale.
Final platform releases accept only locked, released, and attested inputs.

Change an external input through its owning recipe and tests. Publish it from the
default branch, then adopt the generated lock candidate in a separate review.
Ordinary platform and host changes reuse existing dependency releases.

=== Generated system-library interfaces

When an application links to a library supplied by the target environment, its
producer emits only the reviewed symbols and the runtime library's stable name.
The archive does not contain an implementation or an absolute provider path.
Production verifies the exact exported symbol inventory and stable library name,
links a probe through the generated interface, and runs that probe against a
native provider. The release carries the interface recipe, probe, producer, and
archive verification inputs needed to reproduce it.

The target system or package environment supplies the implementation at runtime.
This keeps linker inputs independent of a distribution's filesystem layout while
preserving normal runtime library resolution.

=== Generated macOS interfaces

Read `dependencies/macos-interfaces/README.md` and `PROVENANCE.md` before changing
the macOS catalogue. No Apple SDK binary, header, TBD, framework binary, dylib,
object file, symbol table, generated SDK metadata, or other installed macOS
software may supply interface data.

The project-built `libhost.a` may be inspected only to inventory unresolved
references. That inventory does not establish library ownership, public API
status, weak-link behaviour, or final-link reachability and never populates the
catalogue automatically. Every selected symbol and owning library requires reviewed
public documentation or identified public open-source evidence. Prefix-based
classification and installed system artifacts do not establish library ownership.

Generation is deterministic and offline from the reviewed catalogue. Native macOS
may then final-link and run applications to validate the candidate. This uses the
operating system as the implementation under test; it does not derive the
interfaces from installed Apple software.
