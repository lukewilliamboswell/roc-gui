= Contributing

Read `AGENTS.md` before changing the platform. The central constraint is “test
what we fly”: tests and measurements drive the production implementation and
never reproduce it.

== Pinned development environment

`blueprint run build` builds the native host. `blueprint run test` builds and
runs the application specifications through the production host.
`blueprint run lint` runs Clippy with warnings treated as errors.
`blueprint run check` verifies the installed compiler against `.roc-version`.
Run these commands inside the Blueprint bootstrap environment described in
Getting started. Commit `Blueprint.roc`, `Blueprint.lock`, and `.roc-version`;
`.blueprint/` contains generated files.

The Linux shell supplies native build dependencies, including Fontconfig and
Wayland. The build helper prepends its verified ALSA interface to the shell
search paths. Executables use the native desktop runtime libraries selected by
the system ELF loader.

Development builds select the unified linker-input release when its producer
inputs match the checkout. Missing or stale releases select the development
recipes and their verified component inputs. Invalid locks and failed artifact
verification stop the build. Release packaging requires a matching unified lock.

CI runs the same Clippy command as the local pre-commit hook, including test
targets, with `-D warnings`. Install the `clippy` component from the repository
Rust toolchain when running the hook outside the Blueprint environment.

Change `.roc-version` to select another compiler. Run `blueprint update` when
the locked overlay needs a newer release, and review the lock changes. CI checks
that every maintained example and benchmark has adjacent specifications and
runs the semantic suites. A build or semantic failure fails the gate; it is not
silently skipped. Record unresolved defects in `wip/issues-backlog.md`.

Release packaging verifies the compiler identity and records its exact tag in
the release manifest. Release validation and example archiving insert that tag
into app headers alongside the released platform reference. The branch sources
remain unpinned so the repository has one compiler authority.

== Validate a change

[source,sh]
----
python3 scripts/run_cargo.py test --locked --package roc-gui-host
roc check examples/counter/main.roc
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
----

`roc check` answers whether a program type-checks, which is not the same
question as whether it compiles. A change to the shape of a platform type can
leave every example checking cleanly while code generation for one of them fails
to terminate, so a change to `platform/` is validated by building an application
and not only by checking one. The specification runner builds every application
it runs, which is why it is the gate that matters for a platform change.

The specification runner verifies and stages the independently released native
host when its recorded source fingerprint matches the checkout. A host-source
change automatically builds and exercises the changed production host instead.

Run the affected benchmark family when a change touches rendering, routing,
graph work, allocation, recording, or a scaling-sensitive data structure. Run
the complete specification suite before integrating a cross-cutting change.

When changing an effect, update `wip/resource-access-inventory.md` after reading
the public API, hosted ABI, native owner, configuration source, and verifying
specifications. Mark missing enforcement or evidence `Unverified`; never infer security
from an absent public function or an opaque Roc type.

== Complete a platform feature

A new element, property, event, or state mechanism is complete when it has:

. a Roc API and hosted ABI representation;
. behaviour in the single host graph and GPUI path;
. semantic locators, operations, and assertions where users need to observe it;
. deterministic counters and timing spans recorded by the work owner;
. behaviour, ambiguity, and failure specifications;
. a realistic scaling case for every dimension that can grow;
. focused SQLite reporting for evidence that production code populates;
. application-facing documentation.

A resource feature additionally requires trusted authorisation, OS-enforced
scope, derivation and lifetime rules, revocation semantics, privacy review, and
platform-boundary tests. The Resource access chapter
describes them.

Exercise recorder-disabled, enabled, saturated, output-limited, interrupted,
and writer-failure paths when changing capture infrastructure. Timing is not a
correctness assertion.

== Fixture-backed steps

The steps below are available to any specification, and this repository's
deterministic fixture data is what makes their counts stable. All of them are
numeric owner evidence: no name, path, URI, identifier, or application text is
recorded. What a case may reach is declared by its own `(grants ...)` clause,
described in the specification language reference.

`expect-audio-counters`:: Live outputs, live tracks, and the seven
operation-attempt counters.
`expect-file-access`:: Chooser, provisioned, and revoked root counts.
`expect-file-lifecycle-counters`:: Root allocations, child allocations, live
handles, revocation requests, successful revocations, and post-revocation
operation rejections.
`expect-file-selection-counters`:: Seven host-owned totals, in order: chooser
requests, chosen results, cancellations, denials, unavailable results,
suppressed prompts, and development provisions.
`clipboard-text`:: Changes the clipboard source granted to a fixture, and is
rejected without an explicit fixture grant. The next application timer pull
observes the new value through the production capability and host read route;
the value is neither copied into capture evidence nor emitted as a diagnostic.
`expect-image-owner-counters`:: The production image-data owner's staged-node,
staged-byte, inspection, and failure totals. Image names, paths, encoded
values, and dimensions are not capture evidence.
`expect-asset-counters`:: The production asset owner's six totals, in order:
opens, refused opens, manifest checks, reads, refused reads, and bytes read.
Asset paths, file names, and asset content are not capture evidence.
`expect-document-counters`:: The document owner's picks, chosen files,
cancellations, refusals, and reads, then its live handles.
`expect-hash-counters`:: The file hash owner's files hashed, hashes refused, and
bytes hashed, across directory and single-file grants. File names, paths, and
digests are not capture evidence.
`revoke-file-grants`:: Invokes the trusted-host revocation seam for every chosen
folder and file. It is not an
application event or a Roc capability API.

The Settings Center's 100-, 1,000-, and 10,000-byte profile-note cases exercise
ordinary controlled editing followed by the same worker-backed atomic save the
application uses. `expect-value-bytes` supplies deterministic, content-free
scale evidence; task and patch counters remain owned by their production paths.

== Generated bindings

Regenerate checked-in Roc ABI bindings whenever hosted functions or
`platform/Host.roc` change:

[source,sh]
----
python3 scripts/regenerate_glue.py /path/to/roc
----

`platform/main-glue.roc` is an ABI-generation root. Applications build against
`platform/main.roc`.

== Documentation

AsciiDoc sources live in `docs/`; `docs/index.adoc` is the complete book. Build
the HTML site with:

[source,sh]
----
python3 scripts/build_docs.py
----

Build the standalone PDF as well with `python3 scripts/build_docs.py --pdf`.
Docker supplies the pinned Asciidoctor, diagram, PDF, Mermaid, and syntax
highlighting toolchain; only Python and Docker are required on the host. Output
is written beneath `.docs-out/`.

Documentation describes the product and its enduring contracts. Put defects,
missing capabilities, and implementation tasks in `wip/issues-backlog.md`, then
remove entries when they are resolved.

== Native linker inputs and releases

Generated objects, libraries, TBD files, host archives, and platform bundles do
not belong in Git. Reviewed recipes, catalogs, provenance, locks, and license
texts do.

Native artifacts have three independent release layers:

. The linker-input producer builds one content-addressed release containing the
  complete `x64glibc`, `arm64mac`, and `x64mingw` sets. This includes every
  `platform/main.roc` input the host does not produce; the Windows resource
  therefore belongs to this release, not to the GUI host release.
. Host producers build `libhost.a` for each target and bind it to the exact host
  source, Cargo lock, configuration, profile, and toolchain inputs. The Windows
  host also produces `windows-imports.lib`, described below.
. Platform release assembly admits released external and host inputs, runs the
  supported consumer matrix, and publishes those same tested bytes under Roc's
  content-addressed bundle name.

=== Continuous integration

CI produces each target's native host once per run and exercises those exact
bytes everywhere. The reusable host workflow decides how the checkout's host is
produced: a released host that matches the committed sources is admitted as
published; a host-source change runs the host unit tests once and builds with
the release producer, `scripts/prepare_host_build.py`; a checkout whose linker
inputs are not yet released builds against development inputs. The job seals
the staged `platform/targets/<target>` with its source fingerprint and the
digest of every file.

Every specification, smoke, window, and gallery job admits that sealed host
with `scripts/ci_host.py admit`, which refuses a different source fingerprint or
any changed byte, and runs with `--skip-host-build`. No test job builds a host.
Each target's tests wait only for that target's host.

When the host sources change, a candidate job composes the notice payload,
source companion, and release archive from the same sealed build, so the
archive a release would publish is the one the specifications exercised.
Publishing a host release dispatches the same host workflow; its publish job
remains the attested signer.

=== Host source companions

Host notice selection comes from Cargo's successful build messages and is
checked against the committed lock. Registry sources retain their published
crate archive and checksum. Git sources require an exact repository, revision,
and package path in `dependencies/gui-host-notices/git-sources.json`.

The build captures Git package sources from immutable Git objects, checks them
against the compiler's checkout, and retains original workspace declarations
and notices. In-repository symbolic links are resolved; escaping links and
submodules are rejected. Evidence records the repository, revision, package
path, Git tree identity, and a separate SHA-256 digest of the deterministic
source archive. Notice composition and source-companion validation verify that
archive digest; a Git revision is never used as a crate archive checksum.

=== The Windows import library

A Windows link needs an import record for every DLL function the program
calls. The platform ships exactly those records in one library,
`windows-imports.lib`, rather than the complete export lists of every DLL a
dependency could name. Only the host and the GNU runtime call DLLs, and what
they call is fixed when the host is built, so the host build derives it:

. rustc reports the native libraries the host archive leaves to the final link,
  and the build scripts report where they are.
. `scripts/windows_link_imports.py` follows the link the way the linker does:
  from the host's objects and the runtime's startup object, it pulls a runtime
  or import member only when a symbol it defines is still undefined.
. An import rustc emitted is taken with the DLL and type rustc gave it. A name
  referenced without one is resolved through rustc's native libraries in
  rustc's order. Anything left must be defined by the linker or by the Roc
  application; any other name fails the build.
. The complete exports of `kernel32` are added as the application ABI: code the
  Roc compiler emits calls it as C code calls the UCRT, and a later compiler may
  call more of it than this host does.
. Zig's `dlltool` writes one import library per DLL from a module-definition
  file, and the members are merged into one archive. Every member is read back
  and compared with the requirement it was made from.

The host's own import members are then separated from `libhost.a` against the
host's own inventory. The normalization receipt records both steps, the native
libraries, and every import by DLL, name, and type; a host release is admitted
only when the packaged library matches that receipt.

Linker-input production runs only when explicitly dispatched for an open pull
request whose branch contains a material recipe, catalogue, resource, or symbol
change. The unprivileged producer builds each input twice, validates it, and
uploads exact candidate bytes. The trusted default-branch publisher admits the
requested branch and commit, verifies the successful producer run and its
attestations, and publishes those same bytes under the SHA-256 of the aggregate
manifest. The release remains permanent after the pull request merges. The
publisher adds a GitHub-signed, lock-only commit to that pull request, so the
review adopts the produced release without a bootstrap build on the default
branch.

`link-inputs.lock.json` records the immutable release, target archive digests
and sizes, source revision and branch, signer workflow, source fingerprint, and
aggregate manifest digest. Ordinary pull requests have no linker-input build
job. They restore the archive cache, verify its locked size and SHA-256 even on
a cache hit, and download the immutable release only on a miss.

Consumers verify locked bytes before extraction and on cache hits. A digest,
size, manifest, target, provenance, or attestation mismatch is a hard failure and
must never fall back to a local build. Development builds select native source
inputs when the unified lock is absent or its producer fingerprint is stale.
`./build.py --source-inputs` also selects this path explicitly; the linker-input
producer stages its exact candidate archives before final-link validation.
Final platform releases accept only locked, released, and attested inputs.

Change a linker input through its owning recipe and tests, then dispatch the
trusted linker-input publisher with that pull request number. The resulting
signed lock commit makes the new symbols available to the same branch. Ordinary
platform and host changes reuse the locked release and never invoke a producer.

=== Linux producers with Nix

The five Linux component producers use `dependencies/linux/default.nix` and the
root nixpkgs input in `Blueprint.lock`. Zig 0.16.0 and the build tools come from
that package set. Meson uses the recipe's fixed-hash 1.12.0 source with the same
nixpkgs packaging. Upstream source downloads are fixed-output derivations;
compilation and native probes run inside the network-isolated Nix sandbox.

Run a component producer with an absent output directory, then force a rebuild:

[source,shell]
----
python3 scripts/build_freetype.py --output /tmp/candidate
python3 scripts/build_freetype.py --rebuild --output /tmp/rebuild
cmp /tmp/candidate/freetype-x64glibc.tar /tmp/rebuild/freetype-x64glibc.tar
----

`--rebuild` executes Nix's reproducibility check, even when the first result is
cached. CI requires sandboxing and repeats this for every Linux component.
Schema-2 archives identify the builder tool derivation, nixpkgs revision and
content hash, Blueprint lock, and Nix recipe. Corresponding source includes the
upstream source bytes and reproduction inputs. Consumers also accept the
schema-1 archives used by other targets and existing reviewed releases.

Published shared libraries have no build search paths or store-qualified
runtime dependencies. Producer probes use the sandbox's private loader and
providers. A separate Ubuntu validation job admits the exact candidate archives,
final-links the production host, and runs the GPUI smoke test outside Nix before
those archives can be assembled and attested.

=== Windows inputs from Nix and native Windows

On Linux x86-64, the Windows runtime and resource producers use
`dependencies/windows-gnu-runtime/default.nix`, with nixpkgs pinned by
`Blueprint.lock`. The runtime compiles with the recipe's hash-verified official
Zig distribution; the resource compiler comes from pinned nixpkgs. Downloads
are fixed-output derivations and builds run in the network-isolated sandbox.

[source,shell]
----
python3 scripts/build_windows_gnu_runtime.py --output /tmp/windows-candidate
python3 scripts/build_windows_gnu_runtime.py --rebuild --output /tmp/windows-rebuild
python3 scripts/build_windows_resource.py --output /tmp/windows-resource
python3 scripts/check_linux_reproduction.py /tmp/windows-candidate --target x64mingw
----

On native Windows x86-64, Python 3.12 or newer runs the same runtime compilation
and packaging code using the recipe's hash-pinned Windows Zig distribution.
The resource command uses Zig 0.16.0 on `PATH`. Set `TEMP` to a directory without
spaces, as required by the verbose linker diagnostics used to identify inputs.

[source,powershell]
----
python scripts/build_windows_gnu_runtime.py --output candidate
python scripts/build_windows_resource.py --output resource
----

Native builds use fresh compiler caches on every invocation; `--cache` stores
only the verified Zig download. Schema-3 native archives record the Windows
toolchain digest and reproduction source digests. Schema-2 Nix archives record
the pinned Nix build environment. Neither archive records the builder's local
paths or machine identity.

CI requires two identical Nix builds, two identical native Windows builds, and
matching resource bytes across both hosts. Windows executes the runtime probes
against each host's candidate, including CRT startup and teardown, thread-local
destructors, C++ and Rust unwinding, and UBSan failure. The published runtime is
the Nix candidate that passed native execution; cross-host runtime byte equality
is not required because the build provenance differs.

=== Generated system-library interfaces

When an application links to a library supplied by the target environment, its
producer emits only the reviewed symbols and the runtime library's stable name.
The archive does not contain an implementation or an absolute provider path.
Production verifies the exact exported symbol inventory and stable library name,
links a probe through the generated interface, and runs that probe against a
native provider. The release carries the interface recipe, probe, producer, and
archive verification inputs needed to reproduce it.

The target system or package environment supplies the implementation at runtime.
This keeps linker inputs independent of a distribution's filesystem layout while
preserving normal runtime library resolution.

=== Generated macOS interfaces

Read `dependencies/macos-interfaces/README.md` and `PROVENANCE.md` before changing
the macOS catalogue. No Apple SDK binary, header, TBD, framework binary, dylib,
object file, symbol table, generated SDK metadata, or other installed macOS
software may supply interface data.

The project-built `libhost.a` may be inspected only to inventory unresolved
references. That inventory does not establish library ownership, public API
status, weak-link behaviour, or final-link reachability and never populates the
catalogue automatically. Every selected symbol and owning library requires reviewed
public documentation or identified public open-source evidence. Prefix-based
classification and installed system artifacts do not establish library ownership.

Generation is deterministic and offline from the reviewed catalogue. Native macOS
may then final-link and run applications to validate the candidate. This uses the
operating system as the implementation under test; it does not derive the
interfaces from installed Apple software.
