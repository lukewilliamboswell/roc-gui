= Getting started

Roc GUI runs on Linux x86-64, macOS on Apple silicon, and Windows x86-64.

== Use a published platform

An application names a released platform by its URL and needs nothing else.
Build it with a current Roc nightly. The release page carries the URL and
names the nightly the release was built and tested with:

[source,roc]
----
app [State, main] { pf: platform "https://github.com/lukewilliamboswell/roc-gui/releases/download/<version>/<bundle>.tar.zst" }
----

[source,sh]
----
roc build --opt=dev --output=my-app main.roc
./my-app
----

Every release also publishes an archive of the examples with their headers
already pointing at that platform, so they build without a checkout.

== Work from a checkout instead

Contributors build the platform locally. Install a current Roc nightly as
`roc` and the `blueprint` binary from the
https://github.com/lukewilliamboswell/roc-blueprint/releases/tag/0.8.0[roc-blueprint 0.8.0 release].
On Linux x86-64 or Apple silicon macOS, install Nix with flakes enabled for the
native toolchain, then enter the development shell from the repository root:

[source,sh]
----
blueprint shell
----

`Blueprint.lock` pins the Nix package set and the tooling compiler. Rustup
selects the toolchain in `rust-toolchain.toml`. On Windows, install the Rust
toolchain directly. No application names a compiler: each builds with the
`roc` on the machine.

The host archive is part of every Roc GUI executable. Build it first:

[source,sh]
----
python3 build.py
----

The result is `platform/targets/<target>/libhost.a`, where `<target>` is
`x64glibc`, `arm64mac`, or `x64mingw`. Re-run `build.py` after a host change.

== Build and run the example

[source,sh]
----
roc build --opt=dev --output=counter examples/counter/main.roc
./counter
----

The window contains two independent counters. Their buttons show the normal
application cycle: a press runs a Roc handler, the handler returns a new counter
state, and only that counter's render boundary is rendered again.

== Start an application

Create a directory with a `main.roc` file and point its platform path at this
repository's `platform/main.roc`:

[source,roc]
----
app [State, main] { pf: platform "../../platform/main.roc" }

import pf.Gui

State : { greeting : Str }

render : State -> Gui.Elem(State)
render = |curr_state| Gui.text(curr_state.greeting)

main : Gui.Program(State)
main = Gui.run({ init: |_access| { greeting: "Hello from Roc" }, render })
----

Choose an executable name explicitly when building your application:

[source,sh]
----
roc build --opt=dev --output=my-app path/to/main.roc
./my-app
----

Pass `--host-help` to the executable to list native host options:

[source,sh]
----
./my-app --host-help
----

Capabilities are absent by default. Grant each one explicitly. For example, the
terminal workspace needs a local interactive shell profile:

[source,sh]
----
roc build --opt=dev --output=terminal-workspace examples/terminal-workspace/main.roc
./terminal-workspace --host-cap-process local-shell
----

The application receives only that fixed profile; it cannot select an
executable, arguments, or inherited environment.

`--host-cap-*` options provision development and automation authority. They use
the production registries and operations but are not trusted user consent.
Interactive resource access uses the trusted broker workflows described in the
resource access chapter.

== Reload while you edit

Run an application with `roc` and no flags to start a development session with
hot reload:

[source,sh]
----
roc examples/hot-reload/main.roc
----

When you save a source file, the compiler builds a new application image. The
host asks the running session for its state and starts a session of the new
image with that state. The new session renders the state and installs its own
dispatcher, so render functions and event handlers run from the new image. The
state is kept.

The host links the `roc_hot_reload_generation` symbol. The platform needs a Roc
compiler that defines this symbol. An older compiler does not define it and
cannot link the host.

* A change to the layout of the `State` type requires a restart. The compiler
  rejects the reload with "hot reload changed the platform host interface".
* The compiler does not detect a `State` change that keeps the layout, for
  example two fields of the same type that change places. Restart after such a
  change.
* A change to the platform source requires a restart. The compiler does not
  reliably detect it.
* A task, timer, or completion that started before the reload finishes on the
  code that started it. A task that starts its next task from its own
  completion, such as a sampling loop, runs the old code until the chain stops.
* A function stored in the state keeps the code of the image that created it.
* The new session mounts every component that has no key as a new instance,
  as a parent render does. A task that such a component started is cancelled.
  Editor state inside such a component resets.
* A crash in the render function of the new image ends the process. The state
  is lost.
* Each reload keeps the state of the replaced session in memory until the
  session ends.
* The host reads the window title, size, and colours once, at startup. The
  opening action does not run again.

== Run the specifications

Every application keeps its specifications in one `specs/` directory beside
`main.roc`. Run the counter's cases with:

[source,sh]
----
python3 scripts/run_specs.py 'examples/counter/specs/*.scm'
----

The driver builds the host beside the locked linker inputs. It then builds the application, classifies each
selected `.scm` file by the steps it contains, runs it in a fresh process, and
prints the capture path for every passing case. Semantic specifications use the
production event route and mounted graph without opening a GPUI window; window
specifications open the real window. Pass `--only semantic` or `--only window`
to run one kind.
