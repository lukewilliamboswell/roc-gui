= Understanding captures

Every specification run produces a versioned `.rgstats` SQLite database. The
database keeps the semantic result, attributed operation records, resource
counters, recorder health, and privacy-safe comparison identity together. This
supports several focused reports without inventing a second measurement format.

== Start with the summary

[source,sh]
----
python3 scripts/analyze_stats.py CAPTURE.rgstats
----

The summary validates the schema and capture finalisation, then reports the
case identity, run and cycle counts, and the distribution of measured operation
duration. A capture with lost events, writer failure, output truncation, or an
unclean shutdown is rejected as incomplete.

A capture's verdict follows from its own records. Until `metadata.final_state`
is `complete` it has none: it is _withheld_, because the records a verdict rests
on are decided at finalisation, and a capture still being recorded reads the
same as one whose recorder stopped. A finalised capture is _untrusted_ when
`clean_shutdown` is not `1`, `recorder_health` reports omitted events, a writer
failure, or a reached output limit, `recording_gaps` holds any row, or any
measurement family is still `unfinalized`. It is _partial_ when any family is
`partial`. Otherwise it is _complete_: a `not_recorded` or `unavailable` family
is a declared absence, not a loss. The Observatory example applies this rule to
every capture it lists.

The analyser opens databases read-only. You can also inspect them with any
SQLite client; application-facing reports should use the supplied views so the
evidence-status rules remain visible.

== Choose the question you are asking

[source,sh]
----
python3 scripts/analyze_stats.py CAPTURE.rgstats --view semantic_health
python3 scripts/analyze_stats.py CAPTURE.rgstats --view roc_work
python3 scripts/analyze_stats.py CAPTURE.rgstats --view component_work
python3 scripts/analyze_stats.py CAPTURE.rgstats --view host_gpui_work
python3 scripts/analyze_stats.py CAPTURE.rgstats --view gpui_frame_spans
python3 scripts/analyze_stats.py CAPTURE.rgstats --view native_work
python3 scripts/analyze_stats.py CAPTURE.rgstats --view gpui_frame_work
python3 scripts/analyze_stats.py CAPTURE.rgstats --view virtual_list_materialization
python3 scripts/analyze_stats.py CAPTURE.rgstats --view timeline
python3 scripts/analyze_stats.py CAPTURE.rgstats --view process_resources
python3 scripts/analyze_stats.py CAPTURE.rgstats --view capture_health
python3 scripts/analyze_stats.py CAPTURE.rgstats --view scaling
python3 scripts/analyze_stats.py CAPTURE.rgstats --view spec_results
----

`semantic_health`:: Did runs and steps pass, and is their evidence complete?
`roc_work`:: How much callback time belonged to platform routing, application
update, application render, component comparison, and platform lowering, and
how much Roc allocation activity occurred inside each owned span?
`component_work`:: How many renders, comparisons, skips, component mounts and
retirements, registry visits, ancestor invalidations, keyed order-tree visits,
and keyed fallback snapshot items did the component runtime perform in marked
sample turns?
`host_gpui_work`:: How much time did graph validation, graph application, and
available GPUI materialisation consume, and how many native nodes were retained
or visited during structural validation?
`gpui_frame_spans`:: For each drawn frame, how long did the host's own root
element spend requesting layout, prepainting, and painting the application
subtree, and what is the status of the frame stages the host does not own?
`native_work`:: How many native `NodeView` render calls and host-created
`AnyView` elements occurred in completed GPUI frames, grouped by node kind?
`virtual_list_materialization`:: For interactive GPUI frames, how many logical
items intersected each viewport and how many native entities were
materialised, recycled, and retained? Each list records one row per drawn
frame, after GPUI has drawn it; a patch that rebuilds part of a row, or retires
rows with their list, records the entities it built or recycled in rows of its
own. For a list of rows produced on demand, the intersecting
items include rows not yet mounted, which are drawn as blank places and
materialise no entity. The Roc turns that move such a list's window are
ordinary cycles with the trigger `viewport`. Semantic-headless captures report
this family as `not_recorded` because they have no viewport.
`timeline`:: How many drawn frames record the cycles they were first to draw,
how many list passes record the frame or cycle that produced them, and what
span of the capture's clock do cycles, frames, and passes cover?
`process_resources`:: How did process CPU time, peak RSS, and Roc allocation
counters change across runs?
`capture_health`:: Did batching, queue pressure, omissions, limits, or writer
errors weaken the capture?
`scaling`:: What workload sizes, deterministic work counts, and timings belong
to each measured cycle?
`spec_results`:: Which individual steps passed, and what counts or diagnostics
did they record?

Audio counter assertions retain their complete expected and observed vectors in
`audio_counter_assertions`. The columns cover live output and track resources,
then acquire, load, play, pause, seek, status, and stop operations. Each row is
owned by the assertion step that sampled the production audio host.

Clipboard and SQLite assertions likewise retain complete vectors in
`clipboard_counter_assertions` and `database_counter_assertions`. Clipboard rows
record live handles and acquire, read, and write attempts. SQLite rows record
live connections and open and query attempts. These are correctness counters
sampled directly from the capability owners; unavailable evidence is absent.

HTTP assertions retain live clients plus acquire, send, and denied-operation
counters in `http_counter_assertions`. Transport cancellation is not recorded
because the HTTP capability does not expose it; stale reducer suppression does
not fabricate cancellation evidence.

TCP assertions retain live streams and connect, read, write, and close attempts
in `tcp_counter_assertions`. Endpoint, Redis key, and Redis value text are not
capture fields.

Schema 18 records component work in `component_work_counts`, keyed by cycle
and numeric kind. Kinds are `0 rendered`, `1 compared`, `2 skipped`, `3 mounted`,
`4 retired`, `5 registry_visits`, `6 ancestor_invalidations`,
`7 projection_gets`, `8 projection_sets`, `9 keyed_order_visits`, and
`10 keyed_snapshot_items`. The Roc runtime
reports each count at the operation that owns it. A turn publishes its
observation when the mounted graph accepts its transaction. Rejected turns do
not replace the last committed observation.

`rendered` includes the application root renderer as well as component
renderers; `mounted` and `retired` count component instances, not that implicit
root. `compared` counts comparisons against valid saved input, and `skipped`
counts successful comparisons. `registry_visits` counts logical event-route
lookups and emitted-component instance lookups, not every internal radix-index
step, state projection, or ancestor walk. `ancestor_invalidations` counts strict
ancestor invalidation operations, including ancestors whose snapshot was
already unknown. `projection_gets` and `projection_sets` count actual calls to
configured state adapters during the UI callback, including reads for existence
and memo checks. They count invocation even when a fallible adapter returns
`Removed`. They exclude arbitrary application reads and background worker work.
`keyed_order_visits` counts persistent order-tree nodes visited while updating
mounted keyed-owner metadata. `keyed_snapshot_items` counts items materialised
only for initial mount or stale-revision recovery; an exact journal update
records zero. Neither count stands for host graph work, native edits, layout,
or paint.
The iterative executor accumulates these counts and publishes them before the
same turn commits. They are not inferred from component depth, rendered nodes,
or elapsed time. These are owner-defined events, not estimates of total work.

Capture cycles use the difference between the owner's totals at their start
and end. Each action turn in a gesture has its own cycle; the last-turn
specification assertion describes its final committed turn.

`cycles.component_work_recorded` distinguishes a measured turn with no component
work from a turn with no observation. Positive counts have rows; an absent kind
means zero only for a cycle whose recorded flag is set. The component report
withholds totals when observation coverage is incomplete.
`component_work_assertions` records numeric kind, expected count, and observed
count for each requested assertion field, without component keys or application
state. An unavailable observed count is `NULL`.

The graph owner supplies `cycles.retained_nodes` and
`cycles.validation_visits`. Retained nodes are mounted nodes preserved by
explicit subtree retention. Validation visits count payload examinations in
fresh-node shape validation, rooted fresh/frontier traversal, retirement
discovery, and retained-root liveness checks. They do not stand for metadata
index lookups, identity ancestry work, or all host operations.

Keyed graph transactions additionally report `cycles.keyed_graph_visits`,
`cycles.keyed_original_reads`, and `cycles.keyed_first_touches`. The graph
owner counts validated or retired fragment nodes; the keyed-order owner counts
original link reads and distinct first-touched keys. Ordinary patches report
zero because they perform no keyed graph transaction.
`cycles.keyed_native_edits` and the three keyed item-entity columns record the
native application owner's accepted edits and item entities created, retired,
or moved. Native-work kind 16 records keyed-container renders and view-element
construction. Layout, prepaint, and paint remain frame-wide owner spans; no
keyed-container share is inferred from them.

Each focused view includes `evidence_status` and `evidence_reason`. Read those
before interpreting numeric columns. Missing measurements are `NULL` rather
than a fabricated zero.

== What semantic runs measure

`scripts/run_specs.py` invokes the executable with `--host-run-spec`. The Roc
application still renders through the platform, events still use its installed
dispatcher, and patches still enter the host's canonical mounted graph. The
runner does not open a GPUI window. Consequently its captures can attribute
platform routing and lowering, application update and render, component
comparisons, allocation activity within each span, the enclosing Roc callback,
host validation, graph
application, CPU, RSS, and deterministic graph work, while GPUI layout, paint,
and presentation are unavailable.

`cycles.roc_callback_ns` measures time inside one Roc dispatch call. Each drag
phase and task completion has its own cycle, including steps that await several completions.
A canvas pointer phase records a `drag` cycle, a delivered canvas hover a
`hover` cycle, and a canvas wheel scroll a `wheel` cycle, whether a
specification or a person in the interactive window drives it.
Waiting for workers and applying graph patches are outside the callback span.
The enclosing cycle duration includes the wait.

Schema 18 records task completions delivered by the interactive window loop
as well as those driven by specifications. Each delivered completion records
its own callback, application spans, allocation activity, and graph work.

This distinction matters: headless graph application is useful host evidence,
but it is not a proxy for rendering a frame.

== What a drawn frame measures

Interactive task completions pass through the recorded callback path just as
input events do. Their delivery cycles begin after the worker result arrives;
neither callback duration nor delivery-cycle duration includes queue or worker
waiting. Each accepted completion records its own `task` cycle, including
completions that produce no graph change.

A capture taken with a GPUI window records one `gpui_frames` row per drawn
frame. The application's element tree hangs below a single host-owned element,
and each row holds that element's own three stages for the whole subtree:
`layout_request_ns` builds the subtree's styles and layout nodes,
`prepaint_ns` resolves bounds, text, and hitboxes once layout is solved, and
`paint_ns` produces the frame's scene. Each duration belongs to the call that
performed it.

Two frame stages are performed by GPUI outside any host-owned element and are
therefore reported as unavailable rather than attributed. Taffy solves layout
once for the window from GPUI's own root element, between the host element's
layout request and its prepaint. Presentation and frame completion are private
to GPUI; a compositor frame callback would be the seam that owns them.

== Place work on one clock

Every interval in a capture is measured on one process-relative monotonic
clock, whose origin is fixed when recording starts. `runs.started_ns` and
`runs.ended_ns`, and the `start_ns` and `end_ns` of `cycles`, `gpui_frames`, and
`virtual_list_frames`, are nanoseconds on that clock. They order and place work;
they carry no wall-clock time or machine identity.

Each interval is recorded by the component that performs the work. A cycle's
interval is its owner's: from the instant it began handling the event or
completion to the instant its patch was applied, the same reading its
`duration_ns` is taken from. A frame's interval runs from the start of the host
element's layout request to the end of its paint. It therefore encloses GPUI's
layout solve, whose own duration remains unavailable; the interval places the
frame without attributing that time. A list pass's interval runs from the
first range GPUI asked of the list in a frame to the moment its entities were
settled after that frame, or, for a pass performed while a patch was applied
to native views, across that application.

Causal links are recorded by the owner that knows them, never inferred from the
clock. Two intervals that touch are not thereby related.

[cols="1,3",options="header"]
|===
|Table or column |Link
|`gpui_frame_cycles(frame_id, cycle_id)`
|The recorded cycles whose patches reached native views after the previous
frame began drawing and before this one did: the changes this frame is the
first to draw. An event loop may coalesce several cycles into one frame, which
then has several rows. A frame that follows no new cycle, such as one drawn for
hover or a list's own scrolling, has none. A cycle whose patch changed nothing
is not linked, because it gave a frame nothing to draw. A frame abandoned before
paint hands its cycles to the frame that does draw them.
|`virtual_list_frames.origin`
|`paint` for a pass settled after GPUI drew the list, `patch` for a pass
performed while a patch was applied to native views.
|`virtual_list_frames.frame_id`
|For a `paint` pass, the drawn frame that asked for the list's rows. `NULL`
when the frame that asked is not the frame the host recorded as painted.
|`virtual_list_frames.cycle_id`
|For a `patch` pass, the recorded cycle whose patch performed it. `NULL` for a
patch the host applied outside any recorded cycle.
|===

Two measurement families describe this linkage. `frame_cycle_linkage` is
complete when every drawn frame carries the cycles its owner handed it; a frame
with no row is then a recorded "no new cycle", not a missing one.
`virtual_list_linkage` is complete when every `paint` pass was settled against
the frame that drew it. Both are `unavailable` when no frame was drawn or no
list entered a viewport, and `partial` when the recorder omitted events, since
an omitted cycle or frame has no row to link. Semantic-headless captures report
both as `not_recorded`: they draw no frame and have no viewport, although their
cycles still carry intervals.

== Count native rendering work

Schema 18 stores native work in `gpui_native_work`, keyed by
`frame_id`, numeric `metric`, and numeric `kind`. Each `frame_id` references
`gpui_frames.id`. Metric `0`, `node_view_renders`, counts actual calls to the
production `NodeView::render` implementation. Metric `1`,
`view_elements_created`, counts the host helper constructing an `AnyView`
element to hand to GPUI, including elements for retained native entities.

Native counters are always active, including when capture recording is
disabled. Production-window tests can therefore observe the same operations
without enabling the recorder. The host snapshots these counters at the start
of `Runtime::render` and, when recording is enabled, publishes their deltas when
the root element finishes painting that frame.
The `native_work` report gives totals, maxima, and means per completed frame
for each metric and node kind. Its observation family is `gpui_native_work`.

The `gpui_frame_work` report separates fresh frame construction from cached
subtree replay. GPUI records counts at the operations that own them: prepaint
and paint cache replay, hitbox and listener insertion, scene insertion and
replay, element-state access and finish-time movement, and cached view-range
rebasing. Counts describe operations, not bytes or elapsed time. A missing
completed frame is unavailable rather than zero.

[cols="1,2",options="header"]
|===
|Kind |Node
|0 |Canvas
|1 |Button
|2 |Checkbox
|3 |Textarea
|4 |Image
|5 |Column
|6 |Dialog
|7 |Panel
|8 |Row
|9 |Scroll
|10 |Virtual item
|11 |Virtual list
|12 |Text input
|13 |Text
|14 |Styled text
|15 |Boundary
|16 |Keyed container
|17 |Popover
|===

Schema 20 adds kind 17. A popover's view renders when its surface opens or
closes as well as when the popover itself changes; its anchor and content are
counted under their own kinds. The region that carries hover handlers,
shortcuts, or a focus request for an element is a popover with no content, and
is counted here too.

Rows contain positive counts. A missing metric/kind row means measured zero
only within a recorded frame with complete native-work evidence. A capture
with no completed frames reports unavailable counts. A semantic-headless
capture reports this family as `not_recorded`; it has no native render path.
Incomplete observations withhold counts rather than publishing partial totals
as complete evidence.

Roc component renders, native view renders, and native element construction
measure distinct operations. A local Roc update can perform one component
render while a subsequent frame renders many native views. Native counts
identify this additional work without estimating it from Roc counters or
elapsed time. They do not identify GPUI cache hits, layout-solver work,
presentation, retained memory, or GPU work. Counts are frame-scoped. A frame's
recorded cycles in `gpui_frame_cycles` may be several when the event loop
combines updates, and a frame's work is never divided among them.

Native subtree reuse follows layout ownership. Non-root rows, columns, and
panels whose width and height are fixed by matching pixel size, minimum, and
maximum values, with growth disabled, have outer geometry independent of
child measurement. Baseline-aligned subtrees retain ordinary layout.
Retained off-path containers reuse their native subtree;
a changed descendant invalidates its ancestor path. Intrinsic and flexible
containers preserve their content-driven layout behavior.

The hover grid declares its existing five-pixel cells and one-pixel gaps as
exact row and grid dimensions. A local cell update reaches its button,
translation boundary, row, grid column, and outer application column.
Rebuilding those containers can construct wrappers for their immediate
children. Compare both native metrics across 100, 1,000, and 10,000 cells:
a bounded set of rendered views does not imply the same bound on constructed
wrappers. The row and column fanout is part of the expected work.

The nested hover-grid companion uses the same leaf counts and cell geometry
as the flat grid. Recursive quadrant translations project persistent child
indices with at most four entries. Local hover updates render the leaf;
delegated clicks travel to the depth-one quadrant, which accepts the candidate
and renders its subtree. Reordering sibling quadrants within their native row
preserves their keyed lifetimes; removing a quadrant retires its descendants
and their task deliveries. Compare owner callback spans as well as native
counts across both layouts. Ancestor-invalidations count the affected ownership
path; they do not count composed getter calls or establish linear dispatch cost.

A native-work assertion belongs to a controlled interaction and frame window.
Its expected counts follow the affected patch nodes and ancestor containers in
that case. Input, focus, and layout invalidation can cause additional native
work in other interactions; these assertions are specific evidence rather than
an unconditional limit on rendering for every action.

== Record an interactive application

Recording is disabled by default. Enable it on an ordinary application with:

[source,sh]
----
./counter --host-stats-record
----

Choose a destination explicitly when captures are part of an experiment:

[source,sh]
----
./counter --host-stats-output=counter-session.rgstats
----

Additional controls are:

`--host-stats-detail=summary|full`:: Select the recorder detail policy. Summary
omits setup cycles while retaining measured, initialisation, and interactive
cycles together with all semantic evidence. Full additionally records setup
cycles, making the extra observer work explicit.
`--host-stats-buffer-mib=N`:: Set the bounded in-memory admission buffer.
`--host-stats-max-mib=N`:: Limit database and write-ahead-log output.

The recorder batches writes on a separate thread. When recording is disabled,
the event hot path skips clocks and event construction behind a predictable
inactive branch. Deterministic component and native-work counts remain available to
specifications independently of capture recording. When it is enabled,
recording failure is evidence failure; it
does not change application behaviour.

== Read a capture while it is recorded

A capture is a write-ahead-logged SQLite database, and the recorder commits
batches of events as it goes, so a reader may open it while the application is
still running. Open it read-only and not immutable, as the platform's SQLite
capability does, and each query sees exactly the transactions committed so
far. Every transaction leaves every foreign key satisfied: a reader never sees
a cycle without its run, or a span without its cycle.

What a reader may trust before `metadata.final_state` is `complete`:

`metadata`:: Every key except the finalisation keys below is written once, when
recording starts, and never changes. `capture_id` among them identifies this
capture.
`steps`, `cycles`, `roc_work_spans`, `component_work_counts`, `gpui_frames`, `gpui_native_work`, `gpui_frame_cycles`, and `virtual_list_frames`:: Append-only.
A committed row is never updated or deleted, and ids only grow, so a reader
that remembers the largest id it read finds exactly what arrived since with
`id > ?`. A cycle arrives with its spans and component work, and a frame with
its native work and the cycles it drew, in one transaction.
`runs`:: A run's row arrives when it starts, with outcome `running` and every
end column `NULL`, and is updated once, when it ends.
`gpui_frame_work`:: Recorded after its frame, possibly in a later transaction,
so a frame with no work rows yet may still receive them.

What exists only once `final_state` is `complete`, and must not be read as
evidence before then:

`measurement_status`:: Every family is `unfinalized` until finalisation decides
its status, reason, and row counts.
`recorder_health`:: Absent until finalisation writes its one row.
`recording_gaps`:: Written at finalisation.
`final_state`, `clean_shutdown`, and the drain keys of `metadata`:: `final_state`
is `recording` and `clean_shutdown` is `0` until the recorder finalises, then
`complete` and, as the last write, `1`.

A verdict, a comparison, or a scaling judgement rests on those, so a reader
withholds it until the capture is finalised. A capture whose recorder died
reads the same as one still being written; neither has a verdict.

The Observatory example follows this contract. A capture it opens before
finalisation is marked _Recording_ and watched through the platform's database
watch, which reports each commit to the capture or its write-ahead log; when a
commit wrote rows past the largest ids it read, or ended a run, or finalised
the capture, it reads the capture again and shows the new rows where the
person is. Its verdicts read _capture not yet finalised_ until then.

`capture_id` is a random 128-bit identifier drawn when recording starts. It
carries no machine, user, path, or clock. A reader that sees a file's
`capture_id` change knows the file was replaced by another capture rather than
grown, and reads it again from the start.

== Comparison identity and privacy

A capture stores comparison-relevant build, executable, workload, recorder,
operating-system, architecture, and CPU properties. It never stores usernames,
home-directory paths, hostnames, environment variables, command lines,
application text or state, native pointers, or machine identifiers.

The capture identity, `capture_id`, is random and names only the capture; it is
excluded from every comparison, because two captures are never the same one.

Grant tokens, selected resource names and paths, trusted-dialog contents,
network destinations, device identifiers, clipboard values, and capture-source
identities are likewise excluded. Resource owners record bounded categories and
counters; unavailable authority or enforcement evidence remains absent rather
than being reconstructed from diagnostics.

Compiler and application revisions are represented as unavailable unless they
are supplied by their owning build process. Missing identity weakens a
comparison; it is never guessed.

The Observatory example reads this identity from two captures, each through a
connection of its own, and gates a comparison on it key by key: a key absent or
unavailable in either capture fails the gate rather than being assumed equal.
A second run of the same executable, an A/A capture, bounds the noise of every
difference it shows.
